> 日期：2026-09-22
> 涉及：主插件 `ev-schedule-sync`（v1.0.29 → **v1.0.30**）、最小实验 `tab-experiment`（v1.1.0 → **v1.1.1**）

> 一句话结论：**`ui::render()` 绝对不能放进 `spawn` 的异步任务里；必须在 `on_ui_event` 的同步调用栈内调用。**

**只要在 `on_ui_event` 里看到 `spawn(async move { ... ui::render_main_ui(...) ... })` —— 就是这个 bug。**

| 检查项 | ✅ 正确 | ❌ 错误 |
|--------|--------|--------|
| `on_ui_event` 里的渲染 | 同步调用 `ui::render_main_ui()` | 包在 `spawn(async { ... })` 里 |
| 状态变更（改 `state.page` 等） | 在回调同步栈内 | 在 spawned task 里 |
| 需要 `.await` 的宿主 IO | `wit_bindgen::block_on(async { host_fn().await })` | 在 spawned task 里 `.await` |
| `make_empty_*_future()` | 只用来填 future，可继续用 spawn | —（它无害，别误伤） |

## 1. 症状

- 插件**能装上、能打开、能首屏渲染**。
- 但点「导入 / 导出」Tab（或任何切页按钮）**界面毫无反应**——不是崩溃，不是报错，就是**不刷新**。
- 重启插件、重新安装、换设备都一样。
- 这是主插件从 **v1.0.20 一直到 v1.0.29** 反复出现的老毛病（「切页无效」）。

---

## 2. 根因

### 2.1 一句话

**渲染的「时机」错了，不是渲染的内容错了。**

`ui::render()` 必须在 `on_ui_event` 的**同步调用栈内**完成。
一旦把它包进 `spawn(async move { ... })`，渲染就被推迟到 `on_ui_event` **返回之后**执行，
这次重绘落在事件回调上下文之外，**宿主不认**，于是界面不刷新、按钮点了没反应。

### 2.2 时序对比

```
❌ 异步 spawn（错误）
   宿主调用 on_ui_event ──▶ 立刻 spawn 一个 task，然后返回 reader
                              │
                              └─(回调已返回)-▶ task 才执行：
                                                改 state.page
                                                ui::render_main_ui()   ← 太晚了，宿主不认
   ────────────────────────────────────────────────────────────────
✅ 同步（正确）
   宿主调用 on_ui_event ──▶ 改 state.page
                            ui::render_main_ui()      ← 就在本次回调里
                          ──▶ 返回 reader
```

### 2.3 为什么 `make_empty_string_future()` 也用 spawn 却没事？

因为它内部的 spawn **只负责写一个空字符串去完成 future**，渲染早就同步做完了。
**用了 `spawn` 不是罪，「把 render 放进 spawn」才是罪。** 这个区分很关键，别一看到 spawn 就以为矛盾。

---

## 3. 为什么折腾了好几版才发现（复盘）

主插件从第一版起 `on_ui_event` 就是 `future_new + spawn` 写法，所以它**从来没「好过」过，一直缺对照样本**。
于是每一次「修复」都在改**布局**（无关变量），而问题在**时序**：

| 曾经的诊断 | 实际 |
|-----------|------|
| v1.0.22：写死像素宽度溢出 | ❌ 替罪羊 |
| v1.0.23：`flex(Row)` 横向布局不可用 | ❌ 替罪羊 |
| v1.0.28：overlay 状态没清理 / 没 scroll-area | ❌ 替罪羊 |
| **真相** | **渲染被放进 spawn，时序错了** |

**转折点**：做最小实验 `tab-experiment` 时第一次用了**同步写法**，切换立刻生效，拿到了「能切」的对照；
随后在 demo 里加了「EV 连接检测」、为支持 `.await` 顺手把事件改成异步 spawn —— **切换立刻失效**。
这一正一反的 A/B，才把「同步 vs 异步」这个变量单独暴露出来。

> 方法论教训：**当同一个现象怎么改都不好，先别继续改，先造一个「能复现最小对照组」把变量隔离出来。**

## 4. 修复代码（before / after）

### 4.1 `on_ui_event`：从异步 spawn 改为同步

**❌ 修复前**（`src/lib.rs`，v1.0.20 ~ v1.0.29 一直是这个）

```rust
fn on_ui_event(
    event_id: String,
    event: event::Event,
    event_payload: String,
) -> FutureReader<String> {
    let vtable = &<String as crate::wit_future::FuturePayload>::VTABLE;
    let (writer, reader) = unsafe { future_new::<String>(String::new, vtable) };

    spawn(async move {                                   // ← 元凶
        let needs_render = handle_ui_event_inner(&event_id, &event, &event_payload).await;
        if needs_render {
            let target = STATE.lock().unwrap().render_target.clone();
            if !target.is_empty() {
                ui::render_main_ui(&target);             // ← 渲染被推迟到回调返回之后
            }
        }
        let _ = writer.write(String::new()).await;
    });

    reader
}
```

**✅ 修复后**（v1.0.30 现状）

```136:155:tools/ev-schedule-sync/astrobox-build/astrobox-plugin/src/lib.rs

        event_id: String,
        event: event::Event,

        // 之前把这段包进 spawn(async { ... })，render 被延后到回调返回之后执行，
        // 宿主不认这次重绘 → 切页 / 切 Tab 全部失效。
        // 详见「Tab切换失效-根因-异步渲染.md」。需要 await 的宿主 IO 用 wit_bindgen::block_on。
        let needs_render = handle_ui_event_inner(&event_id, &event, &event_payload);

        if needs_render {
            let target = STATE.lock().unwrap().render_target.clone();
            if !target.is_empty() {
                ui::render_main_ui(&target);
            }
        }

        make_empty_string_future()
    }
```

**注意**：`event_payload` 仍要传进去（输入框的 `Change` 事件靠它取值），别顺手写成 `_event_payload`。

### 4.3 需要 `.await` 的宿主 IO：改用 `wit_bindgen::block_on`

主插件有两处真正的异步宿主调用（设备列表、剪贴板），必须保留 `.await`，
解决办法是**在同一同步回调里用 `block_on` 把它跑完，再回到同步路径统一 render**：

```250:263:tools/ev-schedule-sync/astrobox-build/astrobox-plugin/src/lib.rs
            "btn-goto-select-device" | "btn-refresh-devices" => {
                // 需要 await 的宿主 IO：block_on 同步等结果，再回到同步路径统一 render。
                // （宿主 import 返回的是 RawFutureReader，只实现 IntoFuture，需用 async 块包一层）
                let devices = wit_bindgen::block_on(async { device::fetch_devices().await });
                let mut state = STATE.lock().unwrap();
                // 已经在设备页时（点的是刷新），别把 SelectDevice 记成来源标签页
                if state.page != Page::SelectDevice {
                    state.previous_tab = state.page.clone();
                }
                state.devices = devices;
                state.page = Page::SelectDevice;
                state.guard_error.clear();
                true
            }
```

> `wit_bindgen::block_on` 在 `wit-bindgen 0.57.1` 里存在
> （`src/rt/async_support.rs:545`，经 `#[cfg(feature = "async")]` 从 `wit_bindgen::` 根导出），
> 当前 `Cargo.toml` 的 `features = ["async", "async-spawn"]` 已覆盖。

### 4.4 ⚠️ `block_on` 的坑：不能直接收宿主 import 的返回值

直接写 `wit_bindgen::block_on(clipboard::write_text(&t))` 会**编译失败**：

```
error[E0277]: `RawFutureReader<&FutureVtable<Result<(), ()>>>` is not a future
```

原因：宿主 import 的返回值是 `RawFutureReader`，它**只实现 `IntoFuture`，不实现 `Future`**。
`.await` 能用（走 `IntoFuture`），但 `block_on` 的签名要求 `impl Future`。

**正确写法：用 `async {}` 块包一层**（`async` 块本身是 `Future`，内部再 `.await`）：

```rust
// ✅
let devices = wit_bindgen::block_on(async { device::fetch_devices().await });
let ok      = wit_bindgen::block_on(async { clipboard::write_text(&text).await }).is_ok();
```

> 例外：自己写的 `async fn`（如 demo 的 `check_ev_connection()`）返回值是**真正的 `Future`**，
> 可以直接 `wit_bindgen::block_on(check_ev_connection())`，无需包 `async {}`。

## 8. 一句话记住它

> **改状态 + render，必须在同一个同步调用栈里一起完成。**
> **要 await 宿主 IO，就 `block_on` 把它跑完再 render。**
> **永远不要在 `spawn` 的任务里碰 `ui::render_main_ui()`。**
