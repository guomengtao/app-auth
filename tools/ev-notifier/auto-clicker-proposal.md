# Mac 端自动点击小工具 - 需求分析与方案设计

## 一、原始需求整理

### 1. 核心功能
- 在屏幕任意位置创建一个**可拖拽、可调整大小**的矩形选框
- 选框内每 **10 秒** 自动执行：向下滚动列表 → 点击某个元素
- 无限循环执行

### 2. UI 要求
| 要求 | 说明 |
|------|------|
| 顶部菜单栏图标 | 类似 ev-notifier，纯菜单栏 App，Dock 不显示图标 |
| 计数显示 | 小窗口显示本地点击次数 |
| 控制按钮 | 关闭按钮、暂停/继续按钮 |
| 多实例 | 菜单中点击"新建"可创建多个选框，每个独立运行，可移动到不同位置 |

### 3. 使用场景
- AI 对话框偶尔弹出"操作确认"按钮
- 用户离开时卡住工作流程
- 需要自动点击这些确认按钮，保持 AI 继续工作

---

## 二、需求合理性分析

### ✅ 合理的部分
| 点 | 理由 |
|----|------|
| 菜单栏 App 形态 | 轻量、不占 Dock 空间，适合常驻工具 |
| 多实例 | 可能需要同时监控多个窗口/页面 |
| 暂停/恢复 | 用户需要手动操作时暂停自动点击 |
| 计数统计 | 了解工具实际点击了多少次 |

### ❌ 有问题的部分

#### 1. 屏幕坐标方案本身很脆弱
| 问题 | 说明 |
|------|------|
| 分辨率变化 | 外接显示器插拔、分辨率调整后坐标全乱 |
| 窗口位置变化 | AI 对话框窗口被移动后选框就对不上了 |
| 多桌面/全屏 | macOS 多桌面切换时坐标体系不同 |
| 遮挡问题 | 其他窗口遮挡目标区域时，点击会点到错误的窗口 |
| 鼠标抢占 | 模拟鼠标点击会**抢占用户真实鼠标**，用户体验极差 |

#### 2. "向下滚动列表再点击"逻辑不可靠
- 不同 AI 平台（ChatGPT、Claude、Copilot 等）UI 布局完全不同
- 确认按钮不一定在列表底部，可能在弹窗中间
- 滚动操作可能触发懒加载、无限滚动等副作用
- 10 秒固定间隔太死板，确认弹窗出现时机不固定

#### 3. 实现复杂度高
- macOS 屏幕选框需要处理窗口层级、鼠标事件穿透
- 跨进程模拟点击需要 Accessibility 权限
- 多实例管理复杂

## 三、更好的替代方案

### 🥇 方案 A：智能元素检测 + 自动点击（推荐）

```
不是框屏幕区域，而是智能检测"确认按钮"并自动点击
```

**原理**：
1. 使用 macOS **Accessibility API**（`AXUIElement`）监听前台应用
2. 检测浏览器中出现的按钮文本（如"确认"、"继续"、"Yes"、"Continue"、"Run anyway"等）
3. 匹配到目标按钮后，通过 Accessibility API 直接点击该元素
4. **不移动真实鼠标**，不影响用户操作

**优势**：
| 对比维度 | 屏幕选框方案 | 智能检测方案 |
|----------|-------------|-------------|
| 分辨率/窗口位置 | ❌ 敏感 | ✅ 无关 |
| 多桌面 | ❌ 有问题 | ✅ 正常 |
| 鼠标抢占 | ❌ 抢占 | ✅ 不影响 |
| 多平台适配 | ❌ 需重新选框 | ✅ 统一处理 |
| 可靠性 | ❌ 低 | ✅ 高 |

**实现方式**：
```python
# 伪代码示例
import Quartz
# 监听所有应用的 Accessibility 事件
# 检测按钮文本匹配关键词列表
# 通过 AXPress 直接点击，不移动鼠标
```

### 🥈 方案 B：浏览器扩展方案

如果 AI 对话主要发生在浏览器中，写一个浏览器扩展更简单：

1. 注入 JS 到页面，监听 DOM 变化
2. 使用 MutationObserver 检测确认按钮的出现
3. 自动 `.click()` 目标按钮
4. 通过本地 WebSocket 与菜单栏 App 通信，显示计数

**优势**：精准、不影响鼠标、跨平台
**劣势**：仅限浏览器场景

### 🥉 方案 C：混合方案（最实用）

```
智能检测为主 + 手动选框为辅
```

- **默认模式**：智能检测（方案 A），自动识别确认按钮
- **兼容模式**：如果智能检测无法覆盖某个应用，允许用户手动框选区域作为兜底
- 手动选框模式下，使用 `CGEvent` 发送点击事件到目标窗口（不抢占鼠标）

## 四、推荐方案详细设计

### 架构

```
┌─────────────────────────────────────────┐
│           菜单栏 App (rumps)             │
│  ┌─────────────────────────────────────┐ │
│  │  新建监控    │  暂停全部  │  退出    │ │
│  │  计数: 12    │  规则配置  │  日志    │ │
│  └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
          │
          ▼
┌─────────────────────────────────────────┐
│           监控引擎 (每实例)               │
│  ┌─────────────────────────────────────┐ │
│  │  Accessibility 监听                 │ │
│  │  -> 检测按钮文本                    │ │
│  │  -> 匹配规则                        │ │
│  │  -> 自动点击                        │ │
│  │  -> 计数 + 日志                     │ │
│  └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

### 技术选型

| 组件 | 技术 |
|------|------|
| 菜单栏 App | `rumps`（与 ev-notifier 一致） |
| Accessibility 监听 | `Quartz` / `pyobjc-framework-Quartz` |
| 元素检测 | `AXUIElement` API |
| 模拟点击 | `AXUIElementPerformAction` + `kAXPressAction` |
| 配置存储 | JSON 文件（与 ev-notifier 一致） |
| 多实例管理 | 每个实例一个独立线程 |

### 核心规则配置

```json
{
  "rules": [
    {
      "name": "AI确认按钮",
      "match_buttons": ["确认", "继续", "Confirm", "Continue", "Yes", "Run"],
      "match_roles": ["AXButton", "AXStaticText"],
      "enabled": true,
      "cooldown_seconds": 5
    },
    {
      "name": "Claude限制提示",
      "match_buttons": ["Retry", "Try again", "重试"],
      "enabled": true,
      "cooldown_seconds": 10
    }
  ],
  "exclude_patterns": ["删除", "Delete", "注销", "Logout"],
  "global_cooldown": 3
}
```

### 安全机制

| 机制 | 说明 |
|------|------|
| **排除名单** | 永不点击包含"删除"、"注销"等危险词的按钮 |
| **冷却时间** | 同一按钮两次点击之间强制间隔 |
| **全局冷却** | 任意两次点击之间最小间隔 3 秒 |
| **暂停快捷键** | 全局快捷键一键暂停所有实例 |
| **日志记录** | 每次点击记录时间、应用、按钮文本，可回溯 |
| **窗口限制** | 可配置仅监控特定应用/窗口标题 |

## 六、结论与建议

| 项目 | 建议 |
|------|------|
| **首选方案** | 方案 A（智能元素检测），不抢占鼠标、不受窗口位置影响 |
| **是否保留选框** | 作为兜底，智能检测无法覆盖时使用 |
| **多实例** | ✅ 保留，每实例可绑定不同应用/规则 |
| **计数显示** | ✅ 保留，每实例独立计数 |
| **暂停/恢复** | ✅ 保留，支持全局 + 单实例暂停 |

**核心观点**：不要用"框屏幕区域模拟鼠标"的方案，太脆弱。用 Accessibility API 直接检测按钮元素并点击，既不抢鼠标，又不受分辨率和窗口位置影响。这才是正确的做法。
