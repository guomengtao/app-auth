# EvNotifier 鉴权改造方案：用「后台同款登录」替换共享密钥

> 目标：把客户端那种「手工往 `.env` 里塞一个共享密钥」的开发感做法，换成
> **和网站后台同一套登录（Vercel OAuth + 仅授权账号）+ 登录后长期记住**
> 的桌面软件体验，并且更安全、可撤销、可审计。
>
> 结论先说：**方向完全可行，但有两个前置问题必须先解决**，否则新方案会把客户端
> 挂在一个「形同虚设」的鉴权上。

---

## 0. 结论速览

> 🚀 **阶段 1 已落地（2026-09-26 / main v1.7.79 / ev-notifier v2.3.25）**
>
> **你要做的只有一次**：点状态栏 EvNotifier 菜单 →「**登录 EvNotifier…**」→ 浏览器自动打开
> → 点「**授权此设备**」→ 完成。之后永久有效，换机器只需重复这一次。
>
> 落地内容：`lib/device-token.js`（只存 sha256、可撤销、带 last_seen 审计）、`api/ev.js`
> （`device-start/poll/approve/revoke` + `devices`）、`ev-login.html` 确认页、
> `/api/oauth` 支持 `?next=` 回跳、`clientHasAccess()` 支持 `x-ev-device-token`、
> 客户端 Keychain 读写 + 登录菜单 + 未登录横幅 + 401 自动清理并提示。
>
> **想彻底停用共享密钥**：Vercel 加 `EV_AUTH_MODE=strict` → 再删掉 `EV_SYNC_TOKEN`。
> （strict 只认设备令牌和后台 cookie，不再放行匿名、不再接受共享密钥。）

## 1. ⛔ P0 前置：先修「后台鉴权可被伪造」

> ✅ **已于 2026-09-26 修复并上线验证**（main v1.7.78）。
> 修复内容：`lib/auth.js` 删除 `_vercel_jwt` 信任分支；`api/admin/health.js` 的 `section=me`
> 同步删除；`lib/vercel-auth.js` 改为委托 `requireAuth`（去掉「只解码」能力）。
> 另加两处加固：`req/req.headers` 缺失时返回 401 而不是抛 TypeError；缺 `exp` 的 token 一律拒（不再永不过期）。
> 新增回归测试 `test/auth-forged-cookie.test.js`（23 项）。
>
> **线上验证（修复后）**：伪造 cookie → `section=me` **401**、`section=stats` **401**；
> 对照：`delivery-sync` 带设备 token → 200、`admin_Dx23.html` → 200、无凭据 → 401。
>
> ⚠️ **如果你之前只靠 Vercel SSO 访问后台**（浏览器里只有 `_vercel_jwt`、没有 `token`），
> 修复后会被 401，需要走一次 `/api/oauth` 重新登录。本机实测线上**未启用** Deployment Protection
> （`admin_Dx23.html` 无 `Set-Cookie: _vercel_jwt`、无 302），所以正常走 `/login_aXs12.html`
> 登录的用户**不受影响**。

### 1.1 漏洞原貌（保留供存档）

```68:96:lib/auth.js
function requireAuth(req) {
  var cookies = parseCookies(req.headers.cookie || "");

  var vercelJwt = cookies["_vercel_jwt"];
  if (vercelJwt) {
    try {
      var parts = vercelJwt.split(".");
      if (parts.length === 3) {
        var payload = JSON.parse(Buffer.from(parts[1], "base64url").toString("utf8"));
        if (payload.email && payload.email.toLowerCase() === ADMIN_EMAIL) {
          return { authorized: true, username: payload.email };
        }
        return { authorized: false, error: "only " + ADMIN_EMAIL + " allowed", status: 403 };
      }
    } catch (e) {}
  }
  ...
```

`parts[1]` 只是 **base64 解码**，`parts[2]`（签名）**从头到尾没被校验**，连 `exp` 都不看。

### 1.2 实测验证（2026-09-26，只读请求）

```bash
# 构造一个"签名随便填"的 cookie
H=$(printf '{"alg":"HS256","typ":"JWT"}' | base64 | tr -d '=')
P=$(printf '{"email":"guomengtao@gmail.com","name":"forged"}' | base64 | tr -d '=')
COOKIE="_vercel_jwt=$H.$P.this-signature-is-never-checked"
```

| 请求 | 结果 |
|---|---|
| `GET ?section=me`（带伪造 cookie） | `{"success":true,"email":"guomengtao@gmail.com","name":"forged","provider":"vercel"}` |
| `GET ?section=stats`（带伪造 cookie） | **HTTP 200**，返回真实数据：`totalRedeemCodes: 212, totalActivations: 141` |
| `GET ?section=me`（不带 cookie） | HTTP 401（对照组） |

**影响面**：`api/admin/health.js:870-873` 的鉴权门之后有全部管理接口 ——
兑换码、激活记录、订单、配额、备份、日志、数据库切换、`run-task`（可执行定时任务）等，
**目前任何人都能访问**。

> 这比 `EV_SYNC_TOKEN`（48 位随机值，需要泄露才能利用）严重得多：
> 这个漏洞的利用成本是「一行 base64」，不需要任何密钥。

### 1.3 为什么会这样 + 修法

**历史动机推断**：`_vercel_jwt` 是 Vercel 平台自己的「Deployment Protection / Vercel Authentication」
种的 cookie。当初大概是为了「让 Vercel 平台层已经鉴权过的用户直接进后台」而信任它。

**修法（推荐）**：**删掉这个分支**，只信任自签的 `token` cookie（`verify()` + `ADMIN_EMAIL` + `provider==="vercel_oauth"`）。

```js
// lib/auth.js 替换掉 71-83 行的 _vercel_jwt 分支
// 不要信任任何非自签 cookie：_vercel_jwt 是平台种的，我们拿不到它的签名密钥，
// 所以只能"验签"或"不信任"——没有第三条路。
```

**代价与配套**：
- 如果线上开了 Vercel 的 Deployment Protection，删掉后 `_vercel_jwt` 用户需走一次
  `/api/oauth` 登录（体验损失一次，可接受）；
- 同时检查其它信任 `_vercel_jwt` 的地方（`api/admin/health.js` 的 `section=me`、`lib/vercel-auth.js:24-45`），一并处理；
- 加回归测试：伪造 cookie 必须 401/403（见 §9）。

## 3. 关键约束（决定了方案形态）

| 约束 | 出处 | 对方案的影响 |
|---|---|---|
| 后台登录 session 存在 **HttpOnly + Secure + SameSite=Lax** 的 `token` cookie 里 | `api/oauth.js:135` | **客户端不能靠"读 WebView 的 cookie"拿凭据**（HttpOnly 连 JS 都读不到）→ 必须用**设备授权流程** |
| 只有 24h 的 JWT，**没有 refresh 机制** | `lib/auth.js:8` | 「记住登录」需要**新增**长期令牌，不能靠现有机制 |
| `REDIRECT_URI` 硬编码为 `https://app-auth.gudq.com/api/oauth` | `api/oauth.js:8` | 登录流程必须走线上域名；本地开发无法完整联调 |
| 客户端**直连 Upstash**（TCP 6379 + TLS）订阅 `auth:push_channel` | `ev_notifier.py:redis_loop` | 这是「免配 env」绕不过去的一环（见 §5 阶段 2） |
| Vercel 函数**没有任何 `maxDuration` 配置** | `vercel.json` 全文无 `functions` 字段 | 要做 SSE 长连接必须先加配置（见 §5.3） |

## 4. 阶段 1：设备授权登录（替换 `EV_SYNC_TOKEN`）

### 4.1 设计要点

- **一次性登录，长期有效**：不引入 access/refresh 双层（只有一个用户，没必要）。
  登录成功后发一个 **长期设备令牌**，存 Keychain，之后所有请求直接带它。
- **不依赖 WebView 读 cookie**：用「设备授权码」把浏览器里的登录态"接"给客户端。
- **可撤销、可审计**：服务端存令牌哈希 → 能看到「哪个设备、何时登录、最后活跃」，可一键撤销。
- **失败可见**：未登录时状态栏明确显示「未登录（点击登录）」，而不是静默不出通知。

### 4.2 流程图

```
① 客户端      POST /api/ev/device/start
   （无凭据）    ← { challenge, user_code, verify_url, interval }
                服务端把 challenge 存 Redis（TTL 10 分钟）
                             ↓
② 客户端      自动打开浏览器 → verify_url
              菜单栏同时显示 user_code，便于人工核对
                             ↓
③ 浏览器      GET /ev-login?c=<challenge>
   （走后台登录态）  ├─ 未登录 → 302 到 /api/oauth（Vercel OAuth）
              │            登录后带 ?next= 回到本页
              └─ 已登录 → 显示「授权设备 EvNotifier（MacBook-Air）」+ 确认按钮
                             ↓
④ 浏览器      POST /api/ev/device/approve { challenge }（带 cookie）
              服务端校验 requireAuth + email === ADMIN_EMAIL
              → 生成 device_token（32B 随机），存 sha256 哈希 + 元数据
              → 把 challenge 置为 approved
                             ↓
⑤ 客户端      POST /api/ev/device/poll { challenge }   （每 2s 轮询，最多 5 分钟）
              未就绪 → 202 {status:"pending"}
              就绪   → 200 { device_token, email }（**只返回一次**）
                             ↓
⑥ 客户端      把 device_token 存进 macOS Keychain
              下次启动直接读取使用（无需再登录）
```

### 4.3 接口清单（全部新增，不动现有接口）

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `POST /api/ev/device/start` | 无 | 返回 `challenge`（随机 32B）+ `user_code`（8 位大写，便于人工核对）+ `verify_url` |
| `GET /ev-login?c=<challenge>` | **后台 cookie** | HTML 确认页；未登录先跳 OAuth，回来继续（带 `?next=`） |
| `POST /api/ev/device/approve` | **后台 cookie** | `requireAuth` + `email===ADMIN_EMAIL`；绑定 challenge |
| `POST /api/ev/device/poll` | 无（凭 challenge） | 轮询取 token；**取到即作废 challenge** |
| `POST /api/ev/device/revoke` | **后台 cookie** | 撤销某设备（或全部） |
| `GET /api/ev/devices` | **后台 cookie** | 列出已授权设备（面板里展示） |

> 现有 `delivery-*` 三个端点的 `clientHasAccess()`（`api/admin/health.js:38-56`）
> 改为：**优先校验 `x-ev-device-token`**，`EV_SYNC_TOKEN` 作为过渡期内保留的兼容分支。

### 4.4 数据模型（复用现有 Postgres / Redis，不新建表也行）

建议新建一张表（可审计、可加索引）：

```sql
create table if not exists device_tokens (
  id            bigserial primary key,
  token_hash    varchar(64)  not null unique,   -- sha256(device_token)，不存明文
  label         varchar(128) not null,          -- 人类可读设备名（default: hostname）
  email         varchar(128) not null,          -- 授权账号
  created_at    timestamptz  not null default now(),
  last_seen_at  timestamptz,
  last_seen_ip  varchar(64),
  revoked_at    timestamptz,
  app_version   varchar(32)
);
create index if not exists idx_device_tokens_hash on device_tokens(token_hash);
```

> 过渡期内也可以用 Redis hash（`ev:device:<sha256>`）实现同样的东西。
> 但**要落表**才好做「面板里看设备列表」和长期审计；而且 `ensureTables()` 已经
> 有建 `message_delivery` 的先例（`lib/postgres.js`），加一张成本很低。

### 4.5 客户端改动（`ev_notifier.py`）

| 项 | 做法 |
|---|---|
| 登录 | 新增菜单项「登录 / 重新登录」；执行 `device_start` → `open` 浏览器 → 轮询 → 存 Keychain |
| 令牌存储 | **macOS Keychain**（系统自带 CLI，零依赖）<br>`security add-generic-password -a ev-notifier -s ev-notifier-device -w "$T" -U`<br>`security find-generic-password -a ev-notifier -s ev-notifier-device -w` |
| 令牌注入 | 复用现有 `_auth_headers()`，只是 header 换成 `x-ev-device-token`（或沿用 `x-ev-sync-token`，减少改动面） |
| 未登录状态 | 状态栏标题显示 `Ev vX (未登录)`；面板顶部红条「未登录，通知无法接收 —— 点击登录」；**不要静默失败** |
| 令牌失效（401） | 自动清 Keychain + 变成「未登录」态 + 发一条系统通知提示重新登录（**只提示一次**，别刷屏） |
| 兼容 | 若 Keychain 无令牌但 `.env` 里有 `EV_SYNC_TOKEN`，回退用它（过渡期，用户无需立刻操作） |

### 4.6 安全要点

- `device_token` **只存哈希**（数据库泄露也无法直接使用）；
- `challenge` TTL 10 分钟、一次性（poll 取到即作废）；
- `approve` 必须**同时**满足 `requireAuth` + `email === ADMIN_EMAIL`（沿用后台白名单）；
- 令牌**不参与 URL**，只走 header（避免出现在日志/Referer）；
- 面板加「已授权设备」列表 + 撤销按钮 → 换机器/怀疑泄露时一键踢掉；
- 客户端日志**永不打印令牌**（只打印前 8 位指纹）。

## 5. 阶段 2：消灭 `.env`（把实时推送也搬到服务端）

阶段 1 之后 `EV_SYNC_TOKEN` 没了，但客户端**仍然直连 Upstash**，所以 `.env` 还得有
`KV_REST_API_URL` / `KV_REST_API_TOKEN`（**主密码级，全库可读写**）。
要真正「像独立软件」，必须让客户端**只跟自己的服务端说话**。

### 5.1 两条路线对比

| | A. SSE 长连接（推荐） | B. 短轮询 |
|---|---|---|
| 实现 | `GET /api/ev/stream`，`text/event-stream`，服务端把新消息推给客户端 | 客户端每 5s 调 `GET /api/ev/sync?after=<cursor>` |
| 实时性 | **秒级**（与现在直连 PUB/SUB 体感一致） | 3–15s（可做自适应退避） |
| 断线续传 | `Last-Event-ID`（**正好等于我们的 `seq`**） | 天然就是游标，无需额外设计 |
| Vercel 限制 | 需要 `maxDuration`（函数会被强制断开，客户端需自动重连）；每个连接占一个实例 | 无限制，单次 ~100ms |
| 成本（1 个用户） | 每小时 ~60 次连接 | ~17000 次请求/天，约 0.5 GB-hour/月，远低于免费额度 |
| 复杂度 | 中（要处理重连、心跳、服务端轮询上流） | **低** |

> 两者都**天然复用**已经落地的 `seq` 游标 + `delivery-sync` 接口 —— 因为
> 「实时」和「补拉」在服务端都是「`SELECT ... WHERE id > cursor`」，只是返回管道不同。

### 5.2 推荐：SSE 为主 + 轮询兜底

```
客户端                         服务端 /api/ev/stream
  │  GET (带 device token, Last-Event-ID: <last_seq>)
  ├──────────────────────────────►
  │                                循环：
  │                                  SELECT * FROM message_delivery
  │                                   WHERE id > cursor ORDER BY id LIMIT 200
  │                                  有新数据 → 立即 flush 一帧
  │                                  无数据   → 每 1s 重查（或等 Upstash PUB/SUB 通知）
  │  ◄──── data: {"seq":305,...}\n\n
  │  ◄──── data: {"seq":306,...}\n\n
  │  ◄──── : heartbeat\n\n            （每 15s 注释帧，防中间层超时断连）
  │  （函数到时被断）→ 客户端带 Last-Event-ID 立刻重连，一条不丢
```

实现要点：
- `vercel.json` 加 `functions` 配置（给 `/api/ev/stream` 单独的 `maxDuration`；Hobby 有上限，Pro 更长）；
- 服务端**不要在 SSE 里再订阅 Upstash PUB/SUB**（不可靠、要长连接），直接**轮询 Postgres**，1s 一次（对单用户成本可忽略）；
- 心跳帧 + `Last-Event-ID` 续传 + 客户端指数退避重连；
- SSE 连续失败 N 次 → 降级到短轮询（保证「一定收得到」）。

### 5.3 阶段 2 之后的收获

- `.env` **可以完全删掉** → 换机器只需 `git clone` + 装依赖 + 点一次登录；
- Upstash 主密码**不再离开服务端**（客户端被攻破也拿不到全库读写权限）；
- 推送链路可观测（服务端能看到「谁在线、推到哪了」）。

## 6. 三阶段收益对照

| 维度 | 现在（共享密钥） | 阶段 1（登录 + 设备令牌） | 阶段 2（+ 服务端推送） |
|---|---|---|---|
| 换机器要做什么 | 手工复制 `.env`（**而 token 在 Vercel 是 Secret，`vercel env pull` 拉不到**，忘了就永久 401） | `git clone` + 装依赖 + 点一次「登录」 | 同左，且**无需 `.env`** |
| 泄漏一个值就能冒充？ | 是（48 位串，泄露即失效边界） | 否（泄漏只能冒充**那一台**，且可一键撤销） | 否，且 Upstash 凭据不落地客户端 |
| 能不能看到"谁在用" | 看不到 | 面板可见设备列表 + 最后活跃时间 | 同左 |
| 撤销能力 | 只能**全局轮换**（所有客户端一起断） | 逐设备撤销（不影响其它） | 同左 |
| 实时性 | 秒级（直连 PUB/SUB） | 秒级（**不变**） | 秒级（SSE） |
| 客户端持有的敏感凭据 | Upstash 主密码 + 共享密钥 | Upstash 主密码 + 设备令牌(Keychain) | **仅设备令牌** |

## 7. 需要你先决策的 5 件事

1. **P0 漏洞怎么修**：直接删掉 `_vercel_jwt` 信任分支（推荐），还是先保留但**加验签**？
   （注：`_vercel_jwt` 的签名密钥在 Vercel 平台侧，我们拿不到 → 实际只有"不信"这一条路。）
2. **Vercel 计划**：Hobby 还是 Pro？决定 SSE 能否启用（阶段 2 的形态）。
3. **实时性要求**：必须秒级（→ 阶段 2 走 SSE），还是 5–15s 可接受（→ 直接短轮询，实现量最小）？
4. **阶段 1 是否要双令牌**（access + refresh）？我建议**不要** —— 单设备长期令牌 + 撤销更简单也更安全。
5. **是否保留 `EV_SYNC_TOKEN` 过渡期**？建议：保留一个版本周期（客户端优先用设备令牌，没有则回退 `.env`），确认稳定后再删。

## 9. 验收标准

| 场景 | 期望 |
|---|---|
| 伪造 `_vercel_jwt` cookie 访问 `section=stats` | **401/403**，且日志有告警 |
| 未登录客户端 | 状态栏明确显示「未登录」，面板有引导；**不静默失败** |
| 全新 Mac：clone + 装依赖 + 点「登录」 | 浏览器确认一次 → 通知/补拉全部正常，**无需手工配任何 token** |
| 登录后重启 Mac / 重启客户端 | 自动恢复（Keychain 读取），**不需再次登录** |
| 面板撤销某设备 | 该设备**下一次请求即 401** → 客户端转为「未登录」并提示一次 |
| challenge 过期（>10 分钟）再 poll | 明确报错，客户端提示重新发起登录 |
| 设备令牌泄漏（模拟） | 撤销后立即失效；其它设备不受影响 |
| 阶段 2：停掉 Upstash 侧 PUB/SUB | 通知仍能用（因为走服务端 SSE 而不是直连订阅） |

## 10. 使用说明（阶段 1 已上线）

### 首次登录（每台机器只有一次）
1. 状态栏点 EvNotifier 图标 →「**登录 EvNotifier…**」（会自动打开浏览器）
2. 浏览器里的 `/ev-login` 页面：
   - 若提示"需要先登录管理员账号" → 点按钮走 Vercel 登录，**登录后会自动回到本页**（靠 `?next=`）
   - 已登录 → 确认设备信息 → 点「**授权此设备**」
3. 页面显示"授权成功"，客户端几秒内自动完成并弹「登录成功」通知

### 怎么确认生效了
```bash
# 状态栏菜单 →「状态」里应显示：Auth: 已登录
grep -i "device token" ~/.ev_debug.log     # 应看到 device_login: OK, token stored (fingerprint xxxxxxxx…)
```
面板顶部不再出现红色「未登录」横幅；`Auth:` 不再是「未登录」。

### 换机器
`git clone` → 装依赖（§2）→ 用新机器的 python 跑一次脚本（自动重写 LaunchAgent）→ **点一次「登录 EvNotifier…」**。
不需要再搬运任何密钥（这正是阶段 1 要解决的问题）。

### 撤销某台设备
```bash
# 列出（需后台登录态 cookie；或临时带 CRON_SECRET）
curl -s "https://app-auth.gudq.com/api/ev?action=devices" -H "Cookie: token=<你的后台 token>"

# 撤销
curl -s -X POST "https://app-auth.gudq.com/api/ev?action=device-revoke&id=<设备id>" -H "Cookie: token=<...>"
```
被撤销的机器下次请求会拿到 401 → 客户端自动清掉钥匙串条目、状态变「凭据失效」并**只提示一次**「需要重新登录」。
> 后台面板的「已授权设备」UI 还没接（接口已就绪），需要时可以先手搓上面的 curl。

### 最终停用共享密钥（可选，建议观察一段时间后再做）
1. Vercel 环境变量加 `EV_AUTH_MODE=strict`
2. 删掉 `EV_SYNC_TOKEN`（Vercel + 本机 `.env` 都可以删）
3. 重启客户端验证：`delivery-sync` 仍能工作（走设备令牌），匿名请求 401

> strict 模式定义：`api/admin/health.js` 的 `clientHasAccess()` 只认「设备令牌」或「后台 cookie」，
> **不再放行匿名、也不再接受共享密钥**。回滚就把 `EV_AUTH_MODE` 删掉即可。

## 11. 一句话总结

> **方向对，但顺序要反过来**：先把 `lib/auth.js` 那个「不验签就信任 `_vercel_jwt`」的洞堵上
> （实测现在任何人一行 base64 就能读你全部后台数据），
> 再做「设备授权登录 + Keychain 长期令牌 + 可撤销」替掉 `EV_SYNC_TOKEN`，
> 最后把实时推送也搬到服务端（SSE 或轮询），才能真正做到
> 「装好 → 登录一次 → 永不再配」的独立软件体验。
