## 二、可捕获的错误类型

### 2.1 Python 层面（✅ 可捕获）

| 错误类型 | 触发场景 | 当前是否记录 | 捕获方式 |
|---------|---------|:------:|------|
| `ConnectionError` | Redis 断连、网络故障 | print | `sys.excepthook` |
| `json.JSONDecodeError` | 消息体损坏、文件损坏 | 静默吞掉 | `sys.excepthook` / 函数内 |
| `ValueError` / `TypeError` | 字段类型不匹配 | 静默吞掉 | `sys.excepthook` |
| `FileNotFoundError` | JSON 文件被删 | 静默吞掉 | `sys.excepthook` |
| `OSError` | 磁盘满、权限不足 | 静默吞掉 | `sys.excepthook` |
| `KeyError` | 数据结构缺失字段 | 静默吞掉 | `sys.excepthook` |
| `subprocess.CalledProcessError` | curl/launchctl 失败 | print | `sys.excepthook` |
| `ImportError` | WebKit/WebView 缺失 | 条件判断 | `sys.excepthook` |
| `Exception`（通用） | 其他未知异常 | 少数 print | `sys.excepthook` |

### 2.2 WebView JavaScript 层面（⚠️ 部分可捕获）

| 错误类型 | 触发场景 | 可捕获？ | 方式 |
|---------|---------|:------:|------|
| JS 语法错误 | 面板 HTML 代码 bug | ⚠️ | WebView 注入 `window.onerror` |
| JS 运行时错误 | 图表渲染失败 | ⚠️ | `window.onerror` + fetch 回传 |
| CSS 渲染异常 | 样式不兼容 | ❌ | 无法捕获 |
| 网络请求失败 | fetch/XHR 到本地 | ⚠️ | 注入 fetch 代理 |

### 2.3 原生/系统层面（❌ 不可捕获）

| 错误类型 | 说明 |
|---------|------|
| 内存溢出 (OOM) | 系统 kill，Python 进程直接终止 |
| Segfault | C 扩展崩溃，进程直接终止 |
| AppKit 内部崩溃 | rumps/AppKit 在 OC 层崩溃 |
| 系统强制终止 | launchd 超时、用户 kill |
| 进程被信号杀死 | SIGKILL/SIGTERM |

> 原生/系统崩溃无法在 Python 层面捕获，但可以通过**外部守护**检测并上报。

### 3.3 实现要点

#### Step 1：添加全局异常钩子

```python
import sys
import traceback

# 在文件顶部添加
def _install_error_hook():
    original_hook = sys.excepthook
    def _global_error_handler(exc_type, exc_value, exc_tb):
        tb_str = ''.join(traceback.format_exception(exc_type, exc_value, exc_tb))
        _record_error(
            level="error",
            module="unhandled",
            type_name=exc_type.__name__,
            message=str(exc_value),
            traceback_str=tb_str,
        )
        original_hook(exc_type, exc_value, exc_tb)  # 保留默认行为
    sys.excepthook = _global_error_handler
```

#### Step 2：统一错误记录函数

```python
def record_error(level, module, type_name, message, traceback_str=None, context=None):
    """记录结构化错误到 error_log.json"""
    date_str = datetime.now().strftime("%Y-%m-%d")
    data = load_error_log()
    if date_str not in data:
        data[date_str] = []
    entry = {
        "time": datetime.now().strftime("%H:%M:%S.%f")[:-3],
        "level": level,      # error / warning / info
        "module": module,    # redis / dashboard / orders / curl / file / system
        "type": type_name,
        "message": message,
        "traceback": traceback_str,
        "context": context or {},
    }
    data[date_str].append(entry)
    if len(data[date_str]) > 200:
        data[date_str] = data[date_str][-200:]  # 保留最近 200 条
    save_error_log(data)
```

#### Step 3：改造现有异常处理

## 四、可行性评估

### 4.1 各级错误捕获能力

| 层级 | 捕获率 | 说明 |
|------|:------:|------|
| Python 未处理异常 | **100%** | `sys.excepthook` 全局覆盖 |
| 函数内 catch 后上报 | **100%** | 改造现有 except 块 |
| Dashboard HTML 渲染 | **100%** | `_refresh_content` 已有 try/except |
| WebView JS 运行时错误 | **90%** | `window.onerror` + fetch 回传 |
| WebView JS 语法错误 | **80%** | `window.onerror` 可捕获大部分 |
| Redis 连接/TLS 错误 | **100%** | 已有 try/except 覆盖 |
| curl HTTP 错误 | **100%** | subprocess 返回码检查 |
| 文件 I/O 错误 | **100%** | JSON 读写全覆盖 |
| 原生 Crash（segfault） | **0%** | 进程直接终止 |
| 系统 OOM Kill | **0%** | 无法在 Python 层捕获 |
| AppKit 崩溃 | **0%** | OC 层崩溃不传递到 Python |

**综合评估：预计可捕获约 95% 的日常运行错误。原生崩溃需依赖 macOS 崩溃报告。**

## 五、结论

### 可行性：✅ 完全可行

- **Python 异常可以 100% 捕获**（通过 `sys.excepthook`）
- **原生崩溃无法在 Python 层捕获**（但这是 macOS 层面的限制，非代码问题）
- **工作量很小**：约 160 行代码，1-2 小时可完成
- **几乎零性能开销**：仅异常时才写入文件
- **Redis 消耗无影响**：纯本地文件存储，不走 Redis

### 推荐实施顺序

1. 先加全局 `sys.excepthook` + `record_error()` 函数（核心采集层，10 分钟）
2. 改造关键的 `except: pass` 为 `record_error()`（逐步替换，20 分钟）
3. 新增 Dashboard "日志" 页面（UI 展示层，30 分钟）
4. 可选：WebView JS 错误捕获（附加能力，10 分钟）
5. 可选：进程崩溃外部检测脚本（launchd 心跳检测，30 分钟）

### 不推荐的做法

- ❌ 把错误上报到远程服务器（增加网络依赖和隐私风险）
- ❌ 用 Redis 存错误（消耗 Redis 配额且增加故障点）
- ❌ 用第三方错误监控 SDK（Sentry 等，太重）
- ❌ 在错误风暴时不限流（可能导致磁盘写满）
