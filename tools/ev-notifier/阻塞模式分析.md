# Ev Notifier 阻塞模式分析

> 分析时间：2026-09-17 | 目标文件：ev_notifier.py | 版本：v2.2.12

---

## 一、什么是阻塞模式

Ev Notifier 的核心消息接收采用了 **Redis PUB/SUB 的阻塞监听模式**。

核心代码路径：

```
pubsub = r.pubsub()
pubsub.subscribe("auth:push_channel")
for message in pubsub.listen():    # ← 此处阻塞，等待消息到达
    # 处理消息
```

`pubsub.listen()` 是一个阻塞生成器，当没有消息到达时，**线程会挂起在 recv() 系统调用上**，不消耗 CPU，直到内核通知有数据可读。

这是一个典型的 **事件驱动（Event-Driven）模式**，与传统的"定时轮询"（polling）模式形成对比。

---

## 二、两种模式对比

### 2.1 轮询模式（Polling）

```
while True:
    messages = check_redis()    # 例如 XREAD COUNT 10
    for msg in messages:
        handle(msg)
    time.sleep(1)               # 固定间隔轮询
```

| 特性 | 说明 |
|------|------|
| 延迟 | 取决于轮询间隔，平均延迟 = 间隔/2 |
| CPU 消耗 | 即使无消息也定期唤醒，有固定开销 |
| 网络开销 | 每次轮询产生一次 HTTP/TCP 往返 |
| 实现复杂度 | 简单直观 |
| 消息积压 | 不会积压（每次拉取当前所有） |

### 2.2 阻塞模式（Blocking — Ev Notifier 采用）

```
pubsub.listen()  # 线程阻塞在 recv()，等待内核唤醒
```

| 特性 | 说明 |
|------|------|
| 延迟 | 毫秒级实时推送，零等待 |
| CPU 消耗 | 空闲时几乎为零（线程挂起） |
| 网络开销 | 仅一条长连接，无重复往返 |
| 实现复杂度 | 需要处理重连、心跳、线程管理 |
| 消息积压 | 若接收端处理慢，消息在 Redis 端积压 |

### 2.3 综合对比

| 维度 | 轮询模式 | 阻塞模式（PUB/SUB） |
|------|:--------:|:-------------------:|
| 实时性 | ❌ 中等（秒级） | ✅ 毫秒级 |
| CPU 空闲开销 | ❌ 固定消耗 | ✅ 接近零 |
| 网络开销 | ❌ 频繁请求 | ✅ 单连接复用 |
| 断线恢复 | ✅ 自动（下次轮询） | ❌ 需要额外机制 |
| 实现复杂度 | ✅ 简单 | ❌ 较复杂 |
| Serverless 友好度 | ✅ 天然适配 | ❌ 需要长连接 proxy |
| 连接数 | ❌ 无状态 | ⚠️ 每个客户端一条长连接 |

## 三、Ev Notifier 的阻塞详细路径

```
main()
  └── EvNotifier.__init__()
        ├── threading.Thread(target=_run_event_loop, daemon=True).start()
        │     └── redis_loop()
        │           ├── r.pubsub().subscribe("auth:push_channel")
        │           └── for message in pubsub.listen():  ← 线程挂起等待
        │                 ├── handle_message(msg)         # macOS 通知
        │                 └── record_message(...)          # 记录统计
        │
        ├── rumps.App.__init__()          # 菜单栏初始化
        └── app.run()
              └── NSApplication.runEventLoop()  ← 主线程挂起在 Cocoa 事件循环
```

### 3.1 主线程

调用 `app.run()` → `NSApplication.runEventLoop()`，这是 macOS Cocoa 的 GUI 事件循环。它负责：
- 菜单栏交互（点击事件）
- `@rumps.timer(2)` 定时器回调（每 2 秒更新标题）
- 面板窗口创建和交互

**特点**：主线程永远阻塞在这里，不会退出。

### 3.2 工作线程

`threading.Thread(target=redis_loop, daemon=True)` 启动的守护线程负责：
- Redis PUB/SUB 连接维护
- 消息接收、处理和存储
- 断线重连（指数退避）

**特点**：`pubsub.listen()` 调用内核级的 recv() 阻塞等待消息，不消耗 CPU。

## 四、阻塞模式是好的模式吗？

### 4.1 结论：在该场景下是合适的选择

阻塞模式非常适合 Ev Notifier 的场景，原因如下：

#### ✅ 适合长连接 + 高实时性需求
桌面应用常驻后台，保持一条长连接是最经济的方式。PUB/SUB 阻塞模式比轮询节省大量网络和 CPU 开销。

#### ✅ 适合双向事件的本地 GUI 应用
GUI 框架（rumps、Cocoa）本身也是事件驱动的主循环，阻塞消费线程与 GUI 主线程的架构非常匹配。

#### ✅ 消息量适中，无需复杂的消费者组
每天几十到几百条消息，单消费者足够。不需要 Redis Stream 的消费者组、ACK 确认等机制。

### 4.2 但需要注意以下问题

#### ⚠️ 问题 1：线程阻塞意味着无法优雅退出
守护线程 + 阻塞 socket 意味着：
```python
# 如果非 daemon 线程，程序永远退不出
# 如果 daemon 线程，程序退出时线程被强制终止，可能丢失数据
```
Ev Notifier 使用 `daemon=True`，进程退出时线程被强制杀掉。这对于纯消费场景可以接受（TCP 连接由内核关闭，消息不会丢）。

#### ⚠️ 问题 2：PUB/SUB 无消息持久化
Redis PUB/SUB 是"即发即忘"模式：
- 如果客户端断开连接，期间的推送全部丢失
- 需要用额外的恢复机制来弥补

Ev Notifier 的解决方案：
- 服务端同时将消息写入 Redis Stream
- 客户端通过 `XRANGE` 命令做补偿恢复（`do_recovery_poll()`）
- 维护 `last_id` 记录消费位置
- 周期性完整性检查（`@rumps.timer(2)` 仅是界面更新，非检查逻辑）

#### ⚠️ 问题 3：subprocess.run() 阻塞同一线程
在消息处理路径中（`handle_message->store_message/notify_macos`），使用了多个 `subprocess.run()` 阻塞调用：
```python
subprocess.run(["osascript", "-e", script], timeout=3)  # 通知
```
这些调用会阻塞消息消费线程。如果系统压力大，可能导致消息处理延迟。

#### ⚠️ 问题 4：无应用层心跳
Redis PUB/SUB 连接没有应用层心跳包（ping/pong）。虽然 `redis.Redis` 配置了 `socket_keepalive=True` 和 `health_check_interval=30`，但：
- `health_check_interval` 需要执行 Redis 命令时才会触发
- 阻塞在 `pubsub.listen()` 时，health check 不会介入
- TCP keepalive 依赖操作系统配置（默认 2 小时）

## 五、让阻塞模式工作良好的配合机制

要让阻塞模式稳定可靠，Ev Notifier 做了以下正确的配合：

### 5.1 守护线程 + Cocoa RunLoop（✅ 已实现）

```
          主线程                   工作线程
    ┌──────────────┐       ┌──────────────┐
    │ Cocoa Event  │       │ pubsub.listen│
    │ Loop         │       │ (blocking)   │
    │              │       │              │
    │ 菜单交互     │       │ 消息处理     │
    │ 定时器回调   │       │ 重连逻辑     │
    │ 面板渲染     │       │ 错误恢复     │
    └──────────────┘       └──────────────┘
         │                       │
         └─────── 共享状态（全局变量）───┘
               _new_msg_count, _status 等
```

**原则**：阻塞 I/O 必须放在独立线程，不能阻塞 GUI 线程。

### 5.2 指数退避重连（✅ 已实现）

```python
reconnect_delay = 1
while True:
    try:
        # ... 连接和监听
        reconnect_delay = 1  # 成功后重置
    except Exception:
        time.sleep(reconnect_delay)
        reconnect_delay = min(reconnect_delay * 2, 30)  # 1→2→4→8→16→30
```

### 5.3 消息补偿恢复机制（✅ 已实现）

由于 PUB/SUB 的"即发即忘"特性，需要独立补偿通道：

```
┌────────────┐          ┌────────────┐          ┌────────────┐
│  Vercel    │──PUBLISH─▶│  Upstash   │──SUBSCRIBE▶│  Ev        │
│  Server    │           │  Redis     │            │  Notifier  │
│            │──XADD────▶│  Stream    │──XRANGE───▶│  (恢复)    │
└────────────┘           └────────────┘           └────────────┘
    推送路径：PUB/SUB（实时）
    恢复路径：Stream XRANGE（补偿）
```

服务端同时做两个操作：
1. `PUBLISH auth:push_channel <json>` — 实时推送
2. `XADD auth:notifications:stream * <field> <value>` — 持久化

客户端：
1. 正常时：`SUBSCRIBE` 接收实时消息
2. 断开后：`XRANGE` 扫描丢失的消息

### 5.4 自动重启机制（✅ 已实现）

通过 macOS LaunchAgent 实现：

```xml
<!-- ~/Library/LaunchAgents/com.evnotifier.agent.plist -->
<key>KeepAlive</key>
<true/>
<key>RunAtLoad</key>
<true/>
```

- 如果进程崩溃，`launchd` 自动拉起重启
- 登录时自动启动
- 重启时重新建立 Redis 连接

### 5.5 PID 文件防多开（✅ 已实现）

```python
def _acquire_pid_lock():
    # 检查 PID 文件，防止多个实例
```

### 5.6 连接健康检查（⚠️ 部分实现）

当前配置了 `socket_keepalive=True, health_check_interval=30`。但在阻塞 `pubsub.listen()` 时，health check 不会执行。

**建议改进**：
1. 使用非阻塞的 `get_message(timeout=30)` 替代 `listen()`
2. 或使用 `pubsub.subscribe()` + `pubsub.get_message(timeout=30)` 轮询模式
3. 这样可以在等待消息的同时，定期检查连接健康状态

## 六、可能的优化方向

### 6.1 非阻塞监听（推荐）

将 `pubsub.listen()` 替换为带超时的轮询检查：

```python
# 当前：完全阻塞
for message in pubsub.listen():
    handle(message)

# 优化：带超时的非阻塞轮询
while True:
    message = pubsub.get_message(timeout=30)
    if message:
        handle(message)
    else:
        # 超时，检查连接健康
        try:
            r.ping()
        except Exception:
            # 连接断开，触发重连
            break
```

**优点**：可以在等待消息的同时定期检查连接健康、执行维护任务。

### 6.2 异步支持

使用 `asyncio` + `redis.asyncio` 可以单线程处理多个并发任务：

```python
async def main():
    pubsub = await r.pubsub()
    await pubsub.subscribe("auth:push_channel")
    async for message in pubsub.listen():
        await handle_async(message)
```

但对于 rumps（Cocoa GUI），异步与 Cocoa RunLoop 的配合比较复杂，目前的线程模型反而是更务实的选择。

### 6.3 subprocess.run() 改为非阻塞调用

在消息处理路径中，用 `subprocess.Popen` 替代 `subprocess.run`：

```python
# 当前：阻塞 3 秒
subprocess.run(["osascript", "-e", script], timeout=3)

# 优化：不阻塞消费者线程
subprocess.Popen(["osascript", "-e", script],
                 stdout=subprocess.DEVNULL,
                 stderr=subprocess.DEVNULL)
```

### 6.4 增加 Stream 消费者组

如果未来消息量变大（每日数千条），可以考虑：
- Redis Stream + `XREADGROUP` 消费者组
- 自动 ACK 机制
- 消息重试/死信队列

但目前的消息量级，PUB/SUB + XRANGE 补偿已经足够。

## 七、总结

| 维度 | 评价 |
|------|------|
| 模式选择 | ✅ **合适** — 桌面长连接场景，PUB/SUB 阻塞监听是最优解 |
| 架构设计 | ✅ **清晰** — 主线程 GUI + 工作线程 I/O，职责分离 |
| 容错机制 | ✅ **完善** — 指数退避重连 + 自动重启 + PID 防多开 |
| 补偿恢复 | ✅ **到位** — PUB/SUB + Stream 双通道，丢失可恢复 |
| 健康检查 | ⚠️ **可改进** — 阻塞 listen() 无法执行 health check |
| 通知延迟 | ⚠️ **可优化** — subprocess.run() 阻塞消费者线程 |

### 核心结论

**阻塞模式本身没有好坏，关键看配合机制是否到位。** Ev Notifier 为阻塞模式配备了完整的保障体系：

1. ✅ 独立线程隔离阻塞 I/O
2. ✅ 指数退避重连
3. ✅ 补偿恢复（PUB/SUB + Stream 双通道）
4. ✅ 自动重启（LaunchAgent）
5. ✅ 消息去重和完整性校验
6. ✅ 错误日志记录

当前架构对于"桌面常驻 + 实时推送"的场景是正确且成熟的选择。如果希望进一步优化，可以从 **非阻塞监听** 和 **异步通知** 两个方向入手。
