## 一、结论速览

| 问题 | 结论 | 证据强度 |
|---|---|---|
| 打开面板会不会崩？ | **会**。5 天日志窗口内确证崩溃 **5 次**，全部发生在**面板正在加载**的那一刻 | 确证（崩溃报告 + 日志对时） |
| 崩溃能复现吗？ | **能，且规律稳定**：这 5 次**都是同一个进程内第 2 次打开面板时崩**（5/5 = 100%） | 确证 |
| 崩了会自动重启吗？ | **会**。LaunchAgent `KeepAlive=true`，进程秒级被拉起 | 确证 |
| 崩溃→恢复多久？ | **面板重新可用约 0.8 ~ 2.1 秒**（launchd 拉起延迟实测 **30 ~ 900 ms**） | 确证 |
| 崩溃原因（**已确证**） | **面板被关掉后，`NSWindow` 因默认 `releasedWhenClosed=True` 被释放，pyobjc 包装器变成悬垂指针；下一次「打开面板」再碰它（`isVisible()` / `center()` / `makeKeyAndOrderFront_()`）→ pyobjc 对象类型校验失败 → `__builtin_trap()` → SIGTRAP**。不是 Python 异常（try/except 抓不到），崩溃在主线程 | 确证（最小用例 A/B 复现 + 修复验证） |
| 修复状态 | **已修复并上线**（v2.3.10，2026-09-23，进程 PID 37253）：① `setReleasedWhenClosed_(False)`（关键）② 关闭后不复用 WebView，每次打开重建 ③ 菜单回调移出菜单事件循环 ④ 加崩溃计数/带日期日志。A/B 用例：**改前必崩、改后全过** | 确证（见 §4.4） |
| 崩溃率 | 日志窗口内打开面板 **62 次**，确证崩溃 5 次 ≈ **8%**；若把「面板加载中日志戛然而止」的进程也算上，**16/29 个进程生命周期（55%）终止于面板加载瞬间** | 中（后者只是强相关，非铁证） |
| 崩溃有日志吗？ | **没有**。程序没有任何崩溃捕获（无 atexit 标记、无 crash 计数），`_debug_log` 也不写日期 → 只能靠系统 `.ips` 事后对账 | 确证 |

一句话：**「打开面板」是这个插件目前唯一的稳定崩溃触发器；崩在 pyobjc 类型校验 trap 上，宿主 launchd 1 秒内把它拉回来，所以用户只感知到「面板闪一下就没了 / 要再点一次」；因为插件自己不记崩溃，这件事此前一直是隐形的。**

## 二、现象还原（最小可复现片段）

日志原文（09-19 16:46，一次典型崩溃 + 重启 + 再打开成功）：

```
[16:46:17.104498] open_dashboard clicked                      ← 第 2 次点「打开面板」
[16:46:17.105799] show() called, _HAS_WEBKIT=True, _HAS_WEBVIEW=True
[16:46:17.108633] navAction url=data:text/html;base64,...     ← loading 页策略回调（最后一条日志）
[16:46:18.010959] DashboardWindow.__init__                    ← 0.90s 后【新进程】已经起来
[16:46:20.877302] Startup recovery: checking for missed messages...
[16:46:22.473891] open_dashboard clicked                      ← 用户再点一次（新进程，第 1 次打开）
[16:46:22.668846] navAction url=data:text/html;base64,...
[16:46:22.911471] navAction url=ev://refresh                  ← 正常路径才会出现的 JS 跳转
[16:46:22.911866] _refresh_content: page=messages ...          ← 面板正常显示
```

**关键差别**：正常打开时，loading 页的 JS 会在约 0.2s 后跳 `ev://refresh` → 后面跟着一串 `_refresh_content / HTML built / setMainFrameURL`；而崩溃时，日志**永远停在第一条 `navAction url=data:text/html;base64,...`** 上，再没有任何后续。

**真正的复现步骤（2026-09-23 用最小用例确证）**：

```
打开面板（第一次，正常显示）
  → 关掉面板窗口（点红叉 / ⌘W）
  → 再点「打开面板」          ← 💥 SIGTRAP，进程秒崩
```

之所以日志里"看起来像第二次打开就崩"，是因为中间那次关窗**不留任何日志**（`windowWillClose_` 实测在应用里根本没被调用）。所以准确说法是：**只要面板被关过，下一次打开必崩**。

5 次确证崩溃，**末条日志全部是这一行**（5/5）：

```
崩溃时刻            末条日志（最后动作）
09-21 10:41:28.992  navAction url=data:text/html;base64,...
09-22 07:31:57.661  navAction url=data:text/html;base64,...
09-22 23:01:58.958  navAction url=data:text/html;base64,...
09-23 00:28:03.273  navAction url=data:text/html;base64,...
09-23 00:34:39.650  navAction url=data:text/html;base64,...
```

即崩溃窗口 = **`show()` → `_show_loading()` 把 loading 页塞进 WebView 之后，到 loading 页 JS 跳转 `ev://refresh` 之前**（约 0.1 ~ 0.9s 的窗口）。

## 四、崩溃原因分析

### 4.1 A 类（确证 5 + 疑似 2）：pyobjc 类型校验 trap

`Python-2026-09-23-003442.ips`（09-23 00:34 那次）崩溃线程 = `com.apple.main-thread`，完整栈自顶向下：

```
libobjc.A.dylib              object_getClass
_objc.cpython-314-darwin.so  object_verify_type        ← ★ 就是这里 trap
_objc.cpython-314-darwin.so  object_getattro           ← Python 侧「取属性/取方法」
Python                       _PyObject_GetMethodStackRef
Python                       _PyEval_EvalFrameDefault  ← 正在执行的 Python 代码
Python                       _PyEval_Vector / PyObject_Vectorcall
_objc.cpython-314-darwin.so  method_stub
libffi.dylib                 ffi_closure_SYSV_inner / ffi_closure_SYSV
AppKit                       -[NSApplication(NSResponder) sendAction:to:from:]
AppKit                       -[NSMenuItem _corePerformAction:]
AppKit                       -[NSMenu performActionForItemAtIndex:]
AppKit                       -[NSMenuTrackingSession startRunningMenuEventLoop:]
AppKit                       +[NSContextMenuImpl presentPopup:...]
AppKit                       +[NSStatusBarButtonCell popUpStatusBarMenu:...]
AppKit                       -[NSStatusItem popUpStatusItemMenu:]
```

读法：

1. 用户点的是**状态栏菜单项**（`NSStatusItem → NSMenu → NSMenuItem → sendAction`），对应 `@rumps.clicked("打开面板")` → `open_dashboard()` → `self._dash.show()`。**整个 show() 都还在菜单的事件跟踪循环里同步执行**（栈底 `NSMenuTrackingSession`）。
2. `method_stub` 说明这次调用是「Python 调用 ObjC 方法」；`object_getattro` + `object_verify_type` 说明 pyobjc 在**对一个 ObjC 对象做属性/方法解析时校验该对象的类型**，校验失败 → pyobjc 用 `__builtin_trap()` 结束进程 → **SIGTRAP / EXC_BREAKPOINT**。
3. 这是 **pyobjc 的「对象类型校验失败」硬崩**，典型成因是拿到一个**已失效/已释放/非预期的 ObjC 对象**（use-after-free、悬垂指针、错误类型包装）。它**不是 Python 层异常，`try/except` 抓不到**，这解释了为什么 `open_dashboard` 外面那层 `try/except Exception` 完全没起作用（日志里 `open_dashboard ERROR` 出现 0 次）。
4. 结合 3.2/3.4 的时序，崩溃位置收敛到 `show()` 内、`_show_loading()` 之后紧接着的那批 AppKit 调用（`self._window.center()` / `makeKeyAndOrderFront_()` / `orderFrontRegardless()` / `NSApplication.sharedApplication().setActivationPolicy_()`），且**只在复用已存在窗口（`self._window is not None`）时触发**。

**→ 已确证的那个"失效对象"就是 `self._window` 本身**（下面用最小用例证明了，不是猜测）。

### 4.1-bis 确证根因（2026-09-23 用最小用例复现 + 修复验证）

链条只有三步：

1. `_create_window()` 用 `NSWindow.alloc().initWithContentRect_...` 建窗，**没有关掉 `releasedWhenClosed`**，而 macOS 上它的默认值是 **`True`**（实测 `NSWindow.isReleasedWhenClosed() == True`）。
2. 用户关掉面板窗口 → 窗口对象被 **release/dealloc**，但 Python 侧的 `self._window` 仍指向那个已被释放的 pyobjc 包装器。
   （原代码指望 `windowWillClose_` 通知回调把引用清掉，但**实测该回调在应用里从未被调用**——`_retired` 计数恒为 0，所以引用一直留着。）
3. 下一次 `show()` → `if self._window is not None: ... self._show_loading()` / `self._window.center()` 触碰这个悬垂对象 → pyobjc `object_verify_type` 校验失败 → **SIGTRAP**（实测有时表现为 trap，有时直接卡死——同一类未定义行为）。

最小用例（不放 loading 页、不复用 WebView，只做"开窗 → 关窗 → 再 show()"）：

```
A) 改前： 1) show() 存活 → 2) close() → 3) 再次 show()  →  exit=133 (SIGTRAP) 💥
B) 改后： 1) show() 存活 → 2) close() → 3) 再次 show()  →  存活 ✓ → 4) 再 show() ✓ → 5) 页内刷新 ✓ → exit=0 ✅
```

A 侧同时留下了崩溃报告 `Python-2026-09-23-074719.ips`（栈与线上 5 次崩溃完全一致，栈顶 `object_verify_type` ← `object_getattro`，栈底 `__NSFireDelayedPerform → CFRunLoopDoTimer`），**证明这就是线上那个崩溃，不是另一个 bug**。

所以「为什么总是第 2 次打开才崩」有了准确答案：**不是"第 2 次"本身有问题，而是"上一次打开之后用户把面板关掉了"**。第一次打开时窗口是新的、有效对象，所以永远正常。

### 4.2 触发条件小结

| 条件 | 是否必需 | 依据 |
|---|---|---|
| 面板窗口被关过（红叉 / ⌘W） | **必需** | A/B 用例：不关窗则怎么点都不崩；关过窗下一次打开必崩 |
| 走 `_HAS_WEBKIT` 的 `show()` 路径 | 必需 | 崩溃前必打 `show() called, _HAS_WEBKIT=True` |
| 复用 `self._window`（`is not None`） | 必需 | 崩溃点在 `isVisible()`/`center()` 这几个触碰旧窗口的调用上 |
| 状态栏菜单回调同步执行 | 相关（加剧） | 线上 5 次栈底都是 `NSMenuTrackingSession → sendAction`；已一并改为延后执行 |
| loading 页 / WebView 复用 | 无关 | 最小用例已把它们全部去掉，改前照样崩 |
| 具体页面（messages/orders/trend…） | 无关 | 崩溃时页面还没渲染 |

### 4.3 B 类（4 份）：不是这个插件

4 份 SIGABRT 全在 **09-16 12:57~13:02**、**父进程是 zsh**（终端手动起）、解释器是 **Python 3.13.3**（本插件 LaunchAgent 用的是 3.14.6），栈是：

```
_tkinter.cpython-313-darwin.so  PythonCmd
libtcl9.0.dylib                 NotifierThreadProc / TclNRRunCallbacks
libtcl9tk9.0.dylib              TkWmProtocolEventProc → -[TKApplication windowShouldClose:]
Python                          PyEval_RestoreThread → _Py_FatalErrorFunc → fatal_error → abort()
```

= **Tk 程序在关闭窗口时，Tcl 回调线程拿不到 GIL，触发 Python 致命错误 `abort()`**（经典的 tkinter 多线程坑）。
当前 `ev_notifier.py` 里**没有任何 tkinter 依赖**（全仓库只有 `auto_clicker_*.py` 用 tkinter），所以这 4 份**与「打开面板崩溃」无关**，不计入本插件统计（连续 4 次、每次启动后 6~7 秒即崩，是一次手动调试期的崩溃循环）。

## 五、自动重启机制与恢复代价

**机制（实测 plist）** `~/Library/LaunchAgents/com.evnotifier.agent.plist`：

```xml
<key>KeepAlive</key><true/>      ← 进程一死就拉起（这就是「自动重启」）
<key>RunAtLoad</key><true/>      ← 登录/加载即启动
<key>ProgramArguments</key><array>
  <string>/opt/homebrew/opt/python@3.14/bin/python3.14</string>
  <string>/Users/Banner/Documents/guomengtao/app-auth/tools/ev-notifier/ev_notifier.py</string>
</array>
```

由 `ev_notifier.py` 的 `ensure_auto_start()`（每次启动都重写 plist + `launchctl bootstrap`）自动维护。
⚠️ 另外插件菜单里的「重启 Ev Notifier」走的是 `restart_self()` → **`os.execv`（同 PID 原地换代）**，与 launchd 拉起是**两套重启路径**，在日志里表现几乎一样（都无正常退出痕迹）——统计时必须区分。

**恢复时间（实测）**

| 环节 | 耗时 | 证据 |
|---|---|---|
| 崩溃 → launchd 拉起新进程 | **30 ~ 900 ms** | 末条日志 vs 后继进程 `procLaunch`（如 09-23 00:28:03.273 → 00:28:03.3032，**30ms**） |
| 新进程 → `DashboardWindow.__init__` 就绪 | 0.7 ~ 2.1 s | `procLaunch` vs `__init__` 日志（Δ 0.74~2.07s） |
| **面板重新可用（合计）** | **约 0.8 ~ 2.1 s** | 上两者相加 |

**恢复的副作用（比崩溃本身更值得管）**：每次重启都会跑 `_startup_recovery()`，把最近 168 小时未投递的消息**重新处理并再次触发投递回调**。日志实证（09-22 07:32 那次重启）：

```
Startup recovery: found 18 missed messages
Startup recovery: skipped 12 already-stored messages
Startup recovery: re-processed purchase_click (7f0a2bd6-...)     ← 重放
Startup recovery: re-processed new_order      (4a1281cc-...)
Delivery callback OK: 7f0a2bd6-... event=delivered               ← 又上报一次 delivered
```

→ **每次崩溃重启都会重放 6~9 条历史消息并二次上报**，存在重复通知/统计失真的风险（单条是否真会二次弹窗未在本次排查中确认，标为待验证）。

## 六、顺带发现的其他问题（与崩溃无关，但会影响统计与稳定性）

1. **外部在反复拉起导致「多开」刷屏**：`~/.ev_notifier_stdout.log` 305 行中 **305 行全是 `Another instance is already running (PID xxx). Exiting.`**（275 行指向 PID 36862），另有 1 行 `button returned:确定`。
   → 说明有循环/脚本在反复启同一个插件；这些都会让「重启次数」虚高，也不利于定位真崩溃。
2. **stdout 里 `started` 出现 0 次**：`main()` 里的 `print(f"Ev Notifier {VERSION} started: ...")` 从未落盘 → 因为进程要么被 SIGTRAP 杀掉、要么被 `os.execv` 顶掉，**stdout 缓冲区从未 flush**。反过来印证「几乎不以正常方式退出」。
3. **`notify_macos` 3 次超时**：`osascript display notification` 超时 5s（09-16 09:56 那 3 条激活/失败通知），与崩溃无关，但会让消费线程堵 5s。
4. **日志无法跨天/无轮转保护**（~~已修~~ 见 §7.1-8）：`_debug_log` 只写 `HH:MM:SS.ffffff`（**没有日期**），且超过 2000 行就裁到 1000 行 → 09-18 之前的记录已丢失（本次排查就是因此**无法核对 09-16 和 09-17 的两份崩溃报告**）。同一秒/跨天时间点无法区分，统计只能靠 `procLaunch` 反推。
5. **无崩溃可观测性**（~~已修~~ 见 §7.1-7）：没有 atexit 正常退出标记、没有崩溃计数器、没有版本号/pid 写进 debug 日志 → 崩溃完全隐形。

## 附录 B：A/B 最小复现用例（确证 + 回归用）

把下面脚本存成 `/tmp/ev_probe.py`，用插件同款解释器跑，参数指向插件的**目录副本**（不要指向线上目录，避免污染）：

```python
# 用法: /opt/homebrew/opt/python@3.14/bin/python3.14 /tmp/ev_probe.py <插件目录>
import sys, os
sys.path.insert(0, sys.argv[1])
import ev_notifier as ev
from AppKit import NSApplication
from PyObjCTools import AppHelper
NSApplication.sharedApplication()
def W(s): os.write(2, (s + "\n").encode())      # stderr 不缓冲，进程被 trap 也能看到进度
dash = ev.DashboardWindow(None)
def s1():
    W("1) 打开面板 (show)"); dash.show(); W("   存活"); AppHelper.callLater(1.5, s2)
def s2():
    W("2) 用户关掉面板 (close)"); dash._window.close(); AppHelper.callLater(1.0, s3)
def s3():
    W("3) 关窗后再次打开面板 (show) ← 原崩溃点"); dash.show(); W("   存活 ✓"); AppHelper.callLater(1.0, s4)
def s4():
    W("4) 第三次打开面板 (show)"); dash.show(); W("   存活 ✓"); AppHelper.callLater(0.6, s5)
def s5():
    W("5) 页内刷新 _refresh_content()"); dash._refresh_content(); W("   **ALL PASS**")
    AppHelper.stopEventLoop()
AppHelper.callLater(0.3, s1)
AppHelper.runEventLoop()
```

- 结果判读：`exit=133`（128+5）= SIGTRAP 崩溃；`exit=0` + `**ALL PASS**` = 通过。
- 2026-09-23 实测：`git show HEAD:` 取到的改前版本 → `exit=133`；改后版本 → `exit=0`。
