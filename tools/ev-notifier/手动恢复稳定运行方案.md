## 一、当前恢复机制总览

Ev Notifier 提供**三层消息保障**，确保不丢消息：

| 层 | 方式 | 触发条件 | 消耗 | 延迟 |
|----|------|----------|------|------|
| 第 1 层 | Redis PUB/SUB 实时推送 | 新消息到达 | 0 次额外命令 | 毫秒级 |
| 第 2 层 | 完整性自动检测 + XRANGE 补偿 | 收到消息后 `received_idx` 数量 < `total_server` | 1 次 XRANGE | 5 秒内 |
| 第 3 层 | **手动恢复**（用户触发） | 菜单栏点击"手动恢复" | 1 次 XRANGE | 秒级 |

## 二、手动恢复核心流程

```
用户点击"手动恢复"
        │
        ▼
_recalc_missing()  ← 实时计算丢失数（不走缓存，避免过期数据）
        │
        ├── ≤0 条 → 弹窗"无丢失消息"，结束
        │
        ▼
load_last_id()  ← 读取上次消费到的 stream ID
        │
        ├── None → 弹窗"无法获取 last_id"，结束
        │
        ▼
do_recovery_poll(last_id)
        │
        ├── XRANGE auth:notifications:stream <last_id> +  ← 从断点拉取
        │       │
        │       ├── 逐条 record_message() 写入本地
        │       ├── 逐条 handle_message() 弹出通知
        │       └── 更新 last_id
        │
        ├── save_last_id(new_last_id)  ← 持久化进度
        │
        └── record_poll("manual", recovered)  ← 记录操作日志
                │
                ▼
        弹窗通知恢复结果：已恢复 X 条 / 剩余 Y 条
```

**核心保障点**：
- `_recalc_missing()` 每次实时计算，不依赖缓存的 `_missing_count`（之前 bug 就是缓存过期导致无效）
- `do_recovery_poll()` 从断点 `last_id` 开始拉取，不怕重复
- `record_message()` 通过 `_seen_ids` 内存集合去重，已收到的不会重复计入

## 三、保底机制：强制全量重新扫描

当用户恢复后仍看到 ⚠ 叹号，说明存在**比 last_id 更早的旧消息**未被消费。

此场景已通过以下机制隔离：

```
Redis Stream 消息时间线示例：

   msg_001  msg_002  msg_003  ...  msg_099  msg_100
   ←── 早期未消费 ──→│←── PUB/SUB 正常收到 ──→
                     │
                    last_id（但前面有旧消息）
```

**解决方案：`_recalc_missing()`**

不再依赖 `last_id` 判断丢失，而是：
```
total_server（服务端当天总数）- len(received_idx)（本地收到数）= 丢失数
```

这保证即使 last_id 跳位，丢失数始终准确。

## 四、稳定运行已有的保障措施

### 4.1 进程级保障

| 措施 | 实现位置 | 说明 |
|------|----------|------|
| 未捕获异常 hook | `_install_error_hook()` | 全局捕获，写入 stderr |
| launchd KeepAlive | plist 配置 | 进程崩溃自动重启 |
| 指数退避重连 | `redis_loop()` | PUB/SUB 断线 1s→2s→4s→...→30s 重试 |
| 多 env 文件 fallback | `DOTENV` 列表 | 3 个 `.env` 路径依次尝试 |

### 4.2 数据持久化保障

| 文件 | 路径 | 内容 |
|------|------|------|
| `~/.ev_last_id_v1.5.0` | last_id | 消费进度 |
| `~/.ev_received.json` | received_idx + total_server | 完整性校验基准 |
| `~/.ev_poll_log.json` | poll 操作日志 | 审计恢复历史 |
| `~/.ev_debug.log` | debug 日志 | 错误排查 |

### 4.3 消费限制保障

| 限制项 | 值 | 说明 |
|--------|-----|------|
| 自动恢复频率 | 每小时最多 1 次 | `_last_poll_hour` 防抖 |
| 手动恢复频率 | 无限制 | 用户自己控制 |
| Redis 命令消耗 | 每次 1 条 XRANGE | 极度节省额度 |
| 本地消息上限 | 500 条 | `MESSAGES_FILE` 滚动 |

## 五、是否需要加面板独立页面详细展示过程？

### 5.1 当前已有的展示渠道

| 渠道 | 可见信息 | 形式 |
|------|----------|------|
| 菜单栏标题 | `⚠数字` 丢失条数 | 实时刷新 |
| 手动恢复按钮 | 点击后弹窗通知 | 操作结果 |
| 拉取日志 | 最近 7 天恢复记录 | rumps.alert |
| 调试日志 | 30 条最近 debug 记录 | rumps.alert |
| 状态按钮 | 连接状态/消息数/恢复次数 | rumps.alert |

### 5.2 推荐方案：**不需要独立页面**

理由：

| 维度 | 分析 |
|------|------|
| **用户场景** | 手动恢复是"问题发生时"才用的应急操作，使用频率极低（数天一次） |
| **信息量** | 恢复过程仅涉及 XRANGE 拉取、综合并、通知，没有复杂步骤需要展示 |
| **现有覆盖** | 菜单栏 ⚠ 数字 + 弹窗通知已完整覆盖"发现丢失 → 点击恢复 → 查看结果"闭环 |
| **面板复杂度** | 当前 8 个页面已很丰富，加一个低频页面增加维护成本 |
| **对比轮询统计页** | 轮询统计页已经展示了恢复历史，不需要再建一个相近页面 |

### 5.3 替代方案：增强菜单栏体验

如果觉得恢复过程不够透明，建议以下小改进（成本低、收益高）：

| 改进项 | 实现方式 | 工作量 |
|--------|----------|--------|
| 恢复按钮显示进度 | 点击后按钮短暂显示"恢复中…"，完成后变回 | ~10 行 |
| 恢复结果含明细 | 弹窗从"已恢复 3 条"改为"已恢复 3 条，剩余 0 条" | 已实现 |
| 恢复失败重试提示 | XRANGE 失败时弹窗告知"连接失败，请检查网络" | ~5 行 |
| 一键深度恢复 | 加一个隐藏菜单"全量扫描"，从 `-` 开始 XRANGE 扫所有未消费消息 | ~20 行 |
