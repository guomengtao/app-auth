## 1. 问题一：睡眠唤醒后消息永久丢失

### 1.1 真实证据链（本次实测，非推测）

**服务端侧：消息还在**（只读查询 `delivery-sync&after=330`，保留期 336h 未过期）：

```
success=True  next_cursor=350  has_more=False   → 返回 20 条
seq=331 purchase_click   2026-09-25T17:30:20Z   (= 北京 09-26 01:30)
seq=332 new_order        2026-09-25T17:30:44Z   ← 真实丢单
seq=333..336 page_visit
seq=337 new_activation   2026-09-25T17:36:05Z   ← 真实丢激活
seq=338..348 purchase_click / page_visit / new_order(341) / new_activation(344)
seq=349 page_visit       2026-09-26T01:15:47Z
seq=350 page_visit       2026-09-26T01:17:33Z
```

**客户端侧：游标直接跳过了空洞**（`~/.ev_debug.log` 原文，剪掉无关行）：

```
[2026-09-26 01:21:52.831][pid 34251] sync[periodic]: up to date last_seq=330
        ← 机器进入睡眠（息屏），进程被冻结 ~7h54m（01:21:52 → 09:15:52），期间日志完全空白
[2026-09-26 09:15:52.894][pid 34251] Delivery callback OK: d94bbc23-... event=delivered
        ← 唤醒后收到第一条实时消息（seq=349，由下面 09:16:14 的 last_seq=349 反推）：
          socket 没断，pubsub 直接继续给数据
[2026-09-26 09:16:14.880][pid 34251] sync[periodic]: up to date last_seq=349
        ← 22 秒后的定时补拉：游标已经是 349，after=349 → 331..348 永远不会再被请求
[2026-09-26 09:21:14.032][pid 34251] sync[periodic]: up to date last_seq=350
[2026-09-26 09:26:13.817][pid 34251] sync[periodic]: up to date last_seq=350   ← 之后一直「up to date」
```

**关键推理**：整夜日志里**没有任何** `sync[reconnect]`、`SUBSCRIBE error`、`watchdog: probe failed`。
→ 说明睡眠期间 pubsub 连接**从未断开**（Upstash + 内核都没发 RST/FIN），`listen()` 一直"活着"，
所以「重连 → 强制补拉」这条唯一的兜底路径**根本没被触发**，而游标被 349 这一条实时消息一步推过了 19 个 seq。

**损失清单（本次）**：`331..348` 共 **18 条**永久丢失，其中 **2 笔订单（332、341）+ 2 次激活（337、344）**；`349/350` 是唤醒后实时收到的，没丢。

### 1.2 根因分层（每层都有代码行号）

| 层 | 缺陷 | 位置 |
|---|---|---|
| L1 | **睡眠期间连接"假存活"**：`socket_timeout=60` 只在「读阻塞满 60s」时才抛错；机器睡眠时进程冻结、内核定时器不推进 → 唤醒后读操作既不报错也不返回数据（或先返回历史缓冲），拿不到 `ConnectionError` → **不重连** | `redis_loop()` `:1862`、`socket_timeout=SOCKET_TIMEOUT` `:1900`、`SOCKET_TIMEOUT=60` `:85` |
| L2 | **完全没有睡眠/唤醒钩子**：全文件 grep 无 `NSWorkspaceDidWakeNotification` / `WillSleepNotification`，唤醒后没有任何"强制重连 + 强制补拉"动作 | —（缺失即为根因） |
| L3 | **游标语义缺陷**：`handle_message()` 对**实时**消息调 `_advance_seq(seq)`（无 `force`），而 `_advance_seq` 的闸门只判「补拉中/补拉排队中」，不判「存在未补空洞」 → 一条 `seq=349` 就能把游标从 330 推到 349 | `handle_message()` `:1610`、`_advance_seq(seq)` `:1773`、`_advance_seq()` `:892`（闸门 `:905`） |
| L4 | **空洞不可逆**（两道门都封死）：「补拉只取 `after=last_seq`」→ 跳过去就取不回；「`_claim_message` 对 `seq <= last_seq` 直接判拒」→ 即便手工把数据拉回来也会被当重复丢弃 | `sync_since()` `:1031`（`after = last_seq` `:1035`）、`_claim_message()` `:914`（判拒 `:921-922`） |
| L5 | **兜底时序靠运气**：唯一兜底是 `sync[reconnect]`（依赖连接断）与 `sync[periodic]`（每 300s）。本例唤醒后定时补拉只比首条实时消息晚 **22 秒**，输了就永久丢 | `SYNC_PERIODIC_INTERVAL=300` `:89`、`_periodic_sync_loop()` `:1136` |

**一句话**：整套"不丢消息"的设计押在一个时序假设上 —— **"一次成功的补拉一定发生在第一条实时消息之前"**。睡眠唤醒恰好是打破它的最坏场景：凌晨积压了整夜的空洞，而唤醒那一刻的**第一条实时消息来得最快**（socket 是活的），补拉却要等重连或等 5 分钟定时器。

### 1.3 为什么现有防护没兜住

| 现有防护 | 为什么失效 |
|---|---|
| `socket_timeout=60`（P0-0） | 它防的是"**读**永久阻塞"（黑洞连接）。本例连接是"半活"：能收数据，所以既不超时也无需重连 —— **超时机制解决不了"游标跳洞"** |
| `_advance_seq` 的 `_sync_inflight/_sync_pending` 闸门 | 只覆盖"补拉正在进行"这个瞬间；空洞存在 ≠ 补拉在飞。首条实时消息到达时补拉**不在飞**，闸门形同虚设 |
| `sync[reconnect]` 强制补拉 | 依赖连接断开。睡眠唤醒**不必然断连** → 该路径未必触发（本次就没触发） |
| `sync[periodic]` 每 5 分钟 | 时间粒度太粗；本次 09:16:14 才跑，晚于 09:15:52 的首条消息 22 秒 |
| `_startup_recovery()` 旧式补拉 | 只在 `delivery-sync` 不可用时降级触发；且它按"7 天未投递"状态查，与游标无关，不解决已跳过的空洞 |
| `_claim_message` 的 `seq <= last_seq` 判拒 | 本意是防重复，实际把"事后修复"也堵死了 |

### 1.4 修复方案

#### P0-1（核心）实时消息**禁止跨空洞推进游标**

改 `_advance_seq` / `handle_message` 的协作语义：**游标只能连续推进**。

```python
def _advance_seq(seq, force=False):
    """推进水位线（只增不减）。

    ⚠️ 2026-09-26 修正（睡眠丢消息根因）：实时消息**不得跨过空洞**推进游标。
       旧行为：只要补拉不在飞，就直接 last_seq = seq —— 睡眠唤醒后第一条实时消息
       会把一整夜的空洞一次性跳过，且此后再也补不回来（补拉只按 after=last_seq 取数）。
       新行为：seq > last_seq + 1 时判为「有空洞」→ 游标**原地不动**，记录 gap 起点，
               并立刻强制补拉（补拉会从 last_seq+1 逐页补到实时位置）。
    """
    global _sync_dirty, _gap_start
    ...
    cur = int(_sync_state.get("last_seq") or 0)
    if not force and seq > cur + 1:
        # 空洞：不要跳，交给补拉
        _gap_start = cur + 1 if not _gap_start else _gap_start
        _debug_log(f"gap detected: last_seq={cur} live_seq={seq} gap_start={_gap_start} -> force sync")
        _request_sync("gap", force=True)
        return
    ...
```

- 实时消息**照常入库**（`store_message` 在 `_advance_seq` 之前，不受影响）。
- 空洞期间继续来的实时消息（350、351…）也不会推进游标（它们同样 `> cur+1`），
  补拉完成后由补拉路径 `_advance_seq(nxt, force=True)` 一次性推进到实时位置。
- 已在库的重复行由 `_claim_message` 的 `messageId` / `seq` 去重拦掉，不会重复入库。

#### P0-2 睡眠/唤醒钩子（把"随机时序"变成"确定性"）

用**已验证可行**的 `NSObject` 观察者机制（和刚落地的 `WindowDelegate` 同一套，`:3020`）：

```python
class SleepWakeObserver(NSObject):
    """NSWorkspace 睡眠/唤醒通知。⚠️ 必须是 NSObject 子类并强引用住，
    纯 Python 对象注册的 selector 在本项目里实测从不回调（见 关闭面板自动已读设计.md §3）。"""

    def init(self):
        return self

    def workspaceWillSleep_(self, note):
        # 睡前主动断开：唤醒后 listen() 必然报错 → 强制走「重连 + 强制补拉」
        _disconnect_pubsub("will-sleep")

    def workspaceDidWake_(self, note):
        _disconnect_pubsub("did-wake")          # 兜底：万一没断，这里再断一次
        _request_sync("wake", force=True)       # 不等实时消息，唤醒即补
```

注册（放在 `run()` 里、`NSApplication` 就绪之后）：

```python
nc = NSWorkspace.sharedWorkspace().notificationCenter()
self._sleep_obs = SleepWakeObserver.alloc().init()
nc.addObserver_selector_name_object_(self._sleep_obs, "workspaceWillSleep:",
                                     NSWorkspaceWillSleepNotification, None)
nc.addObserver_selector_name_object_(self._sleep_obs, "workspaceDidWake:",
                                     NSWorkspaceDidWakeNotification, None)
```

`_disconnect_pubsub()`：`_conn_ref["r"].connection_pool.disconnect()`（try/except 包裹）→
`listen()` 立即抛错 → `redis_loop` 走重连 → `_request_sync("reconnect", force=True)`。
**即使唤醒钩子失效，P0-1 也能独立止损**（两条修复互相独立，不构成单点）。

#### P0-3 放宽 `_claim_message` 对补拉来源的游标判拒

```python
def _claim_message(seq, mid, msg_id, source="live"):
    ...
    # 补拉来源不做「seq <= last_seq 判拒」：游标被跳过时，这道判拒会把本该修复的
    # 消息当重复丢弃（防重复别防到"防修复"）。去重仍然由 messageId / seq 已知集合保证。
    if source != "sync" and seq and seq <= int(_sync_state.get("last_seq") or 0):
        return False
```

#### P1-1 游标对账看门狗（可观测性 + 二次保险）

在 `_periodic_sync_loop` 里先做一次 `action=head` 对账，把「服务端 max_seq 与本地游标的差值」写日志/面板：

```python
mx = head.get("max_seq"); cur = last_seq
if mx - cur > GAP_WARN_THRESHOLD:      # 例如 > 20
    _debug_log(f"cursor lag: server={mx} local={cur} diff={mx-cur} -> force sync")
    _request_sync("lag", force=True)
```

好处：**不依赖实时消息**也能发现空洞（例如整夜无实时消息、或未来又出现游标 bug）。

#### P1-2 面板可见性

- 消息页状态行加「空洞」：`gap_start`、`server max_seq`、`本地 last_seq`、`最近一次补拉 recovered N`。
- 唤醒后若补回消息，沿用现有 `_notify_recovery_summary(added)`（`:1104`）弹一条「睡眠期间补回 18 条」。

#### P2 睡眠期间的预期管理

睡眠期间**不可能**收通知（进程冻结）。正确预期 = 「唤醒后 1~3 秒内一次性补回 + 一条汇总通知」。
补回数量与 `seq` 断点写进日志，便于事后核对。

## 2. 问题二：订单列表时间错乱 / 格式 / 排序

### 2.1 真实证据（本机 `~/.ev_messages.json`）

```
订单消息 89 条
time 年份异常(>2100) 56 条 —— 全部是 new_order
样例：'58647-12-15 08:50:41'  '58649-01-07 00:43:48'  '58686-10-01 16:49:18'
存储消息里带 ts 字段的条数：0
有 paid_at(毫秒) 的订单：9 条
存储顺序：前 3 条 = 烂年份的旧同步数据；末 3 条 = 时间正确的实时推送数据
        → 列表顺序：既非时间升序，也非时间降序
```

**可修复性已验证**：`time.mktime(解析出的年月日时分秒)` 能把烂时间原样反算回原始毫秒值：

```
'58647-12-15 08:50:41' → mktime = 1788583423841 → //1000 = 1788583423 → 北京时间 2026-09-05 12:43:43
（对照该单 out_trade_no = 202609050058 → 日期吻合；`calendar.timegm` 会因 5 位年份抛
  ValueError: year 58647 is out of range，**必须用 mktime，不能用 timegm/strptime**）
```

### 2.2 根因（6 条）

| # | 根因 | 位置 |
|---|---|---|
| R1 | **毫秒当秒**：`ts = int(order.get("created_at", 0))`，而 `created_at = Date.now()`（**毫秒**）→ `time.localtime(1.79e12)` → 年份 58647 | `_sync_orders()` `:5260`（`:5296`）、`lib/afdian-processor.js:149,194` |
| R2 | **`ts` 字段从不落盘**：`store_message` 只写 `time/type/payload/messageId/read[/seq]`，没有数值时间戳 → `_build_order_list` 里 `"ts": m.get("ts", 0)` **恒为 0**，无法按真实时间排序 | `store_message()` `:550`（`:554-561`）、`_build_order_list()` `:2054` |
| R3 | **列表按「存储顺序」返回**，不是时间序；而 `_sync_orders` 把历史订单**倒序追加到文件末尾** → 前后两段各自有序、整体乱序 | `_build_order_list()` `:2054`（`:2065-2097`） |
| R4 | **取到最老的 200 条**：`for o in orders[:200]` 在乱序列表上取前 200 → 新订单被切掉（订单量大时最新订单**根本看不见**） | `_html_orders()` `:3920`、切片 `:4096` |

> 建议：**列表主时间 = `paid_at`（真实支付时间，缺失时回退 `created_at` 处理时间）**，并在 UI 上标注。

#### S2 客户端：统一时间解析（新增工具函数）

```python
BJ_OFFSET = 8 * 3600

def _parse_ts_any(v):
    """秒 / 毫秒 / ISO 字符串 → 秒。越界（<2000 年 或 >2100 年）返回 0。"""
    try:
        if isinstance(v, (int, float)) or (isinstance(v, str) and v.strip().isdigit()):
            n = int(float(v))
            if n > 10 ** 11:      # 毫秒
                n //= 1000
            return n if 946684800 <= n <= 4102444800 else 0
        if isinstance(v, str) and v:
            return int(datetime.fromisoformat(v.replace("Z", "+00:00")).timestamp())
    except Exception:
        pass
    return 0

def _fmt_bj(ts, fmt="%Y-%m-%d %H:%M:%S"):
    """北京时间格式化：+8h 后读 UTC 分量（与 lib/rate-limit.js beijingDateKey() 同思路，
    与运行时时区无关）。"""
    try:
        return time.strftime(fmt, time.gmtime(int(ts) + BJ_OFFSET))
    except Exception:
        return ""

def _bj_today_str():
    return _fmt_bj(time.time(), "%Y-%m-%d")

def _bj_now_str(fmt="%Y-%m-%d %H:%M:%S"):
    return _fmt_bj(time.time(), fmt)
```

#### S6 一次性修复历史脏数据（幂等）

```python
def _repair_message_times():
    """修复「毫秒当秒」造成的烂时间（年份 > 2100）+ 补齐缺失的 ts 字段。

    ⚠️ 不能用 time.strptime / calendar.timegm：5 位年份会被拒（实测
       ValueError: year 58647 is out of range）。必须正则拆字段 + time.mktime
       （把烂时间原样反算回原始毫秒值）。
    """
    fixed = 0
    for m in load_messages():
        t = m.get("time", "") or ""
        mt = re.match(r"(\d{4,})-(\d{2})-(\d{2}) (\d{2}):(\d{2}):(\d{2})", t)
        if not mt:
            continue
        y, mo, d, hh, mi, ss = map(int, mt.groups())
        if y > 2100:                                  # 烂时间 → 反算毫秒 → 真时间
            ms = int(time.mktime((y, mo, d, hh, mi, ss, 0, 0, -1)))
            sec = ms // 1000
            m["time"] = _fmt_bj(sec)
            m["ts"] = sec
            fixed += 1
        elif not m.get("ts"):                         # 补齐 ts（旧数据）
            m["ts"] = int(time.mktime(time.strptime(t, "%Y-%m-%d %H:%M:%S")))
    if fixed:
        _mark_messages_dirty()
        _flush_messages_sync()
        _debug_log(f"_repair_message_times: fixed {fixed} messages")
    return fixed
```

- 调用点：`redis_loop()` 启动时（`_rebuild_known_ids()` 之后）跑一次；用标记文件
  `~/.ev_time_repaired_v1` 防止每次启动全量扫（用户可删标记重跑）。
- 若 `payload.paid_at` 存在（毫秒、权威），**优先用它**覆盖上面算出的处理时间。
