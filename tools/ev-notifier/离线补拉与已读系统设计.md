# EvNotifier 离线补消息 + 已读系统设计

> 目标：回答三个问题
> 1. 通知在「客户端离线 → 重新上线」这一段为什么丢、丢在哪一层；
> 2. 给出一套**稳定、规范、可验收**的离线补拉流程（SOP）；
> 3. 重新设计「已读」子系统，并顺带解释「消息面板打不开 / 点完全部已读列表空了」这类表象。

代码基线：`tools/ev-notifier/ev_notifier.py`（205KB 单文件）、`lib/notify.js`、`lib/message-delivery.js`、`api/admin/health.js`。

---

## 0. 结论速览

| 问题 | 根因 | 优先级 |
|---|---|---|
| 离线期间的通知收不到 | Redis PUB/SUB 是 **fire-and-forget**，离线期间发布的消息永久消失；唯一的补拉是「按状态查 7 天未投递」，不是游标 | P0 |
| **连上了也不补拉**（最隐蔽） | `redis.Redis(...)` **没设 `socket_timeout`**，死连接会永久阻塞在 `pubsub.listen()`，既不抛异常也不重连 → `_startup_recovery` 再也不触发 | **P0-0** |
| 补拉会漏 / 会超时 | 补拉是「状态式」（`status IN pending/published/failed`）而非「游标式」，且硬编码 168h 窗口、无分页、无 per-client 维度 | P0 |
| 补拉的消息顺序/去重不可靠 | `store_message` 是 load→insert→save，**无锁**，与 PUB/SUB 线程并发写同一文件；`_seen_ids` 满 1000 直接 `clear()` | P1 |
| 「今日消息」数字乱跳 | 徽标用会话变量 `_new_msg_count`，已读用持久字段 `read`，**两套口径**；切页只清零徽标不写已读 | P1 |
| 点「Mark All Read」后列表空了 | `DOMContentLoaded` 默认 `filterMessages('unread')`，全标已读后当前视图自然为空 → 用户以为面板坏了 | P0（体验） |
| 面板偶发打不开/空白 | `_refresh_content` 用 `data:text/html;base64` 整页灌 + 异常被吞只写 debug log | P1 |

## 2. 离线为什么丢消息：逐层拆解

### 2.1 根因：PUB/SUB 天生不保序、不持久化

`PUBLISH` 没有订阅者时消息直接丢弃，Redis 不保留任何历史。客户端离线 N 分钟，这 N 分钟的所有 `PUBLISH` 全部消失。
**结论：离线补拉不可能靠 PUB/SUB 自身解决，必须有一条独立的「按游标拉取历史」通道。**

### 2.2 P0-0：死连接会永久挂住，连"重连"都不会发生

```python
r = redis.Redis(host=..., socket_connect_timeout=10, socket_keepalive=True, health_check_interval=30)
...
for message in pubsub.listen():   # ← 阻塞读，没有 socket_timeout
```

只设了 `socket_connect_timeout`（建连阶段），**没有 `socket_timeout`（读写阶段）**。当网络进入黑洞状态（无 RST，典型场景：Mac 合盖睡眠 / Wi-Fi 切换 / 路由器 NAT 表老化 / Upstash 侧 idle 断链但本机不知），`listen()` 会无限期阻塞：

- 不抛异常 → `except` 分支不进 → **不重连** → `_startup_recovery` 不再触发；
- `_status` 一直是 `"connected"`（`:1013`）→ 面板显示 Online，用户以为一切正常；
- 实际状态：**实时收不到，离线也不补**。

`health_check_interval=30` 只能覆盖「socket 还能正常读写但空闲」的场景；真正的读阻塞要靠 `socket_timeout`。

### 2.3 兜底的 XADD stream 形同虚设

服务端每次推送都 `XADD` 了 stream（本可当回放日志用），但客户端：
- 主链路不消费 stream（只 PUB/SUB）；
- 唯一消费 stream 的 `do_recovery_poll()` 是死代码；
- Postgres 兜底写的 `kv_streams` 客户端根本不读。

→ **stream 白写了。**

### 2.4 补拉查询是「状态式」而非「游标式」，有 4 个硬伤

`lib/message-delivery.js:105`：

```sql
WHERE status IN ('pending','published','failed') AND created_at > NOW() - INTERVAL '168 hours'
```

| # | 硬伤 | 后果 |
|---|---|---|
| a | **没有 per-client 维度** | 多端（两台 Mac / 重装后新 client）会互相干扰：A 收到后标 delivered，B 就再也补不到这条 |
| b | **没有游标**，每次全量返回 | 高频 `page_visit` 场景下 7 天可达数千条，单次 curl `--max-time 10`（`:669`）必超时，且每次重连重复拉全量 |
| c | **168h 硬窗口** | Mac 关机/睡眠超过 7 天 → 永久丢失，且无任何告警 |
| d | **依赖 status 语义** | `markDelivered` 的 WHERE 是 `status='published'`（`lib/message-delivery.js:71`）：若 `markPublished` 被 Vercel 冻结截断，记录卡在 `pending`，客户端回调 `delivered` **0 行生效** → 这条永远留在 undelivered 列表，每次重连都被重放 |

补充：`status='confirmed'` 恒为 0 —— 全仓**没有任何地方发 `event:"confirmed"`**（`ev_notifier.py:978` 只发 `delivered`），服务端无法知道用户到底看没看。

### 2.5 重连风暴 & 并发写文件

- `_startup_recovery` 在**每次**重连都起一个线程（`:1015`），无节流、无 in-flight 标志。网络抖动 + 30s 退避上限 = 反复全量拉取。
- `store_message`（`:195`）是 `load_messages() → insert(0) → save_messages()`，与 PUB/SUB 线程**并发无锁** → 后写覆盖先写，直接丢消息或写坏 JSON。
- `_seen_ids` 满 1000 整体 `clear()`（`:756-757`），`_switch_to("messages")` 也会 `clear()`（`:4211`）→ 去重能力随时归零 → 重复插入。
- 补拉用 `skip_notify=True`，**用户完全不知道补了多少条**（只在 debug log 里）。

## 3. 设计目标与不变量

**目标**
1. 离线任意时长（≤ 保留期）后重新上线，消息**一条不少、不重复、顺序正确**；
2. 补拉与实时链路互不阻塞，补拉失败不影响实时；
3. 已读状态单一口径、幂等、不卡 UI。

**不变量（写进代码注释，任何改动不得破坏）**
- I1：每条消息服务端有全局单调 `seq`（`message_delivery.id` bigserial）+ 稳定 `message_id`（UUID）；
- I2：客户端持久化 `client_id` 与 `last_seq`，**只以 seq 为水位线，绝不以时间或 status 为水位线**；
- I3：所有入库路径（实时 / 补拉 / 重发）走**同一个幂等入口** `ingest(seq, msg)`；
- I4：`~/.ev_messages.json` 的写入必须持同一把锁 + 原子落盘（tmp + `os.replace`）；
- I5：`read` 是唯一未读口径，徽标由它派生，不再维护第二套计数。

## 4. 规范流程：离线补拉 SOP（推荐方案）

### 4.1 服务端：新增「按游标增量拉取」

**(1) 推送报文带上 `seq`** —— `lib/notify.js:1011-1023`，让实时链路也能推进水位线：

```js
var msg = { ts: ..., type: type, payload: payload || {} };
if (deliveryMessageId) msg.messageId = deliveryMessageId;
if (deliverySeq)       msg.seq      = deliverySeq;   // ← 新增：message_delivery.id
```

> 让 `createMessageDelivery` 用 `INSERT ... RETURNING id` 把 `id` 回传（`lib/message-delivery.js:26-51` 目前只返回 `mid`）。
> 这一步是关键：有了 seq，实时与补拉可以并发跑、靠 max(seq) 收敛，不需要"先补后订阅"的严格时序。

**(2) 新增 per-client 回执表**（解决 2.4-a）

```sql
create table if not exists message_delivery_receipt (
  message_id varchar(64) not null,
  client_id  varchar(128) not null,
  state      varchar(16) not null default 'delivered',  -- delivered | read
  delivered_at timestamptz,
  read_at      timestamptz,
  primary key (message_id, client_id)
);
```

**(3) 新增同步接口** `section=delivery-sync`（放在 `api/admin/health.js:662` `delivery-query` 分支旁边）：

```
GET /api/admin/health?section=delivery-sync&client_id=<cid>&after=<last_seq>&limit=200
→ { success, messages:[{seq, message_id, message_type, payload, created_at}...],
    next_cursor, has_more, server_now }
```

实现要点（`lib/message-delivery.js` 新增 `getSince(afterSeq, limit)`）：

```sql
SELECT id AS seq, message_id, message_type, payload, created_at
FROM message_delivery
WHERE id > $1
ORDER BY id ASC          -- ← 只按 id 排序，不用 created_at（时钟偏移/同毫秒会错位）
LIMIT $2
```

- 游标用 `id`，**不用时间**：时间是浮点、可回拨、同一毫秒会重复；
- 返回后 `has_more=true` 客户端继续翻页，直到追平或达上限；
- 上限保护：单次同步最多 2000 条 / 10 页，超出只补最近 2000 条并提示"部分补齐"；
- 保留期由服务端控制（建议 14 天，可在接口里返回 `retention_hours`）。

### 4.2 客户端：三态 + 水位线

新增 `~/.ev_sync_state.json`：

```json
{ "client_id": "<hostname>-<uuid4>", "last_seq": 0, "last_sync_at": 1730000000 }
```

- `client_id` **首次生成即持久化**，重装不丢、不随 hostname 变化漂移；
- `last_seq` 只在**成功处理完一批**后才推进，且只推进到「本批最大 seq」（不要求连续，允许空洞 —— 空洞是别的客户端/失败记录，无害）。

### 4.3 上线后的标准同步流程（SOP）

```
┌─ 启动 / 重连成功 ─────────────────────────────────────────────┐
│                                                               │
│  S1  读/建 client_id、读 last_seq            （秒级，同步）    │
│  S2  SUBSCRIBE auth:push_channel             （先订阅，避免补拉│
│                                               期间的实时空洞） │
│  S3  SYNC: 循环 GET delivery-sync?after=last_seq&limit=200     │
│        ├─ 每条 → ingest(seq, msg, source="sync")               │
│        ├─ seq <= last_seq  → 跳过（幂等）                      │
│        ├─ has_more → 继续翻页（≤10 页 / 2000 条）              │
│        └─ 本批全部成功后 → 推进 last_seq → 原子落盘            │
│  S4  实时链路收到的 msg.seq → last_seq = max(last_seq, seq)    │
│                              （节流 5s 落盘一次）              │
│  S5  汇总：补回 N 条 → 只弹 1 条聚合通知「离线期间补回 N 条」   │
│      （不逐条弹窗、不逐条念语音，避免补拉风暴刷屏）             │
│  S6  批量回执：POST delivery-callback 批量版，标记 delivered    │
│  S7  进入稳态：每 5 分钟增量 sync 一次（对账），不依赖重连事件  │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

**顺序为什么是「先订阅，再补拉」**
- 反序（先补后订）会在补拉结束与订阅生效之间留一个窗口，期间的消息两边都不管；
- 正序靠 `seq` 幂等去重消除重复（补拉拿到、实时又来一次 → `seq <= last_seq` 直接丢），**重复可接受，丢失不可接受**。

### 4.4 幂等入口（唯一入库路径）

```python
_MSG_LOCK = threading.RLock()          # 与 store_message 共用

def ingest(seq, msg, source="live"):
    """唯一入库入口：幂等、加锁、推进水位线。返回 True 表示是新增消息。"""
    with _MSG_LOCK:
        if seq and seq <= _state["last_seq"]:
            return False                       # 已处理（补拉/实时重复）
        if msg.get("messageId") in _local_ids():
            return False                       # 历史数据无 seq 时按 messageId 兜底去重
        store_message(...)                     # 原子写
        _remember_id(msg.get("messageId"))
        if seq: _state["last_seq"] = max(_state["last_seq"], seq)
        return True
```

- `_seen_ids` 改成 `collections.deque(maxlen=2000)` 或 `OrderedDict` LRU，**淘汰最旧而不是整体 clear**；
- `_switch_to("messages")` 里的 `_seen_ids.clear()`（`:4211`）**必须删掉**；
- `store_message` 改为 `with _MSG_LOCK` + 写 tmp 后 `os.replace`（防半截 JSON）。

### 4.5 断线检测与重连（修 P0-0）

```python
r = redis.Redis(..., socket_connect_timeout=10,
                     socket_timeout=60,           # ← 新增：读阻塞最多 60s
                     socket_keepalive=True,
                     health_check_interval=30,
                     retry_on_timeout=True)
```

再加**看门狗**（独立线程，30s 一轮）：

```
if now - last_rx_at > 90s:
    try: r.ping()
    except: 主动 close() 触发重连         # 只有 ping 失败才重建
```

⚠️ 判据必须是「**ping 失败**」，不能是「一段时间没消息」—— 低流量时段（凌晨没访问）会误判，导致无意义重连风暴。

同步节流：
- `_startup_recovery` / `sync_since()` 加 in-flight 标志 + 最小间隔 30s；
- 补拉失败 → 退避 2/4/8/…/60s 重试，**不阻塞 PUB/SUB**；
- 连续失败 > 3 次 → 面板顶部显示「离线补拉失败，实时推送仍在线」。

### 4.6 时间线示例

```
t=10:00  客户端在线，last_seq=1000，收到 seq=1001 → last_seq=1001
t=10:05  Mac 合盖睡眠（socket 进入黑洞，listen() 阻塞）
t=10:05~12:00  服务端推送 seq=1002…1080（PUBLISH 全部丢弃）
t=12:00  唤醒。socket_timeout=60 到点 / watchdog ping 失败 → 重建连接
t=12:00  SUBSCRIBE 成功 → SYNC after=1001 → 拉回 1002…1080（79 条，一页够）
t=12:00  推进 last_seq=1080，弹 1 条聚合通知「离线期间补回 79 条」
t=12:00  批量回执 delivered ×79
t=12:05  稳态增量 sync，无新消息
```

## 7. 已读系统设计

### 7.1 现状：两套口径 + 一个反直觉默认值

```python
# 切到消息页：只清零徽标，不写已读
def _switch_to(self, page_id):                 # :4206
    if page_id == "messages":
        _new_msg_count = 0                     # :4210  会话变量清零
        _seen_ids.clear()                      # :4211  顺手把去重集合也清了（错）
```

- 未读有两套来源：徽标 `_new_msg_count`（会话级、切页即清零）与 `read` 字段（持久、只有手动点「Mark All Read」才改）；
- 结果：**徽标消失了，列表里那些条目还是未读** —— 用户困惑"到底读没读"；
- `_html_messages` 里「今日消息」卡片用的是 `_new_msg_count`（`:2833`），但它是**会话计数不是今日计数**，切一次页就归零，标签是错的；
- `DOMContentLoaded` 默认 `filterMessages('unread')`（`:4437-4439`）→ 点「Mark All Read」后列表**立刻清空**，配合空态文案 "No messages / Waiting for notifications..."（`:2894-2895`），观感就是"面板坏了 / 消息没了"；
- 没有单条已读；已读不回传服务端 → `confirmed` 恒为 0。

### 7.2 设计目标

1. **单一口径**：未读数 = 本地 `read=False` 的条数，徽标由它派生；
2. **自动但不粗暴**：打开面板即已读，但只标记「实际渲染出来的」，不是无脑全标 500 条；
3. **不卡 UI**：标记异步、防抖批量、幂等落盘；
4. **不反直觉**：标已读后列表不清空。

### 7.3 数据模型

本地消息条目（`~/.ev_messages.json`）：

```json
{ "time": "...", "type": "...", "payload": {...}, "messageId": "...", "seq": 1080,
  "read": false, "read_at": null }
```

服务端（P2）：`message_delivery_receipt.state = 'read'` + `read_at`，或复用 `markConfirmed`（`status='confirmed'`）。

### 7.4 触发规则（推荐）

| 触发 | 行为 | 延迟 |
|---|---|---|
| 面板打开且当前页 = messages **且窗口获得焦点** | 标记当前视图渲染出的卡片（前 50 条）已读 | 1.2s（防误触：切页路过不算） |
| 滚动到底 / 加载更多 | 标记新渲染出的那批 | 300ms 防抖 |
| 单条点击展开详情 | 立即标记该条（`ev://read=<seq>`） | 0 |
| 手动「Mark All Read」 | 全量标记（保留，作为逃生舱） | 0 |
| 后台静默（面板未打开） | **不**自动标记 | — |

> 「窗口获得焦点」这一条很重要：面板在后台被 `_refresh_content` 重灌时不应该把用户没看过的消息标成已读。

### 7.5 写入策略（保证流畅）

```python
_READ_DEBOUNCE = 0.4   # 秒

def mark_read(seqs, persist=True):
    """批量、幂等、防抖、只写一次。"""
    with _MSG_LOCK:
        changed = [s for s in seqs if not _is_read(s)]
        if not changed:
            return 0                      # 幂等：无变化直接返回，不落盘
        for s in changed:
            _set_read(s)
        if persist:
            _atomic_save_messages()       # tmp + os.replace
    _schedule_read_receipt(changed)       # 异步回传服务端，失败静默重试 1 次
    return len(changed)
```

要点：
- **dirty 才落盘**：没有 False→True 的条目就不写文件（现在 `mark_all_messages_read` 的 `changed` 判断是对的方向，保留并推广）；
- **防抖合并**：滚动/多次触发合并成一次写，避免 500 条 JSON 反复全量序列化；
- **同一把锁**：与 `store_message` 共用 `_MSG_LOCK`，彻底消除"新消息到达 vs 标记已读"互相覆盖；
- **不整页重灌**：现在 `_mark_all_read`（`:4214-4218`）走 `_refresh_content()` = 重新 base64 灌整页 → 滚动位置丢失 + 闪屏 + 大 HTML 风险。改成：内存改 `read` → 前端 JS 把 `.msg-unread` 换成 `.msg-read` 并更新计数；**只有筛选条件变化才重灌**；
- 徽标：删掉 `_new_msg_count` 作为未读源，改 `@rumps.timer(2)` 里读 `count_unread()`（加内存缓存，消息变更时失效）。

### 7.6 前端配合改动

```javascript
// 1) 默认筛选从 unread 改成 all，避免"全标已读 → 列表空"
if ('messages' === page) { filterMessages('all'); }

// 2) 面板可见 + 聚焦 1.2s 后，上报当前可见卡片
setTimeout(function(){ window.location = 'ev://read-visible=' + visibleSeqs.join(','); }, 1200);

// 3) 空态文案区分
//    filter=unread 且无未读 → "没有未读消息"（不是 "No messages / Waiting..."）
```

### 7.7 完整时序

```
用户点状态栏「打开面板」
  → open_dashboard (callLater 0.05s)          :4631
  → show() → _show_impl → _recreate_window + _refresh_content   :2473
  → HTML 渲染，默认 filter='all'
  → 1.2s 后 JS 上报可见 seq 列表 → ev://read-visible=...
  → mark_read(seqs) 加锁批量改 + 原子落盘（dirty 才写）
  → 前端就地改 class + 更新未读计数（不重灌页面）
  → 异步 POST read 回执（失败静默重试 1 次）
  → rumps 定时器读 count_unread() 更新徽标
```

## 10. 附：状态机对照

**服务端 `message_delivery.status`**

```
pending ──markPublished──> published ──markDelivered──> delivered ──markConfirmed──> confirmed
   │                            │
   └────── markFailed ──────────┘
```

⚠️ 每个 UPDATE 都带 `WHERE status='<前一态>'`（`lib/message-delivery.js:54-89`）→ 严格串行，任一环被 Vercel 冻结截断，后续全部 0 行生效且**静默**。
建议：改为 `WHERE id = $1`（幂等，允许重复调用），用 `GREATEST`/条件赋值避免倒退。

**客户端消息状态**

```
(补拉/实时) ──> ingest(seq) ──> unread ──> (可见 1.2s / 点击 / 手动) ──> read
                    │
                    └─ seq <= last_seq → 丢弃（幂等）
```

## 11. 一句话总结

> 离线丢消息的根因是 **PUB/SUB 不持久化 + 补拉是状态式而非游标式 + 死连接不会自动重连**；
> 解法是 **给每条消息一个单调 seq，客户端持久化 `client_id` 与 `last_seq`，用「先订阅、再按游标补拉、靠 max(seq) 收敛」的幂等 SOP**；
> 已读的解法是 **单一口径（read 字段）+ 可见即已读 + 防抖批量落盘 + 不整页重灌**，并顺手把默认筛选从 `unread` 改成 `all`，消除「点完全部已读列表就空了」的错觉。
