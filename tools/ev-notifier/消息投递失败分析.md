# EvNotifier 消息投递失败分析

> 问题：`new_activation` 消息停留在"待投递"状态，不推送到 Mac 通知。`new_order` 消息正常投递。
> **状态：已修复 ✅** (2026-09-19)

---

## 0. 修复记录

### 修复 1：`api/activate.js` — 调整 `pushNotification` 在 `res.json()` 之前执行

**根因**：成功激活路径和 catch 块中，`res.json()` 在 `await notify.pushNotification()` 之前调用。Vercel Serverless 在 HTTP 响应返回后会冻结函数，导致 push 操作被中断。

**改动**：
- 成功激活路径：将 `await notify.pushNotification("new_activation", ...)` 移到 `res.json()` 之前
- catch 块：将 `await notify.pushNotification("activation_failure", ...)` 移到 `res.status(500).json()` 之前
- 邮件通知保持 fire-and-forget 在 `res.json()` 之后（低优先级）

### 修复 2：`api/admin/health.js` — 新增 `retry-stuck` 恢复接口

新增 `action=retry-stuck` POST 接口，可重新投递所有 stuck 在 `pending` 状态的僵尸消息。

**调用方式**：`POST /api/admin/health?section=delivery-query&action=retry-stuck`

## 3. 根因分析

### 3.1 最可能的原因：`activate.js` 的 PUBLISH 代码路径有 bug

在 `api/activate.js` 中，伪代码逻辑推测如下：

```javascript
// api/activate.js (推测)
async function handleActivation(req) {
  // 1. 验证兑换码、执行激活
  const result = await activateDevice(...);

  // 2. 创建消息投递记录 (status=pending)
  const msgId = await createMessageDelivery({
    type: 'new_activation',
    payload: { deviceId, productId, months, ... },
    source: 'activate.js'
  });

  // 3. 可能这里出了问题 ⚠️
  // 可能性 A: try/catch 吞掉了 PUBLISH 的错误
  try {
    await publishToRedis('auth:push_channel', { messageId: msgId, ...data });
    await markPublished(msgId);
  } catch (e) {
    console.error('PUBLISH failed:', e);
    // ❌ 没有重试，没有标记 failed，消息永远 pending
  }

  // 可能性 B: 条件判断跳过了 PUBLISH
  if (result.success && result.months >= 99) {
    // ❌ 只有永久激活才 PUBLISH？但数据库记录已创建
    await publishToRedis(...);
  }

  // 可能性 C: 异步 PUBLISH 未 await
  publishToRedis(...);  // ❌ 没有 await, Vercel Serverless 在函数返回后立即冻结
  await markPublished(msgId);  // ❌ 这行永远不会执行
}
```

**最可能的是原因 C**：Vercel Serverless Functions 在 HTTP 响应返回后会立即冻结，如果 `PUBLISH` 和 `markPublished` 没有被 `await` 或者在响应之后执行，它们会被 Vercel 运行时中断。

### 3.2 对比 `new_order` 为什么没问题

`api/afdian/orders.js` 可能在响应返回前完整执行了 PUBLISH + markPublished：

```javascript
// api/afdian/orders.js (推测)
export default async function handler(req, res) {
  const newOrders = await fetchAfdianOrders();
  for (const order of newOrders) {
    const msgId = await createMessageDelivery({...});       // ✅ await
    await publishToRedis('auth:push_channel', {...});       // ✅ await
    await markPublished(msgId);                              // ✅ await
  }
  // ✅ 所有操作完成后才返回响应
  res.json({ success: true });
}
```

### 3.3 次要原因：`_startup_recovery` 无法挽救 pending 消息

EvNotifier 启动时调用 `_startup_recovery()`（位于 [ev_notifier.py:L642](file:///Users/Banner/Documents/guomengtao/app-auth/tools/ev-notifier/ev_notifier.py#L642)），查询：

```
GET /api/admin/health?section=delivery-query&action=undelivered&hours=168
```

**推测服务端 SQL**：
```sql
-- 可能只查询 published 但未 delivered 的消息
SELECT * FROM message_delivery
WHERE status = 'published'              -- ⚠️ 注意这里
  AND delivered_at IS NULL
  AND created_at > NOW() - INTERVAL '168 hours';
```

**如果查询条件是 `status = 'published'`**，那么 `status = 'pending'` 的消息永远不会被 `_startup_recovery` 发现和恢复。pending 消息就变成了"僵尸消息"，永远卡在待投递。

**正确的查询应该是**：
```sql
SELECT * FROM message_delivery
WHERE status IN ('pending', 'published', 'failed')   -- ✅ 包含 pending
  AND delivered_at IS NULL
  AND created_at > NOW() - INTERVAL '168 hours';
```

## 4. 解决方案

### 4.1 短期修复（Server 端）

修改 `api/activate.js`，确保 PUBLISH 在响应返回前完成：

```javascript
// api/activate.js - 修复版
export default async function handler(req, res) {
  try {
    // ... 激活逻辑 ...

    // 创建投递记录
    const msgId = await createMessageDelivery({
      type: 'new_activation',
      payload: { /* ... */ },
      source: 'activate.js'
    });

    // ✅ 必须在 res.json() 之前 await PUBLISH
    try {
      await publishToRedis('auth:push_channel', {
        messageId: msgId,
        type: 'new_activation',
        ts: Date.now(),
        payload: { /* ... */ }
      });
      await markPublished(msgId);
    } catch (pubErr) {
      console.error('PUBLISH failed for activation:', pubErr);
      // 标记为 failed 以便后续恢复
      await markFailed(msgId, pubErr.message);
    }

    // 所有操作完成后才返回
    res.json({ success: true, messageId: msgId });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
}
```

### 4.2 修复恢复查询（Server 端）

修改 `/api/admin/health?section=delivery-query&action=undelivered`：

```sql
-- 修复后：包含所有未送达的消息
SELECT * FROM message_delivery
WHERE status IN ('pending', 'published', 'failed')
  AND delivered_at IS NULL
  AND created_at > NOW() - INTERVAL '168 hours'
ORDER BY created_at ASC;
```

### 4.3 增强 EvNotifier 恢复（可选）

在 `_startup_recovery` 中增加对 pending 消息的重试逻辑：

```python
def _startup_recovery():
    # 当前已查询 undelivered → 若服务端修好后，pending 也会被返回
    # 增加：如果 message_type=='new_activation' 且 status=='pending',
    # 触发一次 retry-delivery API
    ...
```

### 4.4 长期方案：定时清理僵尸消息

在 Server 端增加一个 cron job（或 Vercel Cron），定期检查长时间 pending 的消息：

```javascript
// api/cron/retry-pending.js
export default async function handler() {
  const stuck = await supabase
    .from('message_delivery')
    .select('*')
    .eq('status', 'pending')
    .lt('created_at', new Date(Date.now() - 30 * 60 * 1000).toISOString());

  for (const msg of stuck) {
    await publishToRedis('auth:push_channel', {
      messageId: msg.message_id,
      type: msg.message_type,
      payload: msg.payload,
      ts: Date.now(),
    });
    await supabase.from('message_delivery')
      .update({ status: 'published', published_at: new Date().toISOString() })
      .eq('message_id', msg.message_id);
  }
}
```

## 5. 总结

| 项目 | 状态 | 说明 |
|------|:---:|------|
| Redis PUB/SUB 连接 | ✅ 正常 | `new_order` 消息实时送达，延迟 < 5s |
| `_delivery_callback` | ✅ 正常 | 已送达的消息全部回调确认成功 |
| `activate.js` PUBLISH | ❌ 有问题 | `new_activation` 消息从未 PUBLISH |
| `_startup_recovery` | ⚠️ 部分有效 | 受限于服务端查询条件，pending 消息不被返回 |
| 本地消息存储 | ⚠️ 有缺失 | index 39 丢失（对应一条未收到的消息） |

**核心结论**：问题出在 Server 端的 `api/activate.js`，创建了 `message_delivery` 记录但未成功执行 PUBLISH 到 Redis。需要检查 `activate.js` 中的 PUBLISH 调用是否被正确 await、是否在响应返回前完成、是否有 try/catch 吞掉了错误。
