# 重发按钮无效问题分析

> 问题：消息投递后台点击「🔄 重发」按钮，页面乱晃闪动，消息也没发出去。

---

## 一、完整调用链路

```
用户点击「🔄 重发」按钮
  ↓
[前端] retrySingleMessage(msgId, btn)
  ↓ fetch POST
[服务端] /api/admin/health?section=delivery-query&action=retry-stuck
  ↓ body: { message_id: "xxx" }
  ↓
[服务端] body = req.body || {}
[服务端] targetMessageId = body.message_id
[服务端] singleMsg = await md.getByMessageId(targetMessageId)
  ↓ 查到记录?
  ├─ 是 → retryOneMessage(sm)
  │         ├─ XADD to auth:notifications:stream (Upstash REST API)
  │         ├─ markPublished(msgId)
  │         └─ PUBLISH to auth:push_channel (Upstash REST API)
  └─ 否 → stuckMessages = [] → retried = 0 → 返回失败
  ↓
[前端] 响应到达
  ├─ retried > 0 → btn.textContent = '✅ 已重发'
  │   └─ setTimeout → loadDeliveryMessages()  ← 问题出在这里!
  └─ retried = 0 → btn.textContent = '❌ 失败'
```

---

## 二、问题 1：页面乱晃（视觉闪动）

### 根因

`retrySingleMessage` 成功后调用了 `loadDeliveryMessages()`：

```javascript
// admin_Dx23.html 第 9687 行附近
btn.textContent = '✅ 已重发';
setTimeout(function() { loadDeliveryMessages(); }, 500);
```

而 `loadDeliveryMessages()` 的第一步就是**立即清空整个表格**：

```javascript
// admin_Dx23.html 第 9601 行
function loadDeliveryMessages() {
    ...
    tbody.innerHTML = '<tr><td colspan="7" class="empty">加载中...</td></tr>';
    // ↑ 这句立刻把全部行替换成 1 行 "加载中..."
    //   表格高度瞬间坍塌，看起来像"乱晃"
    ...
    fetch('/api/admin/health?' + params, ...)
        .then(...)  // 几百毫秒后重新渲染全部行
}
```

### 闪动时序

```
1. 表格有 N 行数据（正常显示）
2. 点击重发 → fetch 中...
3. fetch 完成 → 按钮变成 "✅ 已重发"
4. 500ms 后 → loadDeliveryMessages()
5. tbody.innerHTML = "加载中..."    ← 表格瞬间缩成 1 行高，"晃"了一下
6. 200ms 后 → 新数据到达           ← 表格重新展开，又"晃"一下
7. 恢复 N 行数据
```

用户看到的效果：表格先缩再涨，闪烁一下——误以为是「页面刷新」。

### 修复方案

**不要整表重刷**——对于单条重试，只需原地更新该行的状态列即可。避免 `loadDeliveryMessages()` 的整体 innerHTML 替换。

```javascript
// 修复后：重发成功后只更新当前行，不重载整表
btn.textContent = '✅ 已重发';
// 找到当前行的状态单元格并更新
var row = btn.closest('tr');
var statusCell = row.cells[2];  // 第3列是状态
statusCell.innerHTML = '<span style="color:#3b82f6;font-weight:600;font-size:0.72rem">📤 已发布</span>';
// 移除 setTimeut → 不再调用 loadDeliveryMessages()
```

## 三、问题 2：发送失败（消息没发出去）

### 3.1 前端传参是否正常？

```javascript
// admin_Dx23.html 第 9682 行
fetch('/api/admin/health?section=delivery-query&action=retry-stuck', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ message_id: messageId }),
})
```

`messageId` 来自 `r.message_id`，是数据库返回的 UUID（如 `a1b2c3d4-e5f6-7890-abcd-ef1234567890`）。

✅ 前端传参正常。

### 3.2 服务端接收 body 是否正常？

```javascript
// api/admin/health.js 第 698 行
var body = req.body || {};
var targetMessageId = body.message_id || req.query.message_id || null;
```

⚠️ **潜在风险**：在 Vercel Serverless 环境中，`req.body` 是否可用取决于 Vercel 的 body 解析机制。

- Vercel Node.js Runtime 的 `@vercel/node` 默认会解析 JSON body
- 但如果中间件序列改变、或者请求的 Content-Type 处理异常，`req.body` 可能为 `{}`
- 此时 `targetMessageId` 为 `null`，走批量模式 → `getUndelivered(168)` → 可能重试其他消息

**排查方法**：在服务端加一行日志：

```javascript
console.log("[retry-stuck] raw body:", JSON.stringify(req.body), "parsed message_id:", targetMessageId);
```

### 3.3 数据库查询是否正常？

```javascript
// lib/message-delivery.js 第 116-125 行
async function getByMessageId(messageId) {
  if (!messageId) return null;
  var sql = "SELECT * FROM " + TABLE + " WHERE message_id = " + escapeLiteral(messageId);
  var r = await pg.query(sql);
  return (r.rows && r.rows.length > 0) ? r.rows[0] : null;
}
```

如果 `message_id` 正确传入，SQL 应该是 `SELECT * FROM message_delivery WHERE message_id = 'uuid-value'`。

⚠️ **可能失败场景**：
1. 数据库连接在 Serverless cold start 时未就绪 → `pg.query` 抛异常 → 返回 `null`
2. message_id 在页面首次加载和重发之间被清理了（cleanOld 定时任务）
3. 换行符、空格等不可见字符混入 message_id（`escapeLiteral` 只转义单引号）

**排查方法**：同样加日志：

```javascript
var singleMsg = await md.getByMessageId(targetMessageId);
console.log("[retry-stuck] getByMessageId result:", singleMsg ? "found" : "NOT FOUND", "message_id:", targetMessageId);
```

### 3.4 Upstash 推流是否成功？

```javascript
// api/admin/health.js 第 717 行
var xaddUrl = upstashUrl.replace(/\/$/, "") + "/xadd/auth:notifications:stream/*/data/" + encodeURIComponent(retryRaw);
var r = await fetch(xaddUrl, {
    method: "POST",
    headers: { "Authorization": "Bearer " + upstashToken },
    signal: AbortSignal.timeout(5000),
});
```

⚠️ **可能失败场景**：
1. `process.env.KV_REST_API_URL` 或 `KV_REST_API_TOKEN` 未设置 → `upstashUrl` 为空字符串 → XADD URL 不合法
2. Upstash REST API 返回非 200 状态（token 过期、账户限制等）
3. 5 秒超时（网络延迟）

注意：PUBLISH 失败时只打印了 `console.error`，不影响返回结果。所以即使 XADD 成功、PUBLISH 失败，前端也会看到「✅ 已重发」，但 EvNotifier 可能收不到消息（取决于 EvNotifier 是否订阅了 Stream 还是 Channel）。

### 3.5 综合判断

前端已经显示了失败原因（在上次修改中加了 `btn.title = reason`），所以可以**鼠标悬停在「❌ 失败」按钮上**查看 tooltip 中的失败原因。

根据失败原因判断：

| tooltip 内容 | 对应根因 |
|-------------|---------|
| `no Upstash config` | `KV_REST_API_URL` 或 `KV_REST_API_TOKEN` 未设置 |
| `HTTP 401: ...` | Upstash token 无效 |
| `HTTP 500: ...` | Upstash 服务端错误 |
| `timeout` 相关 | Upstash 网络超时 |
| `getByMessageId failed` | 数据库查询异常 |
| 空（retried = 0） | message_id 在数据库中不存在 |

## 四、修复建议

### 4.1 前端修复（问题1：页面乱晃）

修改 `retrySingleMessage` 函数，成功后直接更新当前行的状态列和 timeline 列，而不是调用 `loadDeliveryMessages()` 全表重刷。

### 4.2 服务端修复（问题2：诊断增强）

在 `retry-stuck` 接口加诊断日志，确认：
1. `req.body` 是否正确解析到了 `message_id`
2. `getByMessageId` 是否查到了记录
3. Upstash XADD 和 PUBLISH 的 HTTP 状态码

### 4.3 服务端修复（问题2：健壮性）

如果 `targetMessageId` 有值但 `getByMessageId` 返回 null，返回明确错误给前端：

```javascript
if (targetMessageId) {
    var singleMsg = await md.getByMessageId(targetMessageId);
    if (!singleMsg) {
        return res.json({ 
            success: false, 
            error: "Message not found", 
            message_id: targetMessageId 
        });
    }
    stuckMessages = [singleMsg];
}
```
