## 一、目标与边界

**目标**：给 evtask 任务加上「活跃」概念——每个任务能自答"我负责的会话还活着吗？活了多久没动？"，并让晨割 v2 的 8 小时收割从"人工命令行判断"升级为"系统字段直接可查"。

**要解决的三个真实痛点**（今天上午实战暴露）：
1. 晨割收割 12 条僵尸认领时，只能靠 `ev-claim.sh list` 的文本时间戳人肉判断，无系统字段；
2. Trae 会话裸奔编辑（无认领无心跳），任务系统完全看不见它——**"没有心跳"本身就是最重要的活跃信号**；
3. evops 面板看任务列表时，无法一眼区分"正在进行"和"挂着没人管"。

**边界（本方案不做）**：
- 不改 `in_progress/done/cancelled/blocked` 生命周期状态机（活跃是**附加维度**，不是新状态）；
- 不做推送/告警通知（面板展示 + 晨割查询即可）；
- 不动激活/支付等黑名单域。

## 二、侦察结论（已有地基）

| 已有机制 | 位置 | 可复用度 |
|---|---|---|
| 会话心跳 `evops_sessions.heartbeat_at` + `idle_min` | ev.js L1197/L1553/L1806 | ★ 直接复用——判定主信号 |
| 会话↔任务绑定 `open_task_id` | sessions 表 + task-close 清理（L1744） | ★ 直接复用——反向查任务归属 |
| 任务聚合已拼 `session_heartbeat_at` | ev.js L1843 | ★ 列表接口已带心跳，只差"算出活跃档位" |
| 僵尸判定先例 | L1572 注释："审查员读 heartbeat_at 判断会话是否还活着" | 规则已成文，缺的是系统化 |
| 晨割 v2 | guomengtao/docs/晨割协议-日切归零方案.md | 消费方：需要按 idle 阈值批量收割 |

**关键缺口**：任务表本身无 activity 概念；无"会话死了但任务还 in_progress"的自动降档；认领（.claims 本地 JSON）与服务端任务两套体系活跃度不互通。

## 三、活跃度定义（三信号合成，木桶原则取最差）

| 档位 | 判定 | 阈值 |
|---|---|---|
| 🟢 **active** | 绑定会话心跳 ≤ 30 分钟 且 updated_at ≤ 2h | 心跳 30min |
| 🟡 **stale** | 心跳 30min–8h 或 updated_at 2–8h（任一越限） | — |
| 🔴 **orphan** | 心跳 > 8h / 绑定会话已死 / 无绑定且 updated_at > 8h | 8h = 晨割收割线 |
| ⚪ **unbound** | 任务创建后从未绑定会话（Trae 裸奔类）——单列提醒补心跳 | — |

**与晨割 v2 对接**：orphan 即晨割"无人负责"的系统定义。晨割从"自己算时间"升级为"直接按 `activity=orphan` 查询收割"；unbound 是 Trae 类违规的雷达。

## 六、风险与回滚

| 风险 | 缓解 | 回滚 |
|---|---|---|
| 老会话心跳缺失被误判 orphan | orphan 仅展示，**不自动改任务状态**——收割仍由晨割显式 task-close | 纯派生字段，前端不读即等于回滚 |
| 阈值拍脑袋（30min/2h/8h） | 环境变量 `EV_ACT_TH_*` 可调，跑一周再固化 | 改环境变量即调参 |
| ev.js 单文件 2106 行改挂 | 纯函数独立 + 每阶段 node --check + 独立 commit | git revert 单 commit |
| Trae 无心跳 → unbound 误报 | unbound 只是提醒档；配合 .trae/rules 补丁（95881e8）逐步收敛 | 不影响主流程 |
