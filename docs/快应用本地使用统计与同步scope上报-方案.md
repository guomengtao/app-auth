# 快应用本地使用统计 + 同步 scope 上报 实施方案（v2 · 设备身份锚点版）

> 2026-11-08 · 需求来源：用户使用时长/频率无法统计（手环无网，同步器只是短窗口）
> v2 增补（用户 11-08 19:16 定调）：**以 MAC / Node ID 为不变锚点**，先解决"这台手环装过几次、
> 什么时候开始用"，再做每日使用细化；全程**保守、轻量、向下兼容**，不得影响激活与打开速度。
>
> **结论先行**：不用新建通道。快应用已在用 `@system.storage`，同步器已有「域白名单」同步协议。
> 只要 ①手环端本地记账（`usage` 只读域）②手机端把 `MAC + nodeId + 本地 usage` 绑在一起上报，
> 就能得到**跨重装、跨重置、跨换机都不丢**的长期曲线。

---

## 0. 三条硬约束（先立规矩，再谈功能）

| # | 约束 | 具体落地 |
|---|---|---|
| 1 | **不影响激活** | `usage` 全部逻辑与 `activate` / `zero:` / 授权链路零交叉；任何异常 try/catch 吞掉，绝不上抛 |
| 2 | **不影响打开速度** | 记账只在 `onInit` 之后异步执行；一次 `storage.get` + 一次合并 `storage.set`；首屏渲染不等存储回调 |
| 3 | **向下兼容** | 老固件无 `usage` 域 → 请求无回包不报错；老 APK 不请求 → 数据只在手环本地躺平；字段一律"有则报、缺则省" |

## 1. 设备身份锚点（本次的核心）

### 1.1 三层标识，分工不同，绝不能混用

| 标识 | 来源 | 生命周期 | 权限 | 用途 |
|---|---|---|---|---|
| **BLE MAC** `04:34:C3:06:B8:85` → `0434C306B885` | 系统蓝牙 bonding 列表（`DeviceProbe`） | **出厂烧录，跨重装/重置/换机稳定** | Android 12+ 需 `BLUETOOTH_CONNECT` | **首选锚点**：认"这台手环" |
| **nodeId** `2239421161` | 小米穿戴服务 SDK `Node.id` | **跨重装/重置稳定**（11-04 实证） | 无 | **次选锚点**：MAC 缺权限时兜底 |
| **install_id** `apk-8fcb219d` | APK 本地 `UUID.randomUUID()` 前 8 位 | **每次重装/清数据都变** | 无 | **只用来数"装过几次"**，绝不当身份 |
| 手环 deviceId `2b081f25…4B91` | 手环 `get_device_id` | **重置就变** | 无 | 只做"码内设备段校验"，**统计不用它做身份** |

> 这套分工在 `DeviceProbe.java:15-28` 已有注释确认，本方案只是把它用到统计上。
> ⚠️ 历史坑：`0.5.101` 及之前把 nodeId 当 deviceId 上报过，服务端归一时要能识别（见 §6.4）。

### 1.2 锚点归一规则（唯一口径）

```
anchor = "mac:" + mac12u          // mac12u = 12 位大写无分隔，来自 DeviceProbe.normalizeMac
       : "node:" + nodeId         // MAC 拿不到（无权限 / 随机地址 / 未配对）
       : "iid:" + install_id      // 两者全缺，降级（极少见，需打标）
```

- 三档同时上报原始字段，**服务端也存原始值**，策略变了可以重算，不用回刷客户端。
- `macRandom=true`（Android 给未授权应用的占位 `020000000000` 或随机地址）时，**不采用 MAC**，回落 nodeId。`DeviceProbe` 已算好这个标记，直接透传。
- 一只手机连多只手环 → 每个 `(anchor, nodeId)` 组合各算一台；换手机但手环没换 → anchor 不变，历史自动接上。

### 1.3 手环端的限制（必须承认）

手环快应用**没有蓝牙权限，拿不到 MAC 和 nodeId**。所以：

- 手环端只负责"我自己的账"（首次启动、打开次数、每日页面访问）+ 报自己的 `deviceId`；
- **身份锚点由手机端补齐**：上报时把 `(anchor, watchDeviceId, usage)` 绑成一条，MAC/nodeId 一进来，锚点就永久稳定。

这正好解决最痛的场景：**手环重置 → deviceId 变了、本地 usage 被清空 → 只要 MAC/nodeId 还在，服务端就能认出"还是那台手环"，并把历史串起来。**

## 2. 为什么必须在手环端本地累计（实测依据）

同步器窗口太短，不足以承载「使用频率」这种长期指标。取全库 116 个同步器安装实例的**最新累计值**：

| 指标 | 中位 | 均值 | 头部 |
|---|---|---|---|
| 存活（first_install → last_open） | **0.08 天（≈2 小时）** | 4.7 天 | 最长 42.8 天 |
| 前台时长 | **6.5 分钟** | 31.5 分钟 | 最长 777 分钟 |
| 打开次数 | **2 次** | 7.4 次 | 最多 127 次 |

- 47%（54/116）的安装在**1 小时内**就不再打开；只有 22%（25 个）留存超过 7 天。
- 典型误判：用户 `爱发电用户_rYcX` 2026-09-18 就已在用课程表，同步器 `first_install` 是 **11-08 15:28** — 偏差 **51 天**。
- 全站可匹配 48 个用户，同步器安装晚于首次激活 7 天以上的只有 4 个 —— 说明**绝大多数人在"临门一脚"才装同步器**，前期使用全在盲区。

**推论**：`first_install`（同步器安装）≠ 首次使用课程表。唯一正解是**手环端自己记账，等同步器出现时一次性带回**。

## 3. 目标与非目标

**目标**
1. **安装次数**：同一只手环（anchor）装过几次课程表/同步器（`distinct install_id`）。
2. **首次使用时间**：手环上课程表第一次启动的时刻，跨重置不后移（服务端取 min）。
3. **每日使用**：每天有无使用（60 天位图）、每天打开几次、每天访问了几个页面。
4. **时长**：前台累计毫秒（心跳法，±1 分钟；实现复杂，放 P2）。
5. 全程走现有同步链路，不要求手环联网、不新增服务端接口。

**非目标**
- 不做实时在线统计（手环无网，只能"下次同步补传"）。
- 不采集课程内容、课程名、联系人等隐私数据；页面统计只存**页面码计数**，不存参数。
- 不改授权/门禁逻辑（`usage` 域永远只读）。

## 4. 数据模型（手环端本地）

### 4.1 存储位置与体积

- 单键：`ev_usage_v1`，值 JSON 字符串。键名带版本，便于结构升级时并存迁移。
- 满配体积实测预算：**< 700 字节**（含 60 天位图 + 14 天 PV + 7 天页面分布）。
- 写入策略：**只在有变化时写**；一次记账合并为**一次 `storage.set`**。

### 4.2 字段定义

| 字段 | 类型 | 含义 | 写入时机 |
|---|---|---|---|
| `v` | int | 结构版本，当前 `1` | 初始化 |
| `firstInstallTs` | int64 | **首次启动时刻**（ms）= 课程表安装时间 | 仅当为空时写，**永不覆盖** |
| `firstInstallVer` | string | 首次启动时的版本号 | 与 `firstInstallTs` 同写 |
| `lastOpenTs` | int64 | 最近一次进入前台（ms） | 每次 `onShow` |
| `openCount` | int | 累计启动次数（全量） | 每次 `onShow` +1 |
| `activeDays` | int | 累计有打开的天数（全量） | 当天首次点亮时 +1 |
| `dailyDay0` | int | 位图第 0 位对应本地日期 `YYYYMMDD` | 首次写入 / 滚动时 |
| `dailyBits` | string | 近 60 天活跃位图（60bit → 15 位 hex） | 每次点亮当天位 |
| `pvDay0` | int | PV 数组第 0 天日期 `YYYYMMDD` | 首次写入 / 滚动时 |
| `pv14` | string | **近 14 天每日页面浏览数**，逗号分隔，如 `12,8,0,5,…` | 每次记账 |
| `pgDay0` | int | 页面分布第 0 天日期 | 首次写入 / 滚动时 |
| `pg7` | string | **近 7 天各页面访问次数**，如 `1:23,3:11,5:4`（页面码:次数，只留 top6） | 每次记账 |
| `fgMs` | int64 | 累计前台毫秒（心跳法，P2） | 每满 1 分钟 +60000 |
| `maxStreak` | int | 最长连续活跃天数（P2 可选） | 每日首次点亮时 |

### 4.3 每日活跃位图（原有设计，不变）

- 固定 **60 天滚动**，每天 1 bit，`dailyDay0` 记第 0 位日期；60 天曲线只占 15 字符。
- `openCount` / `activeDays` 是**全量累计**，不被滚动窗口吃掉 → 长期频率与近期曲线兼得。
- 跨天判定用**手环本地时区日期**（`getFullYear/getMonth/getDate`），不用 UTC（否则东八区凌晨错一天）。
- 点亮幂等：当天位已置 1 不再加；`activeDays` 只在 0→1 那次 +1。

### 4.4 每日页面访问怎么记（本次新增）

**页面码表**（固定映射，只增不改，新增页面往后追加）：

| 码 | 页面 |
|---|---|
| 1 | 课表主页 |
| 2 | 设置 |
| 3 | 外观/主题 |
| 4 | 课程详情 |
| 5 | 关于/版本 |
| 6 | 授权/激活页 |
| 7 | 其他（兜底） |

- **一次页面进入 = `pv14[今天] + 1`**，同时 `pg7[页面码] + 1`。
- 只记次数，**不记停留时长**：停留需要页面级心跳，成本远高于收益，放 P2。
- `pg7` 只保留次数最高的 6 个页面码，防止键无限膨胀；总量守恒（丢弃的进码 7）。
- 体积上限：`pv14` ≈ 56 字节，`pg7` ≈ 45 字节。

### 4.5 前台时长 `fgMs`（P2，先不做）

快应用没有可靠"退出"回调，用**心跳法**：进入前台起 60s 定时器，每次触发 `+60000`；切后台清定时器；单会话上限 4 小时防漂移。精度 ±1 分钟。
**P1 不实现**——先保证"每天用了几次、看了几页"这两项，收益/风险比更高。

## 5. 快应用侧改动点（`class-schedule/src/app.ux`）

### 5.1 新增 `usage` 域（三处，均为"加几行"）

**(1) 白名单** — `SYNC_ACCESS`（约 :585）：

```js
usage: { read: "explicit", write: false },  // 使用统计：只读，须插件显式请求
```

选 `explicit` 而非 `always`：默认导出不带，避免每次同步多传一段数据。
`write: false` 是硬约束 —— `SYNC_FIELD_DOMAIN` 里**不要**加任何 `usage` 字段，从机制上写不进去。

**(2) 域清单** — `SYNC_ALL_SCOPES`（约 :615）：

```js
var SYNC_ALL_SCOPES = ["schedule","profile","homepage","appearance","version","pinned","auth","usage"]
```

**(3) 收集分支** — `syncCollectScopes()`（约 :690，与 `auth` 分支同构）：

```js
if (syncWantScope(list, "usage")) {
  pending++
  usageStore.get(function (u) {
    result.usage = u || {}
    finish()
  })
}
```

⚠️ 必须遵守既有 `pending++ / done++ / registered` 计数协议，`finish()` 只能调一次，否则提前回包只带部分域（**高危**，见 §8）。

### 5.2 采集钩子位置

| 时机 | 动作 | 成本 |
|---|---|---|
| `onInit` 之后（**首屏渲染后**） | 读 `ev_usage_v1`；`firstInstallTs` 为空则写（含版本号）；记账一次 | 1 次 get + 1 次 set |
| `onShow`（每次进前台） | `openCount++`、`lastOpenTs`、点亮当天位 | 合并在同一次 set |
| 每次页面路由切换 | `pv14` / `pg7` 对应页面码 +1 | 同上（合并写） |
| 60s 心跳 | `fgMs += 60000`（P2） | — |

**铁律**：任何情况下不得重置 `firstInstallTs`、`openCount`、`activeDays` —— 只有"手环本地数据被物理清空"（重置/换装）才会丢，属真实事件，应如实反映；跨重置的历史由服务端靠 MAC/nodeId 串回来。

### 5.3 性能红线（用户明确要求）

- 记账函数**整体包在 try/catch 里，异常静默**；不 `console.error` 刷日志。
- **不在 `onInit` 同步路径里读存储**：现有 `app.ux:1132` 已有"版本一致时只有 1 次 `storage.get`"的优化，新增逻辑必须复用同一次读，不额外开通道。
- 路由切换只改内存对象并打脏标记，`set` 由已有的合并写方法在**同一 tick 或下次进入**统一落盘，禁止每切一页写一次。
- 不新增任何权限、不新增任何网络请求。

## 6. 手机端（同步器 APK）改动点

### 6.1 请求 `usage` 域

同步时 `scopes` 追加 `"usage"`。`explicit` 策略下不请求就不返回，这步必须做。
**开关放在手机端**：老固件 / 出问题时，不下发请求即可完全停用，手环侧零改动 —— 这是最保守的灰度手段。

### 6.2 上报身份锚点（本次最关键、也最小的一步）

`Stats.fillWatch()` 里补两个字段（数据 `DeviceProbe` 已现成，**不用新写探针**）：

| 埋点字段 | 来源 | 缺失时 |
|---|---|---|
| `watch.mac` | `DeviceProbe.Result.mac`（12 位大写 hex） | 省略该字段 |
| `watch.mac_random` | `DeviceProbe.Result.macRandom` | 省略 |
| `watch.node_id` | `SyncEngine.getNodeId()` / `DeviceProbe.nodeId` | 省略 |

> 现状确认：**MAC 目前只在激活/支付请求里以 `deviceKey` 传，从未进过访客埋点**，所以服务端现在算不出"装过几次"。这一步是纯增量。

### 6.3 usage 随埋点平铺上报

在 `device` 对象上平铺新增（不建嵌套，便于 SQL 直查）：

| 埋点字段 | 来源 |
|---|---|
| `u_first_install_ts` / `u_first_install_ver` | `usage.firstInstallTs` / `.firstInstallVer` |
| `u_open_count` / `u_active_days` / `u_last_open_ts` | 同名 |
| `u_daily_day0` / `u_daily_bits` | 位图 |
| `u_pv_day0` / `u_pv14` | 近 14 天每日 PV |
| `u_pg_day0` / `u_pg7` | 近 7 天页面分布 |
| `u_fg_ms` / `u_ver` | P2 / 结构版本 |

### 6.4 兼容与归一（老固件、老 APK、历史脏字段）

- 老快应用无 `usage` 域 → `result.usage === undefined` → **整块不上报**，绝不回填 0/null（否则"老固件"与"从未使用"混为一谈）。
- 老 APK 不请求 `usage` → 手环本地照常记账，只是没上报；将来升级 APK 自动补全历史，**不丢**。
- `0.5.101` 及之前把 nodeId 当 `deviceId` 上报过 → 服务端识别：纯数字 9~10 位 = nodeId，32 位 hex = deviceId，分别归位，不要混进同一列。

## 7. 服务端落库与统计口径

### 7.1 落库

`visitor_logs.device` 是 jsonb，**零迁移**容纳上述字段；`tracking_events.payload` 同理。

### 7.2 四个必须区分的时间

| 名称 | 来源 | 含义 |
|---|---|---|
| `first_install` | APK 自报 | **同步器**安装时间（语义不变） |
| `u_first_install_ts` | 手环端 | **课程表首次启动** ← 真正想要的 |
| `auth_ts` | 服务端激活记录 | 首次付费激活时间 |
| `anchor_first_seen` | 服务端 min(ts) by anchor | **这台手环第一次出现在我们视野里** |

### 7.3 核心口径

- **安装次数**：`count(distinct device->>'install_id') group by anchor` —— 重装几次就有几个；同一 anchor 多手机也计入（口径标注"安装实例数"）。
- **首次使用时间**：`min(u_first_install_ts)` by anchor，**绝不用最新值覆盖**（重置会让本地归零）。
- **DAU 还原**：取每设备最新 `u_daily_bits` 展开成日期集合按日聚合（补传口径，天然滞后，报表标注）。
- **日均 PV**：`u_pv14` 求和 / 非零天数；**页面偏好**：`u_pg7` 全站累加 → 页面码排行。
- **日活率**：`u_active_days / (今天 - u_first_install_ts)`；**日均打开**：`u_open_count / u_active_days`。

### 7.4 白嫖时长（这次最想回答的问题）

`auth_ts - u_first_install_ts` 为负 → 用户**先用了 N 天才付费**（正是「用了一段觉得好用才买」那批人）。此分布出来，运营和定价才有依据。

## 8. 边界与坑（都会踩）

| # | 场景 | 处理 |
|---|---|---|
| 1 | **手环重置/恢复出厂** | 本地清空，`firstInstallTs` 会变成重置那一刻 → 服务端取 min；靠 `mac`/`node_id` 把前后串成同一台 |
| 2 | **重装 APK** | `install_id` 变、anchor 不变 → 安装次数 +1，身份不散 |
| 3 | **换手机但手环不变** | anchor 不变，历史接上；`install_id` 新增一条 |
| 4 | **换手环** | anchor 变 → 真实新设备，各算各的；需要合并时人工用 nodeId 关联 |
| 5 | **MAC 拿不到**（无 `BLUETOOTH_CONNECT` / 随机地址 / 未配对） | 回落 nodeId；两都缺才用 `iid:` 降级并打 `anchor_level=3` 标记 |
| 6 | **版本升级** | 键名带版本，新增字段走"读旧→补默认→写新"，**禁止**清空重来 |
| 7 | **时区** | 位图/PV 按手环本地日期；服务端不跨时区校正 |
| 8 | **storage 写失败 / JSON 损坏** | 静默丢弃本次记账（不重建、不清零），下次启动正常继续；**绝不 throw** |
| 9 | **`explicit` 忘了请求** | 数据恒为空且无报错，最难查 → 联调必须先验证 `result.usage` 非空再放行 |
| 10 | **`syncCollectScopes` 计数错乱** | 漏 `pending++` 会导致回包只含部分域，进而覆盖手机端课表（**高危**，必须跑单测） |
| 11 | **页面码表扩容** | 只追加、不复用旧码；码 7 为"其他"，永不复用为具体页面 |
| 12 | **服务端白名单会把新字段丢掉**（2026-11-08 实测踩到） | `api/activate.js` 的 `sanitizeDevice()` 是**白名单**，只挑认识的字段返回。APK 新增 `watch.mac` 后，服务端必须同步加 `watch_mac` / `watch_mac_random`，否则**发了也被丢弃、且无任何报错**。任何新增埋点字段都要两头改 |

## 9. 分期落地（先能看，再精修）

| 阶段 | 内容 | 改动面 | 风险 | 验收 |
|---|---|---|---|---|

**建议顺序：P0 单独先发**。它不碰快应用、不影响启动、20 行代码，就能立刻回答"这只手环装过几次、是不是老用户重置回来的"。P1 再随时跟上（本地记账对用户完全不可见，出问题也只是少一份数据）。

## 附：与「重复下单」问题的关系

`rYcX` 的 51 天盲区、以及零配激活（`zero:devkey:*` MAC 记忆）**全库只有 1 台设备登记**，指向同一结论：
**手环端不自己记账、MAC 不进埋点，服务端就永远只能看到"用户买的那一刻"，看不到"用户用了多久、装过几次"。**

本方案 P0 落地后，「装过几次 / 是不是重置回来的老用户 / 用了多久才买」这三个问题立刻有答案，且不依赖任何快应用版本升级。
