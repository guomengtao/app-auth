## 五、数据源一致性检查（Postgres / Redis / Supabase / data/*.json）

### 5.1 四处数据源现状

| 数据源 | 角色 | 一致性风险 |
|---|---|---|
| **Upstash Redis** | 运行时读写主力 + 存放主库开关 `auth:db:primary` | 与 PG 之间靠定时同步，存在窗口期 |
| **Neon / Vercel Postgres** | 持久化主存储（受 `lib/redis.js` PG 路径代理） | 若 primary 指向 Supabase 且被禁用 → **split-brain（P0-10）** |
| **Supabase** | 备用库 | 若数据陈旧，被 `force-sync`/`clean-orphans` 当作源会覆盖新数据 |
| **`data/*.json`** | **示例/种子数据，运行时不读取**（后端无 `require`/`readFileSync`） | 无 serverless 只读 FS 问题；但 `admin_Dx23.html:4561-4571` 会用它 seeding localStorage，管理员可能误以为是真实数据 |

### 5.2 同步 / 备份脚本风险评级

| 脚本 | 方向 | 护栏 | 评级 |
|---|---|---|---|
| `clear-db.js` | 删除 Upstash 全部 `auth:*` | 无 | ☠️ **危险**（含 `auth:db:primary` 与全部备份） |
| `force-sync.js` | Supabase → Neon，**先 `DELETE` 目标全表再拷贝** | 无 | ☠️ **危险** |

### 5.3 Cron 并发与幂等

`vercel.json:9-22` 定义 03:00 拉单 / 04:00 备份 / 05:00 同步，三者按小时错开**本身不重叠**，但：

- **无任何互斥锁**：手动「Run now」或 Vercel 超时重试会启动第二个实例，两个实例并发执行孤儿清理 → 互相删除对方刚写入的键。
- **无失败重试**：`health.js:2000-2005` 即使 `errors > 0` 也返回 `success:true`，失败静默。
- `query-orders.js:396` 在部分失败时仍推进 `afdian:last_sync`，会**永久跳过失败批次**（漏发兑换码）。
