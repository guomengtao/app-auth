## 一、本轮结论摘要

**一句话**：用户侧的付费激活主链路本身是通的（校验、限流、重复占用、错误文案均正确），**真正的重灾区在后台管理端——默认模式下后台大面积不可用，且兑换码的删除功能全线失效**；另有若干运维脚本会**静默抹除已付款数据**。

**五个必须先看的风险**：

| # | 结论 | 影响 |
|---|---|---|
| 1 | **默认模式（local-first）下「激活记录」表格永远空白** | 管理员登录后看不到任何激活记录，且提示语永久停留在"正在更新" |
| 2 | **默认模式下 7 类写操作被拦、快捷激活整块不初始化** | 新建产品 / 生成兑换码 / 删除 / 批量导入全部弹红 toast 拒绝 |
| 3 | **删除兑换码功能 100% 失败**：单条删除与批量清理调用的后端接口**根本不存在** | 兑换码只能增不能删，管理员会反复重试 |
| 4 | **`scripts/clear-db.js` / `force-sync.js` / `clean-orphans.js` 无护栏** | 一次误执行即清空全部 `auth:*`，已付款激活记录不可恢复 |
| 5 | **Webhook 无签名即放行** | 任意人可伪造爱发电回调自动刷出真实兑换码（资损） |
| 6 | **新增的 Mac 通知器会丢消息**（一次 read 多条只处理第一条；去重键不含订单号） | 漏通知 = 付了钱没人知道，已实测复现 |

> 说明：第 5 条属安全类，按你定的优先级排在 P4，但其后果是**付费权益被白嫖**，建议在排期上提到 P0 一起处理。

## 二、P0 · 用户操作直接受影响的功能 Bug

### P0-1 【已核实】默认模式下「激活记录」表格永远空白，且提示语永久卡住

**复现步骤**
1. 浏览器首次打开后台 `admin_Dx23.html` 并完成登录（默认 `ADMIN_MODE` 为 `local-first`）
2. 点击左侧「激活记录」

**期望结果**：显示筛选栏 + 激活记录表格。
**实际结果（推断）**：表格区域**一片空白**，顶部提示永久停在 `📴 本地缓存模式，后台正在从服务器更新...`，之后即使服务端数据成功返回也不会刷新。

**定位（关键链路）**
| 位置 | 代码 | 问题 |
|---|---|---|
| `admin_Dx23.html:4355` | `var ADMIN_MODE = 'local-first'; // local-first: default` | 默认就是本地优先模式 |
| `admin_Dx23.html:5879` | `renderRecordsTable(localRecs, highlightRc, highlightAc, true, null, rc);` | **返回值被丢弃**，未赋给 `#recordsTable` |
| `admin_Dx23.html:5880` | `fetchAndCacheRecords(pid, rc, status, deviceId, ip);` | 后台异步拉取 |
| `admin_Dx23.html:5834` | `renderRecordsTable(filtered, null, null, true, null, rc);` | **服务器数据回来后返回值同样被丢弃** |
| `admin_Dx23.html:6080` | `return tableHtml;` | 该函数内部**不做** innerHTML 赋值，只返回字符串 |
| `admin_Dx23.html:5949` | `document.getElementById('recordsTable').innerHTML = html;` | 全局唯一的赋值点，但位于**非 local-first 分支**（`api-always`） |

**对照证明这是遗漏而非设计**（同一文件内另外两个列表的写法完全不同）：
- 产品表：`admin_Dx23.html:5308`、`:5334` → `renderProductsFromLocal` / `renderProductsFromApi` **内部各自完成** `productsTable.innerHTML = html`
- 兑换码表：`admin_Dx23.html:5476` → `renderCodesTable` **内部完成** `codesTable.innerHTML = html`
- 唯独激活记录把赋值交给外部调用方，而 local-first 的两次调用都没接住返回值

**严重度**：严重　**影响端型**：全部（Web 后台）
**修复建议**：在 `:5879` 与 `:5834` 两处改为 `document.getElementById('recordsTable').innerHTML = renderRecordsTable(...)`；或统一把赋值移进 `renderRecordsTable` 内部，与其他两个列表写法保持一致。

### P0-2 【已核实】默认模式下 7 类写操作被拦截、快捷激活面板不初始化

**定位**
```js
// admin_Dx23.html:4395-4401

  if (ADMIN_MODE !== 'api-always') {
    showToast('❌ 当前为本地缓存只读模式，请先切换为「线上模式」再进行' + (actionName || '操作'), 'error');

```

被拦住的入口（全部走 `ADMIN_MODE === 'local-first'` 分支）：
| 操作 | 行号 |
|---|---|
| 添加 / 编辑产品（`submitProduct`） | `:6196` |
| 删除产品 | `:6246` |
| 生成兑换码 | `:6293` |
| 删除兑换码（单条） | `:6325` |

**实际结果（推断）**：管理员登录进来后，产品增删改、兑换码生成与删除、批量导入全部弹同一个红 toast 要求"先切换为线上模式"；快捷激活面板因为 `initDirectActivate` 直接 return，产品列表不加载，看起来就是"功能坏了"。

### P0-3 【已核实】删除兑换码功能 100% 失败——后端根本没有这两个接口

前端调用 vs 后端实现（全量比对前端所有 `/api` 调用点后的结果）：

| 前端调用 | 行号 | 后端是否存在 | 结果 |
|---|---|---|---|
| `DELETE /api/admin/redeem-codes/{code}`（单条删除） | `:6328` | ❌ `api/admin/` 下无 `[code].js`；`redeem-codes.js` 只实现了 `GET`(`:116`) 与 `POST`(`:152`)，**无 DELETE 分支** | 路由 404；即使命中也落到 `:236` 的 `405 Method not allowed` |
| `POST /api/admin/redeem-codes/purge`（批量清理） | `:6352`、`:6368` | ❌ 全仓 `api/` 无任何 `purge` handler | 404 |

**实际结果（推断）**：单条删除会走 `:6336` 的 `showToast('删除失败','error')`；批量删除同理失败。兑换码**只能新增，永远删不掉**。

**对照**：产品删除是正常的 —— `api/admin/products.js:117` 有完整 DELETE 实现，`:119` 读取 `delBody.id` 或 `req.query.id`。可见是 redeem-codes 模块漏实现，而非整体设计如此。

**严重度**：严重　**影响端型**：全部（Web 后台）
**修复建议**：在 `api/admin/redeem-codes.js` 中补 DELETE 分支（解析路径或改前端发 `{id}` body），并新增 `api/admin/redeem-codes/purge.js`；同时建议给所有 CRUD 列举出接口清单做一次对账。

### P0-4 【已核实】`api/activate.js` 激活写入非原子，可能"扣了配额却没落库"

```js
// api/activate.js:404-411
await Promise.all([
  redis.set("auth:redeem:" + code, JSON.stringify(updated)),
  redis.set("auth:activation:" + activationCode, JSON.stringify(record)),
  redis.sadd("auth:activation_codes", activationCode),
  redis.set("auth:device:" + deviceHash, activationCode),
  redis.incr(USED_COUNTER_KEY).catch(function () {}),
]);
```

五条写操作彼此独立，任一失败都会造成半成品状态（例如兑换码已标记 `used=true`，但激活记录未写入 —— 用户**兑换码作废了却拿不到激活码**，且第二次兑换同一码会被"已被使用"拒绝，形成死局）。

值得肯定的是 `lib/redis.js:477` 已经实现了带事务的 `setWithSadd`（BEGIN/COMMIT/ROLLBACK），但本链路没有使用。

**严重度**：严重　**影响端型**：全部　**修复建议**：改用 `setWithSadd` 或把五条写入包进同一事务。

### P0-5 【已核实】爱发电 Webhook 无签名即放行，可任意刷兑换码

```js
// api/afdian/webhook.js:41-54
if (sign) {
  var valid = afdianSign.verifyWebhookSignSimple(signStr, sign);
  if (!valid) { return res.status(200).json({ ec: 200, em: "sign_verify_failed" }); }
} else {
  console.log("[afdian:webhook] no sign provided, skipping verification");
}
var result = await afdianProcessor.processOrder(order);   // :57 直接发货
```

只要请求体里不带 `sign` 字段，校验被整段跳过。
另外 `:63` 的异常分支同样返回 `{ ec: 200 }`，爱发电会认为投递成功不再重试 —— 内部实际失败时**没有任何告警**，用户付款后拿不到码且无人知晓。

**严重度**：致命（资损）　**影响端型**：服务端　**修复建议**：无 `sign` 一律 400 拒绝；异常分支返回非 200 以触发平台重试并接入告警。

### P0-6 【已核实】运维脚本无护栏，可静默抹除全部已付款数据

| 脚本 | 位置 | 问题 |
|---|---|---|
| `scripts/clear-db.js` | `:9-22` | `redis.scan({ match: "auth:*" })` + `redis.del(...keys)` 循环清库。**无环境判断、无二次确认、无 dry-run**，只要环境变量指向生产就会清空全部激活/兑换数据 |
| `scripts/force-sync.js` | `:41-44` | `DELETE FROM kv_strings / kv_hashes / kv_sets / kv_zsets` 先清空目标库（Neon）再全量灌入源库（Supabase）数据，**无事务包裹**；源库若陈旧或不完整，新数据被直接覆盖丢失 |
| `scripts/clean-orphans.js` | `:48-82` | "孤儿"判定 = 目标库有而源库无 → 直接 DELETE。若目标库才是生产主库而源库是陈旧备份，**生产有效数据会被误删** |

**方向冲突（额外风险）**：`force-sync.js:37` 是 **Supabase → Neon**，而 `scripts/_run-sync.js:75-76`、`scripts/setup-supabase.js:70` 是 **Neon → Supabase**。同一仓库内两套脚本方向相反，手工跑错一个就把新数据覆盖成旧数据。

**失败静默**：`scripts/upstash-to-postgres.js:169-172` 单键错误被 catch 后继续，`:186-191` 仍 `process.exit(0)`；`backup-to-upstash.js`、 `sync-all-dbs.js:698-705` 同类。**Cron 永远判定同步成功**，差异会持续扩大而不被发现。

**严重度**：致命（资损）　**影响端型**：服务端/数据
**修复建议**：给 `clear-db.js` 加 `NODE_ENV==='production'` 拒绝 + `--confirm` + dry-run；同步类脚本改为 upsert + 临时表 rename；统一同步方向常量；错误数 > 0 时 `process.exit(1)`。

## 七、本轮新增提交专项：Mac 原生通知器（`tools/ev-notifier/`）

本轮期间作者新增了这个组件（提交 `2472012` / `8eb8281`），它订阅 Upstash Pub/Sub 频道 `auth:push_channel`，把「兑换码被激活」「新订单」「激活失败」事件弹成 macOS 系统通知。**这是付费订单的实时监控通道 —— 它丢消息，就意味着"用户付了钱但没人知道"**，因此按 P0 处理。

### P0-7 【已实测】Redis 协议解析器会丢消息：一次 read 拿到多条消息时只处理第一条

`tools/ev-notifier/ev_notifier.py:81-110` 的 `parse_redis_reply()` 每次只返回**第一个** reply，且**没有跨 read 累积缓冲区**。而 `:323` 的 `reader.read(8192)` 在 TCP 层面完全可能：
- **一次返回多条消息**（并发事件同时到达，订阅场景极常见）
- **一条消息被拆成两次 read**（payload 较大时）

**实测结果**（复刻该函数 + 构造真实 RESP 报文）：

| 场景 | 输入 | 解析结果 | 后果 |
|---|---|---|---|
| 两条消息合并到达 | `*3 message ...(ts=1)` + `*3 message ...(ts=2)` | 只解析出 `ts=1` | **第二条静默丢失** |
| 单条消息被拆包 | 前半 `$120\r\n{"ts":3,"type":"new_act` + 后半 `ivation",...}` | 第一次得到**残缺 JSON** → `json.loads` 失败 → `:334 continue` 丢弃；第二次得到 `None` | **整条消息丢失** |

**严重度**：严重（漏通知 = 漏订单）
**修复建议**：改成标准的「缓冲区累积 + 按 RESP 长度前缀切分」解析（维护一个 `bytearray`，每次 append 新数据后循环解析完整 reply，剩余部分留在 buffer 里），并让解析器返回**列表**而非单条。

---

### P0-8 【已实测】去重 key 设计错误，同毫秒同类型的第二条事件被当重复丢弃

```python
# tools/ev-notifier/ev_notifier.py:196
mid = f"{ts}_{mtype}"
if mid in _seen_ids:
    return          # 直接丢弃
```

去重键只用了「时间戳 + 事件类型」，**不含订单号 / 兑换码 / 激活码**。

**实测结果**：两笔不同订单（`out_trade_no` 分别为 A1、B2）在同一毫秒到达时，第二笔被判定为重复 → **通知被丢弃**。批量激活（后台一次直开多个设备）场景下几乎必然触发。

**修复建议**：改为 `f"{ts}_{mtype}_{out_trade_no or activation_code or redeem_code}"`。
