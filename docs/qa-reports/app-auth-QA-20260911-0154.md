## 五、数据源一致性

**四处数据源**：Postgres（Neon / Supabase 双库）、Upstash Redis、`data/*.json`、`db-registry.json`。

- **实际生效的数据源**：`lib/redis.js:7` —— 当 `USE_UPSTASH=true` 或主库为 upstash 时用 Upstash REST；否则用 Postgres 上的 `kv_strings/kv_hashes/kv_sets/kv_zsets` 四张表做 KV 模拟。**即「Redis」这一层实际是二选一，不是并存的双写**。
- **是否会导致用户激活状态错乱**：**当前不会**。理由：
  1. 激活写入走 `redis.pipeline()` 原子提交（`api/activate.js:395-411`），双键 `auth:activation:*` + `auth:device:*` 同批写；
  2. 客户端是**离线校验激活码**，不读服务端 → 服务端数据即使短暂不一致，也不影响已激活用户；
  3. 本轮 P0-10 已修（`:1284` 禁止禁用主库），split-brain 的主要触发路径已封死。
- **残留风险**：`?cron=1` 未鉴权（P0-S-1）可被人触发 `section=sync`，用 A 库覆盖写 B 库。这是**唯一**还能造成激活数据错乱的路径，已按 P0-S 提级。
- **`data/*.json`**：为静态种子数据，不参与运行时读写，无覆盖写风险。
- **sync/backup 脚本覆盖写**：`scripts/clear-db.js`、`scripts/force-sync.js` **本轮已加护栏**（`NODE_ENV=production` 拒绝执行 + 必须带 `--confirm` + 交互式输入 `YES_DELETE_ALL`），P0-6 确认修复 ✅。
