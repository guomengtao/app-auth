## 一、本轮结论摘要

> **一句话**：上轮 4 条待办作者修了 3 条（cron 401、解绑入口、ES6 化），**但 ES6 化的那次修改把激活页改坏了——现在所有端型点「立即激活」都会卡在「激活中...」永不显示激活码，线上已复现。这是本轮唯一需要立刻止血的问题。**

三条关键风险：

1. **P0-16（新，线上已复现）**：`activate.html` 手搓的 thenable 对象只有 `.then` 没有 `.catch`，`activate()` 调用链 `.then(...).catch(...)` 同步抛 `TypeError` → 按钮永久禁用在「激活中...」，激活码永不展示。**服务端其实已经激活成功**（作者侧照样收到通知），用户侧完全无反馈 —— 极其迷惑的"静默成功"。
2. **P0-15（沿用，仍需作者确认）**：`CRON_SECRET` 是否在 Vercel 配好，决定每日 04:00 备份 / 05:00 同步是不是一直在 401 空转。静态无法判定，仓库里也没有任何配置文档。
3. **P1-13（文档 vs 代码）**：用户手册教用户"换新手环直接用同一个兑换码重新生成"，代码实际上是**直接拒绝**。换设备的用户 100% 撞墙，而错误文案让他"联系作者"却全站找不到任何联系方式。

P0 共 2 条（1 新 1 待确认），P1 共 5 条。**没有新增 P0-S**。

### P0 — 用户用不了

#### P0-16 ｜ 激活页点「立即激活」永久卡在「激活中...」，激活码永不显示（本轮新引入回归）

| 项 | 内容 |
|---|---|
| 优先级 | **P0** |
| 模块 | 用户侧 · `activate.html`（最核心页面） |
| 复现步骤（用户视角） | 用手环/手机/电脑打开激活页 → 输入正确或错误的 4 位兑换码 → 点「立即激活」 |
| 期望结果 | 短暂 loading 后显示「激活成功！」+ 18 位激活码 + 复制按钮；失败则显示错误原因 |
| 实际结果（推断 + 线上核实） | 按钮变灰并显示「激活中...」，**再无任何变化**。控制台报 `TypeError: xhrFetch(...).then(...).catch is not a function`。服务端其实已处理完请求（作者侧会收到激活成功/失败通知），但用户看不到任何结果，也无法再次点击（按钮 disabled） |
| 影响端型 | ①②③④⑤ **全部**（与浏览器内核无关，是纯 JS 逻辑缺陷） |
| 严重度 | 致命 —— 核心付费转化链路断在最末端 |
| 定位 | `activate.html:212-213`（`result.then = function(cb){...return result;}` 只挂了 `then`）、`:236`（`return result` 返回裸对象）、`:357-404`（调用链 `.then(...).catch(...)`）、`:410`（`.then(setLoading(false))` 永远到不了） |
| 修复建议 | **方案 A（推荐，一行）**：给裸对象补 `catch` —— `result.catch = function(){ return result; };`，放在 `result.then = ...` 旁边。<br>**方案 B（更彻底）**：直接恢复 `new Promise(...)`。Promise 在 Chrome ≥32 / Android 4.4.4+ 就已原生支持，比手搓 thenable 安全得多；本轮正是因为手写 Promise 替代物漏了方法才出的问题。若担心手环内核，可保留 XHR 但用真 Promise。<br>**建议同时做**：把 `setLoading(false)` 挪进 `xhr.onload`/`xhr.onerror` 内部（而不是靠 Promise 链尾），这样即使以后回调链再出错，按钮也不会卡死 |

## 五、数据源一致性

- **激活状态权威源**：单一 Redis（Upstash）。`api/activate.js:404-410` 用同一 pipeline 写 `auth:redeem:<code>`、`auth:activation:<code>`、`auth:activation_codes`、`auth:device:<hash>`，读取校验同源 → **不存在"激活成功但服务端查不到"**。
- **Postgres / Supabase 备库**：只由 05:00 的 `section=sync` 批量同步，不参与在线读写判定 → 备库落后不会让用户激活状态错乱。
- **结论**：**本轮数据源一致性本身没有问题**。唯一让它升级为 P0 的是 **P0-15** —— 一旦 `CRON_SECRET` 没配，备份与同步同时停摆，主库出问题时既无备份可恢复、备库也是陈旧的。这是本轮唯一的数据源风险点。
- `data/*.json` 仅为本地开发样本，不参与线上链路。

## 八、已知风险 · 不急修（P4，仅记录）

1. **解绑不回收老设备的激活状态**：`api/admin/redeem-codes.js:325-334` 只把兑换码置回 `used:false`，**不删** `auth:activation:<激活码>` 和 `auth:device:<设备hash>`。老设备上的激活码依然有效，新设备又能用同一个兑换码激活 → 一个码可同时供两台设备。损失上限 = 一单。触发条件：用户换机后作者执行解绑。
2. **4 位兑换码空间**：`36^4 ≈ 168 万` 组合，配合 `lib/rate-limit.js` 的 IP/设备限流，爆破成本高于收益。
3. **`section=visit` 端点无鉴权无限流**：`api/admin/health.js:575`，任何人可循环 POST 触发推送通知，效果是作者被通知刷屏，不影响用户激活。

> 按你的定位：以上知道就行，不排期、不进交接本待办。
