### ⚠️ P0-16 ——「部分修」，异常路径仍会卡死（→ 升级为新 P0-21）

作者声明：「thenable 补 `.catch` 属性；`xhr.onload`/`xhr.onerror` 内加 `setLoading(false)` 安全网」。

**复核：正常路径确实修好了，但异常路径仍然卡死。**

`activate.html:219-238`：

```js
xhr.onload = function() {
  var _text = xhr.responseText;
  var res = {
    json: function() { return { then: function(cb) { cb(JSON.parse(_text)); } }; },  // ← 同步抛错
    ...
  };
  for (var i = 0; i < callbacks.length; i++) { callbacks[i](res); }   // ← 抛穿这里
  if (typeof setLoading === 'function') setLoading(false);            // ← 永远到不了
};
```

三个问题叠加：

1. `JSON.parse` 是**同步**抛出，没有 try/catch
2. 抛出点在 `callbacks[i](res)` 循环内 → 直接抛穿 `xhr.onload`
3. `setLoading(false)` 在循环**之后** → 被跳过

**Node 复现实测结果：**

```
正常 JSON 响应                   loading=false  结果=OK
  [抛穿 xhr.onload] SyntaxError: Unexpected token '<', "<html><bod"... is not valid
Vercel 502 HTML 响应           loading=true    结果=null      ← 按钮永久卡死
  [抛穿 xhr.onload] SyntaxError: Unexpected end of JSON input
空响应体                         loading=true    结果=null      ← 按钮永久卡死
```

另注：`activate.html:214` 的 `result.catch = function(cb) { return result; };` 是**空壳** —— 它从不注册回调，所以链上所有 `.catch(handler)` 都是死代码，异常永远静默。

→ **P0-21（新增）**，详见第四节。

## 四、本轮新增 / 复活缺陷

### 🔴 P0-S-1（复活 · 本轮最高优先）— `?cron=1` 绕过后台全部鉴权

| 项 | 内容 |
|---|---|
| **优先级** | **P0-S**（会造成数据丢失 / 用户激活状态错乱，按用户规则提到 P0 顶格，不放 P4） |
| **模块** | `api/admin/health.js` |
| **定位** | `health.js:460`（isCron 判定）、`health.js:577`（鉴权门） |
| **复现（用户视角）** | 任意人在浏览器地址栏输入 `https://app-auth.gudq.com/api/admin/health?section=switch-db&cron=1` —— 无需登录、无需任何 token |
| **期望结果** | 401 Not authenticated |
| **实际结果（线上实测）** | **HTTP 200**，返回完整后台数据；`section` 换成任意受保护栏目同样 200 |
| **影响端型** | 全端（服务端缺陷） |
| **严重度** | 致命 |

**可达的高危动作**（均在 `:577` 鉴权门之后，全部被 `isCron` 放行）：

| section | 行号 | 后果 |
|---|---|---|
| `switch-db` | :1624 | **改主库 → 写 A 读 B → 已付款用户显示未激活** |
| `sync` | :1675 | 触发数据库同步，**可用一份旧数据覆盖新数据** |
| `backup` (GET) | :581 | 读取全部备份，**含所有激活记录** |
| `run-task` | :2179 | 执行任意已配置任务（默认 3 个：afdian-pull / health-backup / db-sync-backup） |
| `cron-tasks` (POST) | :2053, `:2091-2092` | **可新增/修改任务的 `vercelPath` 为任意 URL** → 变相 SSRF |
| `quota` / `dbswitches` / `dbstatus` | :1227/:1269/:1324 | 配置与配额信息泄露 |
| `logs`/`vercel-logs`/`email-logs`/`resend-logs`/`afdian-dm-logs` | :870 起 | 日志泄露 |

**修复建议（二选一，约 5 分钟）：**

- **方案 A（推荐）**：`isCron` 只认 Authorization 头，**删掉 `|| req.query.cron === "1"`**。Vercel Cron 本来就会带 `Authorization: Bearer $CRON_SECRET` —— 当初 P0-15 的 401 根因大概率是 `CRON_SECRET` 未配置，而不是请求方式问题。既然作者已在三环境配好 `CRON_SECRET`，改回纯 Bearer 校验即可同时满足两边。
- **方案 B**：保留 `?cron=1`，但**只放行 `section=backup` 和 `section=sync` 这两个**，其余一律拒绝。改动稍大。

> ⚠️ 建议先做方案 A 并线上验证一次 cron 是否仍 200；若 cron 真的因为拿不到 header 而失败，再退回方案 B。

### 🔴 P0-21（新增）— 服务端返回非 JSON 时激活按钮再次永久卡死

| 项 | 内容 |
|---|---|
| **优先级** | **P0**（用户点一次就再也用不了，必须刷新页面） |
| **模块** | `activate.html` |
| **定位** | `activate.html:219-238`（`xhr.onload`）、`:214`（空壳 `.catch`） |
| **复现（用户视角）** | 用户点「立即激活」时，恰好遇到 Vercel 冷启动超时 / 502 / 网关返回 HTML 错误页 / 空响应 → 按钮永远停在「激活中…」，**且屏幕上没有任何错误提示**，用户不知道发生了什么 |
| **期望结果** | 显示「网络异常，请重试」并恢复按钮可点 |
| **实际结果** | 按钮永久禁用、无提示；只能手动刷新页面（而刷新会再消耗一次激活限流额度，见 P0-18） |
| **影响端型** | 全端，手环端最严重（刷新成本高） |
| **严重度** | 高 |

**这是 P0-16 的残留** —— 作者修好了正常路径，异常路径未覆盖。Vercel Serverless 冷启动返回 502 HTML 在低频项目上并不罕见（本项目一天只有几单，冷启动概率反而更高）。

**修复建议（约 10 行）：**

```js
xhr.onload = function() {
  var _text = xhr.responseText;
  var res = {
    status: xhr.status, ok: xhr.status >= 200 && xhr.status < 300, _text: _text,
    json: function() {
      return { then: function(cb) {
        var parsed = null;
        try { parsed = JSON.parse(_text); }
        catch (e) { parsed = { success:false, error:"服务端返回异常，请稍后重试" }; }
        cb(parsed);
      }};
    },
    text: function() { return { then: function(cb) { cb(_text); } }; }
  };
  try { for (var i=0;i<callbacks.length;i++){ callbacks[i](res); } }
  catch(e){ console.error(e); }
  if (typeof setLoading === 'function') setLoading(false);   // 移到 finally 语义位置
};
```

同时建议把 `result.catch` 从空壳改成真正注册错误回调。
