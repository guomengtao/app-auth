## 一、本轮结论摘要

**一句话**：作者把上一轮提的 8 条几乎全修了（手环端 fetch→XHR、解绑接口、cron 鉴权、index 语法错误等逐条复核通过），**但 cron 鉴权改造落下了两处 `&cron=1` 的调用方，导致后台「定时任务 → 立即执行」的备份与同步按钮现在必然 401 失败**——这是一次典型的"改了鉴权没改调用方"的回归。

**关键风险**（只谈功能与可用性）：
1. **P0-14｜后台手动备份 / 同步按钮已失效**：点「▶️ 立即执行」→ 提示"执行失败: HTTP 401"。定时路径（Vercel 自动带鉴权头）不受影响，但**手动兜底通道已断**。
2. **P0-15｜待确认｜CRON_SECRET 未配置则每日备份与同步静默全停**：作者自己在回复区点了这一点（"需要在 Vercel 环境变量中设置，否则 Cron Job 会因鉴权失败无法执行"），但尚未确认已设置。**这是当前最需要你动手确认的一件事**——一旦没配，等于没有备份、没有跨库同步。
3. **P1-9｜解绑接口有了但后台没按钮**：`unbind` 后端完整可用，但 `admin_Dx23.html` 全文 0 处"解绑"入口，实际只能 curl。

> 上轮 8 条待办：**7 条已复核确认修复，1 条（P0-13）部分修复降级为 P1**。本轮新增 P0 ×2、P1 ×2、P3 ×1、P4 ×2。

### 数据源一致性小节（Postgres / Redis / Supabase / data/*.json）

- **用户激活状态的权威源 = Redis（Upstash KV）**，激活写入与客户端校验读取同源，用户侧**不会**出现"激活成功但显示未激活"。
- 备库（Supabase / Neon）通过每日 05:00 `section=sync` 镜像同步，属灾备用途，不参与用户读取 → **正常情况下不一致不会造成用户状态错乱**。
- **因此数据一致性问题只在一种情况下升级为 P0**：`P0-15` 成立（CRON_SECRET 未配）→ 备份与同步双双停摆 → 主库出问题时既无备份可恢复、备库数据也是陈旧的。**这才是本轮唯一的数据源风险点，已列为 P0-15。**
- `db-registry.json` 中 upstash=coordinator、supabase/neon=data，角色划分清晰，未发现配置错误。
