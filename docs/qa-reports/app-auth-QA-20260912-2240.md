## 一、本轮结论摘要（一句话）

> **代码零变更、历史已修项零回归，但线上实测暴露 2 个 P0：① IP 限流一旦触发就永不解除（130 秒空闲后仍返回 429，`retry-after: 1` 说明计数器已失去 TTL，用户被永久封禁且无任何自助/后台解除手段）；② 激活失败响应被同步邮件通知阻塞（实测 0.97s–68.8s，6 次请求中 1 次 30 秒完全无响应），而 `activate.html` 的 XHR 没有 timeout 兜底 → 按钮永久卡「激活中...」，必须刷新页面，而刷新又会再吃掉一次限流配额。**

**这两个 P0 会叠加**：用户输错几次码 → 被永久限流 → 每次重试再等最长 68 秒 → 卡死 → 刷新 → 再吃配额 → 彻底无法激活。

## 三、缺陷清单

### P0-23（新增·最高优先）IP 限流触发后永不解除，用户被永久封禁

| 项 | 内容 |
|----|------|
| **优先级** | **P0**（用户彻底用不了 + 报错文案与实际不符） |
| **模块** | 限流 / `lib/rate-limit.js` + `lib/redis.js` |
| **复现步骤（用户视角）** | 用户连续输错 5 次兑换码 → 页面提示「请求过于频繁，请稍后再试」→ 等 1 分钟、5 分钟、甚至第二天再来 → **依然提示同样的话，永远无法激活** |
| **期望结果** | 60 秒窗口过后自动恢复，提示里给出真实可等待时长 |
| **实际结果（本轮线上实测）** | ①**完全空闲 130 秒后的第 1 次请求仍返回 429**（耗时 68.8s）；②此后 6 次连续探测全部 429，响应头**恒为 `retry-after: 1`**；③`retry-after: 1` 意味着 `pttl` 返回 -2/-1（键已无有效 TTL），但 `incr` 仍在返回持续增长的历史计数 → **计数器只增不减** |
| **影响端型** | **全端型**（手环 9 Pro / 10 Pro / 移动 / 微信 / 桌面）。手环与移动网络用户走运营商 NAT 共享出口 IP，**一个人触发会连坐同一 IP 上的其他用户** |
| **严重度** | 致命 |
| **定位** | `lib/rate-limit.js:48-60`（`checkIpRateLimit` 依赖 `redis.incr` + `redis.pexpire` 组合）；`lib/redis.js:241-256`（Postgres 代理 `incr` **不过滤也不清理过期键**）、`:258-268`（`pexpire` 对「已过期」的键 `rowCount=0` 静默无效）、`:270-277`（`pttl` 返回 -2） |
| **根因（两种可能，取决于线上生效的 DB 模式）** | A. **Postgres 代理模式生效**：`incr` 的 `SELECT` 不带 `expires_at` 过滤，且无人删除过期行 → 计数读到的是历史残留值；`pexpire` 又因 `expires_at <= NOW()` 而不生效 → 键永远带着旧 TTL、旧计数。**B. Upstash 模式生效但 `pexpire` 调用失败被 `.catch(function(){})` 吞掉**（`rate-limit.js:52`）→ 键根本没有 TTL → `incr` 永不归零。两种情况的**共同签名都是 `retry-after: 1`**，与本轮观测完全吻合 |
| **放大因素** | 全仓库**没有任何地方能重置限流键**：`grep "ratelimit:ip"` 全仓仅命中 `rate-limit.js:50` 的定义处，**无后台按钮、无脚本、无 API**。用户被封后作者只能手工改数据库 |
| **修复建议** | ① 让限流自愈：在 `incr` 上带绝对过期时间（存 `expireAt` 字段，`incr` 时先比对 `now > expireAt` 则重置为 1），或改用 `SETEX` 语义的单一原子写入；② `pexpire` 失败不要 `.catch` 空吞，要记日志并降级为「本次不计数」；③ `checkIpRateLimit` 返回值带上真实剩余秒数，前端把「请稍后再试」改成「请 X 秒后重试」；④ 后台加一个「清空限流」按钮（当前完全没有逃生通道） |

> 备注：`checkDeviceRateLimit`（`:62-70`，50 次/天）走同一套 `incr`，但因 key 带日期（`ratelimit:device:<YYYY-MM-DD>:<hash>`）次日会换新键，所以**设备限流不是永久的**；只有 **IP 限流（`ratelimit:ip:<ip>`，无日期）是永久的**。

### P0-24（新增，由第 10 轮 P1-17 升级）激活失败响应被同步邮件阻塞 + 前端无超时 → 按钮永久卡死

| 项 | 内容 |
|----|------|
| **优先级** | **P0**（对应 P0 定义中的「卡死按钮全失效」） |
| **模块** | `api/activate.js` / `lib/notify.js` / `activate.html` |
| **复现步骤（用户视角）** | 打开激活页 → 输入兑换码（可能对也可能错）→ 点「立即激活」→ 按钮变成「激活中...」并置灰 → **一直转圈，没有任何提示，也不会恢复** |
| **期望结果** | 最多几秒内给出成功或失败提示 |
| **实际结果（本轮线上实测）** | 本轮共 15 次 `POST /api/activate`，耗时分布 **0.97s / 1.13s / 2.08s / 2.10s / 2.64s / 2.70s / 3.63s / 4.72s / 6.39s / 10.03s / 16.10s / 41.26s / 68.82s**，以及 **1 次 30 秒内服务端完全没有任何响应**（`HTTP:000`）。第 10 轮另观测到 2 次无响应 |
| **影响端型** | **全端型**，手环端最严重（老内核 + 小屏，用户更难判断是卡了还是在加载） |
| **严重度** | 高 |
| **定位** | 服务端：`api/activate.js` **9 处** `await notify.sendActivationFailure`（`:167` `:187` `:209` `:233` `:258` `:280` `:304` `:406` `:526`，全部在 `res.status(...)` 之前）；`lib/notify.js:272`（Resend 超时 10s）、`:206`（SMTP 超时 15s），且 Resend 失败会再退到 SMTP → **最坏 25s+**，加上 `logEmailEvent` 写库与冷启动可到 68s。前端：`activate.html:216-259` 的 `xhrFetch` **没有 `xhr.timeout` / `xhr.ontimeout`**，只在 `onload`/`onerror` 里 `setLoading(false)` |
| **根因** | 把「给管理员发一封通知邮件」这种**纯旁路动作**放在了用户响应链路里同步等待。同一文件里 `notify.pushNotification`（10 处）全都是**不 await** 的正确写法，唯独 `sendActivationFailure` 是 `await` —— 同文件内写法不一致 |
| **为什么第 10 轮定 P1 本轮升 P0** | 第 10 轮样本是 2.3–9.4s；本轮拿到了 **68.8s / 41.3s** 和 **1 次 30s 零响应**，并且确认了「零响应 → 按钮永久 disabled」这条完整因果链（`setLoading(false)` 只在 `onload`/`onerror` 里调用） |
| **修复建议** | ① 9 处 `await notify.sendActivationFailure(...)` 全部**去掉 `await`**（末尾 `.catch` 已存在，不会漏错）；② `activate.html` 加 `xhr.timeout = 15000` + `xhr.ontimeout`（各 1 行），并在 timeout 分支里 `setLoading(false)` + 提示「网络超时，请重试」；③ 建议给 `sendActivationFailure` 加个「同一 IP+原因 60 秒内只发一封」的去重键 |

### P1-16（未修·本轮再次确认，因 P0-23 后果被放大）页面访问埋点与激活共抢同一 IP 限流配额

| 项 | 内容 |
|----|------|

## 七、文档 vs 代码实测

| 文档 | 文档说法 | 代码实测 | 结论 |
|------|----------|----------|------|
