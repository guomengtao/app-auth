## 一、本轮结论摘要

> **一句话**：本轮作者 38 个提交几乎全部投在一个**桌面端通知客户端（EvNotifier）**上，服务端主链路只做了「去通知化→再加回通知」的往返；**上轮两个 P0 一个未修、一个被改得更严重** —— IP 限流**永久封禁**（本轮空闲约 40 小时后首次请求仍是 429，根因已定位到 `lib/redis.js:243`），激活接口因**新增 11 处 `await`** 变得更慢（实测 0.8s–25.2s），而激活页**仍然没有 XHR 超时**，用户按钮会永久卡在「激活中...」。

**关键风险排序（只谈功能与可用性）**

| 排序 | 编号 | 一句话 | 优先级 |
|------|------|--------|--------|
| 1 | **P0-23** | **IP 限流一旦触发永不解除**，用户被永久封禁且全系统无重置入口。本轮空闲 40 小时后实测仍 429 | P0 |
| 2 | **P0-24** | **激活响应被 21 处同步外部调用阻塞**（本轮又新增 11 处），前端无 timeout → 按钮永久卡死 | P0 |
| 3 | **P1-16** | 页面埋点与激活共抢同一 IP 限流配额，用户实际只有 4 次试错机会 | P1 |
| 4 | **P1-18** | 后台 `Promise.allSettled`（ES2020）无降级 → 旧浏览器上统计卡片全 0 | P1 |
| 5 | **P2-25** | 爱发电发码路径新增同步推送，webhook 超时风险上升 | P2 |

**本轮无新增 P0-S。** 上轮待办 3 条（P0-23 / P0-24 / P1-16）**全部未修**，其中 P0-24 因本轮改动**逆向恶化**。

## 三、缺陷清单

### P0-23（未修·本轮定位到精确根因）IP 限流触发后永不解除，用户被永久封禁

| 项 | 内容 |
|----|------|
| **优先级** | **P0** |
| **模块** | 限流 `lib/rate-limit.js` + `lib/redis.js` |
| **复现步骤** | 用户在同一网络下打开激活页 5 次以上（含页面加载时的埋点请求）→ 第 6 次起永远无法激活，等待 1 分钟、1 小时、1 天都无效 |
| **期望结果** | 60 秒窗口过后自动恢复，可继续激活 |
| **实际结果（推断）** | **永久 429**，提示「请求过于频繁，请稍后再试」，且响应头 `Retry-After: 1` 会诱导前端 1 秒后重试，形成空转 |
| **影响端型** | 全部（手环 / 移动 / 微信 / 桌面）——手环端最难自救 |
| **严重度** | 致命。付费用户拿到码却激活不了，且无联系方式可解（唯一出路是作者手工改数据库） |
| **定位** | `lib/redis.js:243`（`incr` 的 `SELECT ... FOR UPDATE` **不带过期过滤**）、`:251-252`（`ON CONFLICT DO UPDATE SET value = EXCLUDED.value`，过期行被复活）、`:270-277`（`pttl` 对已过期键返回 `-2`）；`lib/rate-limit.js:48-60`；`lib/rate-limit.js:43-44`（`IP_MAX_HITS=5` / 60s） |
| **放大因素** | 全仓 `grep "ratelimit:ip"` **仅命中定义处** `rate-limit.js:50`，**没有任何后台按钮 / 脚本 / API 能重置限流** |
| **本轮新增证据** | 距上轮探针**约 40 小时零请求**后，4 次连续请求**全部 429**，`Retry-After` 恒为 `1` |

**根因链（本轮首次打通）**

1. 首次请求：`incr` 建行 `expires_at=NULL`，返回 1 → `pexpire` 写入 `expires_at = now+60s`。此时是对的。
2. 60 秒后键已过期，但 **Postgres 不会自动删行**。
3. 下一次 `incr` 走到 `lib/redis.js:243`，`SELECT value FROM kv_strings WHERE key = $1 FOR UPDATE` —— **没有 `AND (expires_at IS NULL OR expires_at > NOW())`**，于是读到旧值 5，加 1 得 6。
4. `:251` 的 `ON CONFLICT DO UPDATE SET value = EXCLUDED.value` 只更新 `value`，**不重置 `expires_at`**，过期行被永久复活。
5. `6 > 5` → 拦截。`pttl` 读到过去的 `expires_at` → `remaining` 为负 → `Math.max(remaining, -2)` = **-2**。
6. `rate-limit.js:56` `Math.max(ttl || 1000, 1000)` → `-2` 为真值 → `max(-2, 1000)` = **1000** → `Retry-After: 1` 秒。

`retry-after: 1` 就是「TTL 已丢失但计数仍在」的独有指纹。

**修复建议（按成本排序）**

1. **最小改动**：`lib/redis.js:243` 的 SELECT 补 `AND (expires_at IS NULL OR expires_at > NOW())`，让过期键自然从 1 重新计数。
2. **更彻底**：`checkIpRateLimit` 不依赖 `pexpire`，改为把「窗口起始时间」存进 value（`{n:1, start:ts}`），`incr` 时判断 `now - start > 60s` 就重置。Postgres 代理与 Upstash 两种模式都能覆盖。
3. **逃生通道**：后台加一个「清空 IP 限流」按钮（读 `ratelimit:ip:*` 后 `del`）。当前作者本人遇到这个问题也只能手工改库。

### P0-24（未修·本轮逆向恶化）激活响应被同步外部调用阻塞，前端无超时 → 按钮永久卡死

| 项 | 内容 |
|----|------|
| **优先级** | **P0** |
| **模块** | `api/activate.js` + `activate.html` |
| **复现步骤** | 打开激活页 → 输入兑换码 → 点「立即激活」→ 按钮变「激活中...」后长时间无反应 |
| **期望结果** | 3 秒内给出成功或失败提示 |
| **实际结果（推断）** | 本轮 4 次实测耗时 **12.0s / 3.6s / 25.2s / 0.8s**。极端情况请求完全无响应 → 按钮永久 disabled，用户只能刷新页面 |
| **影响端型** | 全部 |
| **严重度** | 高。与 P0-23 叠加后是「输错几次码 → 永久限流 → 每次再等几十秒 → 卡死 → 刷新 → 又吃一个配额」的死循环 |
| **定位** | `api/activate.js` **21 处**在 `res.status()` 之前 `await` 外部调用：9 处 `sendActivationFailure`（:167/195/217/241/266/288/312/414/534）+ 1 处 `sendActivationNotification`（:499）+ **11 处 `pushNotification`（:175/203/225/249/274/296/320/400/422/513/543）**；`activate.html:224-258`（XHR 只有 `onload`/`onerror`，**无 `xhr.timeout`、无 `ontimeout`**） |

**本轮恶化点（重点）**

`07eef54` / `286720b` 两个提交把原本**不 await** 的 `notify.pushNotification(...)` 全部改成了 `await notify.pushNotification(...)`，理由是「防止 Vercel 冻结异步请求」。方向没错，但**副作用是把外部调用的延迟直接转嫁给了用户**，且成功路径也被拖累：

- 修之前：成功路径只有 1 个 await（发邮件）。
- 修之后：成功路径有 2 个 await（发邮件 **+** 推流），而 `pushNotification` 内部自己还要串行跑 `getDailyCounter()`（1 次 Upstash INCR）+ `xadd`（1 次）+ `publish`（1 次）= **3 次外部 HTTP**。
- 429 分支同样被加了一个 `await pushNotification`（`:175`）——**被限流的用户反而是最慢的**（本轮实测第一次 12.0s）。

**修复建议**

1. `activate.html:224` 之后加一行 `xhr.timeout = 15000;` 并补 `xhr.ontimeout`（在 `setLoading(false)` 之后再提示「网络超时，请重试」）。**这一行能独立消灭「永久卡死」**。
2. 服务端：把 `res.status().json()` 提到所有通知之前（先响应，再 await 通知）。Vercel 冻结问题可用 `waitUntil` 或在响应后继续 await 解决。
3. 429 分支（`:175`）不要发通知 —— 限流本身就是「同一用户在疯狂重试」，每封邮件都是噪音。

## 七、回归测试建议（给开发的可执行 checklist）

**A. 激活主链路（每次发版必跑）**
1. 全新浏览器 / 无痕窗口打开 `activate.html`，输入正确兑换码 → 期望 **3 秒内**返回激活码。
2. 输入错误兑换码 → 期望 3 秒内报错，按钮恢复可点（**不是永久「激活中...」**）。
3. 连续快速点 5 次「立即激活」→ 期望第 6 次才被限流，提示里**带具体秒数**。
4. 触发限流后**什么都不做等 65 秒** → 再提交 → 期望**恢复正常**（当前：仍 429，P0-23）。
5. 用手机流量（换 IP）重复步骤 1 → 期望正常激活（用于区分「限流」和「真故障」）。
6. 断网后点激活 → 期望**超时提示**而不是永久转圈（P0-24）。

**B. 限流自愈（P0-23 专项）**
7. 在数据库里查 `SELECT key, value, expires_at FROM kv_strings WHERE key LIKE 'ratelimit:ip%';` → 确认过期行的 `value` 在下次请求时**回到 1**，而不是继续累加。
8. 确认存在某个入口（后台按钮或脚本）能手动清空 `ratelimit:ip:*`。

**C. 后台（P1-18 专项）**
9. 用安卓 7 / iOS 13 真机或 Chrome DevTools 设备模拟打开后台 → 确认首屏四张统计卡片**有数字**而不是 0。
10. 刷新后台首页 → 确认统计数字在 3 秒内出现（CDN 阻塞修复是否生效）。

**D. 爱发电（P2-25 专项）**
11. 在爱发电下一笔测试单 → 确认 webhook 在 5 秒内返回，且兑换码正常生成。
12. 确认重复回调同一订单号时**不会重复发码**。
