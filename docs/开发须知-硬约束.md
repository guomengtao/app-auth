# app-auth 开发须知：硬约束

> 本文件登记的是**改这里会出事的约束**，不是教程。
> 每条都附了「为什么」和「踩过的具体代价」，改代码前先扫一遍。
> 最近更新：2026-11-03

## 1. 组件真实位置（别再凭感觉判断延迟）

| 组件 | 真实位置 | 怎么确认的 |
|---|---|---|
| Supabase 数据库 | **美东 us-east-1** | `.env` 连接串 `aws-0-us-east-1.pooler.supabase.com` |
| **Redis 实际模式** | **Postgres proxy**（`kv_strings`/`kv_hashes` 表 → Supabase 美东），**不是 Upstash** | 线上日志 `[redis] MODE: Postgres proxy`；`go:mapping` 数据实际存在 `kv_hashes` 表（23 条） |
| Upstash 账号 | 东京 ap-northeast-1（Global 就近） | `dig` CNAME → `global-apn1`；**但当前只是备用，线上未承载短链数据** |
| Vercel 函数 | **iad1 美东**（2026-11-03 曾迁 hkg1，当天回滚） | 响应头 `x-vercel-id: sin1::iad1` |

**约束**：
- 讨论性能前必须先钉死这几行，否则结论会反过来（本项目反过一次，见第 11 条）。
- Supabase 走 Cloudflare 代理，**从外部无法判断其区域**，唯一可靠证据是 pooler 主机名。不要在没看连接串的情况下断言「数据库在亚洲」。
- **判断 redis 模式不要看环境变量，要看线上日志**。`db-switches` 的三开关（upstash/supabase/neon 全 on）只表示「可用」，不代表当前在用哪个；真正的分支在 `lib/redis.js` 第 13 行，取决于 `USE_UPSTASH` 与 `effectiveProvider`。
- 迁区域后必须**实际请求一次**看 `x-vercel-id`，配置项写了不等于生效。

## 2. 跳转路径（302 之前）禁止任何同步 IO

**为什么**：`api/go.js` 的 302 是用户点「购买」后的必经之路。任何 `await` 都在用户眼前发生。

**允许存在的 await**：零。配置读取必须走内存缓存（`cfgGet`），不能每次都 `await redis.hget`。

**踩过的代价**：2026-09-23 提交 `4af5186` 引入 `await Promise.race([pushTask, 5s])`，把整条推送链串在 302 前面，实测首字节 1.79s / 5.12s / **20s 超时**。移动端用户以为没反应就退出，W39 起转化率 39%→16%。一个 `await` 腰斩了转化率。

**反模式清单**：
```js
// ❌ 全部禁止出现在 res.status(302) 之前
await redis.hget(...)              // 跨洋往返
await fetch("https://api.qq.com")  // IP 定位
await supabase.from(...)           // 写库
await Promise.race([task, 5000])   // 「限时等待」依然是等待
```

**正确姿势**：`background.run(promise, "label")` —— 底层是 `@vercel/functions` 的 `waitUntil`，平台保证跑完，但不阻塞响应。

## 3. Vercel 会在响应结束后冻结函数实例

**约束**：`res.end()` 之后再跑的 Promise **不保证完成**，裸 `promise.then()` 会被拦腰截断。

**踩过的代价**：`visitor_logs` 的 INSERT 丢过整条记录；`purchase_click` 投递记录停在 `pending`（通知根本没发出去）。

**规则**：
- 所有后台任务必须 `background.run(...)`。
- 反过来也成立：**不要**因为怕丢就 `await` 它（那就是第 2 条事故）。两者是配套的，缺一不可。

---

## 4. 读失败 ≠ 不存在

**约束**：`redis.hget` 返回 `null`（不存在）和抛异常/超时（读失败）必须走**不同分支**。

**踩过的代价**：原代码 `if (!raw) return notFound(...)`，一次 Redis 抖动就能把所有短链变成 404。用户看到的是「链接不存在」，实际是后台挂了。

**正确姿势**（`api/go.js` 已实现）：
```js
try {
  raw = await hgetWithTimeout(slug);   // 1.5s 上限
  if (raw === CFG_TIMEOUT) { readFailed = true; raw = null; }
} catch (e) { readFailed = true; raw = null; }
// 读失败 → 陈旧缓存 → 静态兜底；确实不存在 → 404
```

**连带要求**：任何读到配置后写库的逻辑，写失败只能打日志，**不能影响主流程返回**。

## 5. 缓存 TTL 换来的副作用要主动告知运营

配置缓存在进程内存，TTL 60s。**改 `go:mapping` 后最长 1 分钟才全网生效。** 改价请提前 1 分钟操作，不要改完立刻去页面点验证然后怀疑没生效。

陈旧兜底窗口是 6h —— 意思是 Redis 挂了 6 小时内，老配置还能把人送到正确页面。

## 6. 向下兼容红线（已发布的东西不能改）

已有 4 条硬红线，来自「安装包参数写死、二维码已印刷」的现实：

1. **已上线的 URL 参数名不得改名或改变语义**。新增标记只能追加，不能替换。
2. **`p`（product）是唯一机型来源，绝对不能删**。曾经误判 `m`/`p` 重复可省 64 字符，实际 `m` 恒为 `"ap"`（2 字符），删 `p` 等于毁掉全部机型归因。
3. **`c` 是人工投放位编号，不是来源**。用它统计来源得出过「扫码占 53%」的错误结论，真实确证手环来源只有 24.9%。
4. **短链二维码长度已到极限**：实测长码 190 字符 / QR Version 10（53×53），硬上限 213 字符（Version 11 边界），余量 23。`i=1` 这类标记只在失败场景加（成功场景零增长）。

## 7. 数据口径坑

- `device_norm = '0000'` 是**脏值**，出现在 6034 条记录上，做设备统计必须排除。混用它统计过「23 台活跃设备」，实际是手机 78 台 + 手环 84 节点。
- `watch_device_id` = 安卓手机（同步器宿主）；`watch_node_id` = 手环。两者不能相加当「设备数」。
- `x-vercel-ip-city` 对非 ASCII 城市名是 **percent-encoded**（`Maghār` → `Magh%C4%81r`），入库前必须 `decodeURIComponent`，否则后台显示 `Z · Magh%C4%81r`。

---

## 8. 安全约束

- `/dl/:file` 的文件名走**白名单正则**（`^EVSyncProbe-v\d+\.\d+\.\d+\.apk$`），不要改成「拼接用户输入」。这是防开放重定向的唯一防线。
- slug 必须过 `SLUG_RE`（RFC 1123 label-ish），不要为了兼容放宽到允许任意字符。
- `Location` 头只允许来自 Redis 配置或静态兜底表，**不允许来自请求参数**。

## 9. 部署与验证

1. 改 `api/*.js` → 必须重新部署才生效，本地 `node --check` 只是语法。
2. 部署后用响应头 `x-vercel-id` 验证实际执行区域（形如 `hkg1::hkg1`），**不要只看 `vercel.json`**。
3. Hobby 套餐 region 是**单选**（Pro 5 个 / Enterprise 全部），写数组多个值不会多区域部署。
4. 环境变量 `GO_FALLBACK_MAP` 需要手动配（JSON 字符串），**没配就少一层保险**。至少覆盖已在二维码/安装包里流通的 slug：

```
GO_FALLBACK_MAP={"ev-timetable":"https://afdian.com/item/xxxxxx"}
```

## 10. 迁 region 前必须确认 redis 模式（2026-11-03 真实事故）

**事故**：12:55 把 `regions` 改成 `["hkg1"]` 部署后，**全部短链立刻 404**（12:22 数据库还有正常跳转记录）。13:14 回滚 iad1 后恢复 302。

**根因**：生产 redis 走 Postgres proxy，`hget` 实际是「查 Supabase 的 `kv_hashes` 表」。函数迁到香港后：
- 每次 `hget` 变成「香港 → 美东」跨洋 SQL 查询
- 我同时给 `hget` 加了 1.5s 上限（原本为了防 20s 超时）
- 跨洋查询超过 1.5s → 判读失败 → 无静态兜底 → 404

**两个错误叠加才出事，单独一个都不会**。反过来说：**加超时必须配静态兜底**，否则等于把「慢」升级成「挂」。

**硬规则**：
1. `redis` 未真正切到 Upstash（东京）之前，**不要迁 hkg1**。当前 redis 数据在 Supabase 美东，函数必须待在 iad1。
2. 若将来要迁，前置条件是：① 数据从 `kv_hashes` 迁到 Upstash；② `USE_UPSTASH=true` 且线上日志出现 `[redis] MODE: Upstash Redis`；③ 迁完先用 `x-vercel-id` + 一次真实 302 验证，再撤旧部署。
3. 任何给关键路径加超时的改动，**必须同时配一个兜底值**（静态表/陈旧缓存），否则就是把延迟问题变成可用性问题。
