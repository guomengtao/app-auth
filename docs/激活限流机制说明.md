# 激活限流机制说明

## 一、触发机制全景

```
用户打开激活页
    │
    ├──► 前端自动触发 visitor-track 埋点
    │       └──► api/activate.js:29  →  checkIpRateLimit()
    │            消耗 1 次 IP 配额
    │
    └──► 用户点击"激活"按钮
            │
            ├──► api/activate.js:163  →  checkIpRateLimit()
            │     │
            │     ├── 未超限 → 继续设备限流检查
            │     │             └──► checkDeviceRateLimit()
            │     │
            │     └── 超限 → HTTP 429
            │           "请求过于频繁，请稍后再试"
            │
            └──► 每次失败（含 429）都发邮件给管理员
```

## 二、两层限流体系

### 2.1 IP 限流

| 参数 | 值 | 位置 |
|------|----|------|
| Key | `ratelimit:ip:<YYYY-MM-DD-HH-MM>:<clientIp>` | `lib/rate-limit.js:66` |
| 窗口 | **1 分钟（按分钟分区）** | `lib/rate-limit.js:47-57` |
| 重置方式 | key 自带分钟前缀，每分钟自动换新 key，无需依赖 `pexpire` | `lib/rate-limit.js:67` |
| 上限 | **15 次/分钟** | `lib/rate-limit.js:44` |
| 计数方式 | `incr` + `pexpire`（首次置 TTL，用作过期清理） | `lib/rate-limit.js:68-70` |
| 阻塞返回 | HTTP 429 + `Retry-After` 头 | `lib/rate-limit.js:72-74` |
| 错误文案 | `请求过于频繁，请稍后再试` | `lib/rate-limit.js:74` |

**触发点**（两处共抢同一个 key）：

| 触发点 | 代码位置 | 何时发生 |
|--------|----------|----------|
| visitor-track 埋点 | `api/activate.js:29` | 激活页面加载时自动 |
| 主激活流程 | `api/activate.js:163` | 每次点击"激活"按钮 |

> 用户实际可用次数 ≈ **14 次**（15 减去页面加载的 1 次埋点），远高于之前的 4 次。

### 2.2 设备限流

| 参数 | 值 | 位置 |
|------|----|------|
| Key | `ratelimit:device:<YYYY-MM-DD>:<deviceId hash>` | `lib/rate-limit.js:63` |
| 窗口 | **当天 00:00 到次日 00:00（北京时间）** | `lib/rate-limit.js:35-42` |
| 上限 | **50 次/天** | `lib/rate-limit.js:61` |
| 错误文案 | `该设备激活次数过多，请明天再试` | `lib/rate-limit.js:69` |

设备限流的 key 带日期，次日自动换新 key，不会永久锁定。

## 三、Postgres 模式下的已知缺陷

### 3.1 P0-23（已修复）：IP 限流永不解除

**当前状态**：已通过分钟分区 key 彻底规避，不再依赖 `pexpire` 可靠性。

**修复方式**：Key 从 `ratelimit:ip:<ip>` 改为 `ratelimit:ip:<YYYY-MM-DD-HH-MM>:<ip>`。每分钟 key 自动切换，旧 key 随 TTL 自然过期。即使 Postgres `pexpire` 静默失败，新分钟的新 key 也从 0 开始计数。

**影响范围**：不再触发。

### 3.2 P0-24：429 响应被同步邮件阻塞

`api/activate.js:167-173` 中，IP 限流分支在返回 429 之前，先**同步等待**邮件发送：

```javascript
var ipNotifyResult = await notify.sendActivationFailure(req, { ... });
```

邮件发送涉及 SMTP 连接（最长 15s）+ Resend API（最长 10s），单次等待最长 **68.8 秒**。在此期间：
- 前端 XHR 无 timeout → 按钮永久卡在"激活中..."
- 用户唯一自救：刷新页面 → 又吃 1 次 IP 配额 → 死循环

### 3.3 P1-16：埋点与激活共抢 IP 配额

`activate.html` 加载时自动调 `visitor-track`，该埋点也走 `checkIpRateLimit`，使用相同的 `ratelimit:ip:<ip>` key。

**实际效果**：用户 1 分钟内可用次数 = 5 - 1（埋点）= **仅 4 次**。

在共享出口 IP 环境（校园/公司/运营商 NAT），一人触发会**连坐同一 IP 下的所有用户**。

## 四、限流触发后的连带影响

| 影响 | 说明 |
|------|------|
| 每次 429 都发邮件 | 管理员邮箱被刷屏，真正重要的失败通知被淹没 |
| Retry-After 不真实 | P0-23 下 `pttl` 返回 -2，`Retry-After: 1` 暗示 1 秒后可重试，实际永远不行 |
| 前端无超时兜底 | XHR 无 `timeout`/`ontimeout`，按钮卡死无反馈 |
| 无后台解除手段 | 当前无任何方式清空限流计数 |

## 五、数值速查表

| 限流类型 | Key | 窗口 | 上限 | 恢复方式 |
|----------|-----|------|------|----------|
| IP 限流 | `ratelimit:ip:<分钟时间戳>:<ip>` | 1 分钟 | **15 次** | 下一分钟自动换新 key，计数从 0 开始 |
| 设备限流 | `ratelimit:device:<date>:<hash>` | 当天 | 50 次 | 次日 00:00 自动换 key |
| 页面埋点 | 同 IP 限流 key | 1 分钟 | 共抢 15 次 | 每次打开页面消耗 1 次 |
| 激活请求 | 同 IP 限流 key | 1 分钟 | 共抢 15 次 | 实质可用约 14 次 |
