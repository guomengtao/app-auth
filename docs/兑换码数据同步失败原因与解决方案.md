# 兑换码数据同步失败原因与高效解决方案

## 概述

app-auth 项目采用**本地优先（local-first）** 架构，数据存储在浏览器 `localStorage` 中，通过「一键同步」按钮将数据推送到 Vercel 部署的 Postgres（Neon）数据库。但在实际使用中，兑换码管理的数据同步频繁出现失败，表现为：服务器返回 0 条兑换码、本地数据推送后丢失、同步按钮无响应等。

本文档深入分析同步失败的根本原因，并提供高效解决方案。

---

## 一、系统架构回顾

### 1.1 数据存储模型

```
浏览器 localStorage                Vercel Serverless (Postgres/Neon)
─────────────────────               ─────────────────────────────────
STORAGE_KEY_PRODUCTS    ──push──→   kv_hashes (auth:products)
STORAGE_KEY_CODES       ──push──→   kv_strings (auth:redeem:<code>)
                         ──push──→   kv_sets (auth:redeem_codes)
STORAGE_KEY_RECORDS     ──push──→   kv_strings (auth:activation:<code>)
                         ──push──→   kv_sets (auth:activation_codes)
STORAGE_KEY_COUNTERS    ──push──→   kv_strings (auth:product_counter)
STORAGE_KEY_DELETES     ──push──→   (delete from above tables)
```

### 1.2 同步流程（merge 模式）

```
1. 客户端 → GET /api/admin/sync  → 服务器返回快照 (snapshotAll)
2. 客户端 mergeServerDataIntoLocal(服务器快照) → 合并到本地
3. 客户端 collectLocalPushPatch() → 收集本地变更
4. 客户端 sanitizePatchDeletes(patch) → 删除保护白名单校验
5. 客户端 → POST /api/admin/sync (mode=merge, patch) → 服务器 applyPatch()
6. 服务器 applyPatch → 逐条写入 Postgres → 返回新快照
7. 客户端 mergeServerDataIntoLocal(新快照) → 最终一致
```

## 二、兑换码同步失败的 6 大根因

### 根因 1：Postgres 读写分离导致数据写入后立即读取为空

**严重程度：🔴 高**

**问题描述：**

Vercel Postgres（Neon）默认开启了读写分离。写入操作路由到**主库（Primary）**，读取操作可能路由到**只读副本（Read Replica）**。由于副本同步存在延迟（通常 100ms ~ 2s），在 `applyPatch` 写入兑换码后，`snapshotAll` 立即通过 `smembers` + `mget` 读取时，可能从副本读到**空数据或旧数据**。

**代码证据：**

[lib/postgres.js](file:///Users/Banner/Documents/guomengtao/app-auth/lib/postgres.js#L96-L99) 中已有注释说明此问题：

```javascript
// ⚠️ 统一使用 vercelDb.connect() 路径
// 之前混用 vercelSql.query（无params）和 vercelDb.connect（有params）
// Vercel Postgres 可能对两者做读写分离，导致 applyPatch 写入主库后
// snapshotAll 通过只读副本读，立刻读到空数据！
```

虽然代码已改为统一使用 `vercelDb.connect()`，但 Neon 的**计算分支（Compute Branch）** 架构仍可能导致读写分离问题。Neon 的读写分离是**连接级别**的，而非 SQL 级别。

**影响：**

- 同步后服务器返回的快照中 `redeemCodes` 为 0 条
- 前端保护逻辑检测到服务器返回 0 但本地有 >0 条，触发 `🛡️ 保护` 跳过 merge
- 虽然保护了本地数据不丢失，但服务器端数据实际未写入成功（或写入后前端没读到）

**解决方案：**

1. **在 Neon 控制台禁用只读副本（Read Replica）**：如果免费版开启了只读副本，在 Neon Console → Project → Branches → 选择主分支 → Settings → 关闭 Read Replica。

2. **写入后添加短暂延迟再读取**：在 `applyPatch` 完成后，`snapshotAll` 前添加 500ms-1s 延迟：

```javascript
// sync.js applyPatch 返回前
await new Promise(resolve => setTimeout(resolve, 800));
```

3. **使用 Neon 的 `neon_unsafe_reads` 参数**：在连接字符串中添加 `?options=neon_unsafe_reads%3Dtrue` 强制读取主库。

### 根因 2：兑换码的双存储结构不一致

**严重程度：🔴 高**

**问题描述：**

兑换码数据存储在**两个地方**：

1. `kv_strings` 表：`auth:redeem:<CODE>` → 存储兑换码的 JSON 数据
2. `kv_sets` 表：`auth:redeem_codes` → 存储所有兑换码 code 的集合索引

如果写入 `kv_strings` 成功但 `sadd` 到 `kv_sets` 失败，则 `smembers("auth:redeem_codes")` 返回的集合中不包含该 code，`snapshotAll` 将永远找不到这条兑换码。

**代码证据：**

[api/admin/sync.js](file:///Users/Banner/Documents/guomengtao/app-auth/api/admin/sync.js#L262-L272) applyPatch 中：

```javascript
await redis.set(key, JSON.stringify(cv));          // 写入 kv_strings ✅
try {
  var sr = await redis.sadd("auth:redeem_codes", cv.code);  // 写入 kv_sets ❓
  console.log('📦 applyPatch write redeem:', cv.code, 'set=OK, sadd=' + sr);
} catch (se) {
  console.error('📦 applyPatch redeem sadd failed:', cv.code, se.message);
}
```

注意 `sadd` 使用了 `try/catch` 包裹，如果失败不会抛出异常，但兑换码将**静默丢失**（在集合索引中不出现）。

**同样的问题也存在于：**

- [api/admin/redeem-codes.js](file:///Users/Banner/Documents/guomengtao/app-auth/api/admin/redeem-codes.js#L227-L228) 生成兑换码时
- `snapshotAll` 通过 `smembers` 获取 code 列表，再用 `mget` 批量读数据

**解决方案：**

1. **使用 Postgres 事务**：将 `set` + `sadd` 包装在同一事务中：

```javascript
// redis.js 中添加事务支持
async function setWithSadd(key, value, setKey, member) {
  await pg.query('BEGIN');
  try {
    await pg.query(
      "INSERT INTO kv_strings (key, value, expires_at) VALUES ($1, $2, NULL) " +
      "ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value",
      [key, value]
    );
    await pg.query(
      "INSERT INTO kv_sets (key, member) VALUES ($1, $2) ON CONFLICT DO NOTHING",
      [setKey, member]
    );
    await pg.query('COMMIT');
  } catch (e) {
    await pg.query('ROLLBACK');
    throw e;
  }
}
```

2. **添加定期一致性检查**：在服务器健康检查中增加 `kv_strings` 和 `kv_sets` 的一致性校验。

### 根因 3：Neon Postgres 冷启动超时

**严重程度：🟡 中**

**问题描述：**

Neon 免费版在 5 分钟无活动后自动暂停计算节点（scale-to-zero）。下次请求时需要**唤醒**，冷启动时间通常为 1-5 秒。Vercel Serverless Function 的 Hobby 计划超时时间为 **10 秒**。

如果同步操作涉及大量数据（如数百条兑换码的 `mget` 批量读取），加上冷启动时间，很容易超过 10 秒超时限制。

**影响：**

- 同步请求返回 504 Gateway Timeout
- 前端显示「同步失败: Internal server error」
- 如果超时发生在写入中途，可能导致数据不一致

**解决方案：**

1. **升级 Neon 计划**：Pro 版不自动暂停，避免冷启动。
2. **使用 Neon 的 `@neondatabase/serverless` 驱动**：支持 HTTP fetch 连接，冷启动更快。
3. **分批处理大数据量**：将 `snapshotAll` 的 `mget` 批次从 200 减小到 50，降低单次请求耗时。
4. **添加预热端点**：在 Vercel Cron Job 中每 4 分钟 ping 一次 `/api/admin/health`，保持 Neon 活跃。

### 根因 4：`smembers` 全量加载的性能瓶颈

**严重程度：🟡 中**

**问题描述：**

[api/admin/sync.js](file:///Users/Banner/Documents/guomengtao/app-auth/api/admin/sync.js#L38) 中 `snapshotAll` 使用 `smembers("auth:redeem_codes")` 一次性加载**所有**兑换码 code 到内存：

```javascript
var codeSet = await redis.smembers("auth:redeem_codes");
var codeKeys = Array.isArray(codeSet) ? codeSet : [];
```

`smembers` 映射到 `SELECT member FROM kv_sets WHERE key = $1 ORDER BY member`，返回全部行。当兑换码数量达到数千条时：
- 内存占用增大
- 传输时间增加
- 后续 `mget` 批量读取也相应增大

**解决方案：**

1. **使用 `sscan` 替代 `smembers`**：分页读取，避免一次性加载全部数据。`redis.js` 已实现 `sscan`：

```javascript
// snapshotAll 中改为
var allKeys = [];
var cursor = "0";
do {
  var result = await redis.sscan("auth:redeem_codes", cursor, { count: 200 });
  allKeys = allKeys.concat(result[1] || []);
  cursor = result[0];
} while (cursor !== "0");
```

2. **考虑使用 Postgres 原生查询**：绕过 Redis 兼容层，直接用 SQL JOIN 查询兑换码数据，避免两次查询。

### 根因 5：数据校验规则过于严格导致静默跳过

**严重程度：🟡 中**

**问题描述：**

[api/admin/sync.js](file:///Users/Banner/Documents/guomengtao/app-auth/api/admin/sync.js#L135-L149) 中 `validateLocalCode` 有严格的校验规则：

```javascript
function validateLocalCode(obj, idx) {
  if (!obj || typeof obj !== "object") return null;
  var c = String(obj.code || (typeof idx === "string" ? idx : "")).toUpperCase().trim();
  if (!/^[A-Z0-9]{3,16}$/.test(c)) return null;   // ← 严格正则
  var pid = String(obj.product_id || "01").padStart(2, "0");
  var dm = Number(obj.duration_months);
  if (!/^\d{2}$/.test(pid)) return null;           // ← product_id 必须 2 位
  if (!Number.isFinite(dm) || dm < 1 || dm > 99) return null;  // ← duration 1-99
  // ...
}
```

**哪些情况会静默跳过：**

- code 包含小写字母（会被 `toUpperCase` 处理，但如果在途中截断有风险）
- `product_id` 不是 2 位数字格式
- `duration_months` 为 0 或超过 99
- 前端生成 code 时可能包含特殊字符
- 从旧版本迁移的数据可能缺少必填字段

**影响：**

- `applyPatch` 报告中 `redeemCodes.skipped` 增加，但用户不知道具体原因
- 本地有 100 条兑换码，推送后服务器只收到 80 条，剩余 20 条被静默跳过

**解决方案：**

1. **增加详细的跳过日志**：在 `validateLocalCode` 返回 null 时记录具体原因：

```javascript
function validateLocalCode(obj, idx) {
  if (!obj || typeof obj !== "object") {
    console.warn('validateLocalCode: invalid object', obj);
    return null;
  }
  var c = String(obj.code || (typeof idx === "string" ? idx : "")).toUpperCase().trim();
  if (!/^[A-Z0-9]{3,16}$/.test(c)) {
    console.warn('validateLocalCode: invalid code format', c);
    return null;
  }
  // ...
}
```

2. **前端提交前做预校验**：在 `collectLocalPushPatch` 中过滤掉不符合规范的兑换码，并给用户提示。

### 根因 6：localStorage 容量限制导致数据截断

**严重程度：🟢 低（但需关注）**

**问题描述：**

浏览器 `localStorage` 通常限制为 **5-10MB**。每条兑换码的 JSON 数据约 100-200 字节，数千条兑换码加上产品、激活记录等数据，可能接近限制。

[admin.html](file:///Users/Banner/Documents/guomengtao/app-auth/admin.html#L2020-L2040) 中 `saveLocalData` 已有 QuotaExceededError 处理：

```javascript
} catch (e) {
  var quota = e && (e.name === 'QuotaExceededError' || e.code === 22 || ...);
  if (quota) {
    console.warn('⚠️ localStorage 容量不足，尝试压缩存储:', key, serialized.length, 'bytes');
  }
}
```

但仅做了警告，没有实际的数据压缩或清理策略。

**解决方案：**

1. **定期清理已使用的兑换码**：将已使用的兑换码从本地存储中移除（或迁移到单独的归档存储）。
2. **使用 IndexedDB 替代 localStorage**：IndexedDB 存储上限通常为浏览器磁盘空间的 50% 以上，远大于 localStorage。
3. **数据压缩**：对 JSON 字符串使用 LZ-String 压缩后再存储。

## 三、其他潜在问题

### 3.1 Vercel Serverless 并发限制

Hobby 计划限制**同时最多 10 个并发请求**。如果用户在同步时同时打开了多个管理页面（如多个 Tab），可能触发并发限制。

### 3.2 删除保护的白名单校验额外请求

[sanitizePatchDeletes](file:///Users/Banner/Documents/guomengtao/app-auth/admin.html#L4265-L4300) 在推送删除前会额外请求一次 `GET /api/admin/sync` 做白名单校验。这个额外请求：
- 增加了同步耗时
- 如果该请求失败，删除操作会被阻止
- 白名单校验依赖服务器快照的准确性（见根因 1）

### 3.3 时间戳冲突解决逻辑

`applyPatch` 中产品使用 `updated_at` 比较，兑换码使用 `used_at || created_at` 比较。如果客户端和服务端时钟不同步，可能导致较新的数据被较旧的覆盖。

## 四、高效解决方案（按优先级排序）

### 方案 1（立即实施）：禁用 Neon 只读副本 + 写入后延迟

**操作步骤：**

1. 登录 [Neon Console](https://console.neon.tech)
2. 进入项目 → Branches → 主分支 → Settings
3. 关闭 Read Replica（如果已开启）
4. 在 `sync.js` 的 `applyPatch` 中，写入完成后、`snapshotAll` 前添加：

```javascript
// 在 sync.js applyPatch 末尾，snapshotAll 之前
await new Promise(function(resolve) { setTimeout(resolve, 1000); });
```

### 方案 2（推荐）：事务化写入 + 一致性校验

在 `redis.js` 中添加原子写入方法，确保 `kv_strings` 和 `kv_sets` 同步写入。并在健康检查中增加一致性校验。

### 方案 3（推荐）：smembers 改为 sscan 分页

修改 `snapshotAll` 中的 `smembers` 调用为 `sscan` 分页，降低单次查询的内存和耗时。

### 方案 4（可选）：添加兑换码数据预热/缓存

在 Vercel 中添加 Cron Job，每 4 分钟 ping 一次 `/api/admin/health`，保持 Neon 不进入暂停状态。

### 方案 5（长期）：迁移到 IndexedDB

将前端本地存储从 `localStorage` 迁移到 `IndexedDB`，获得更大的存储空间和更好的性能。

## 五、诊断检查清单

当同步失败时，按以下步骤排查：

| 序号 | 检查项 | 方法 |
|------|--------|------|
| 1 | Neon 是否已暂停？ | 访问 `/api/admin/health`，查看 Postgres Connectivity 状态 |
| 2 | 是否有只读副本延迟？ | 在 Neon Console 查看 Replication Lag |
| 3 | `kv_sets` 和 `kv_strings` 是否一致？ | 在 Neon SQL Editor 中执行：`SELECT COUNT(*) FROM kv_sets WHERE key='auth:redeem_codes'` 对比 `SELECT COUNT(*) FROM kv_strings WHERE key LIKE 'auth:redeem:%'` |
| 4 | Vercel Function 是否超时？ | 查看 Vercel 部署日志，搜索 "Task timed out" |
| 5 | 前端控制台日志 | 打开浏览器 DevTools，搜索 `🔀` 和 `📦` 日志标签 |
| 6 | localStorage 容量 | 在 DevTools → Application → Local Storage 查看使用量 |
| 7 | 校验规则跳过 | 检查 `applyPatch` 日志中 `redeemCodes.skipped` 数量 |
