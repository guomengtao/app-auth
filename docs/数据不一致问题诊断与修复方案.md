# 数据不一致问题诊断与修复方案

针对"数据总是不一致"这个问题，根源不在于操作流程，而在于当前代码逻辑中存在 **"删除不同步"** 和 **"快照非原子"** 两个硬伤。本文将直接针对这两个痛点，给出**立即可执行的诊断与修复方案**，不再重复基础操作说明。

---

## 一、为什么数据总是不一致？（代码层面的2个致命点）

### 1. 合并逻辑（`mergeServerDataIntoLocal`）只增不减
- **现象**：在服务器上删除了一个产品/兑换码，执行 `merge` 同步后，本地依然保留着该数据。
- **代码证据**：`mergeServerDataIntoLocal` 函数中，**只有在 `forceReplace` 为 `true`（即 `pull` 模式）时才会清理本地多余数据**。日常使用的 `merge` 模式只会合并 `sProducts` 和 `sCodes`，**从不删除本地存在但服务器不存在的条目**。
- **结果**：本地僵尸数据越积越多，导致统计数量永远对不上。

### 2. 快照生成（`snapshotAll`）非原子性
- **现象**：`scanAllSetMembers` 先 `SSCAN` 获取 Key 列表，再分批 `MGET` 取值。如果在两次操作之间（毫秒级），Redis 中的兑换码被激活/删除，服务器返回的快照就是**不一致的半成品**（例如，Set 里有 Key A，但 `MGET` 没取到值，或取到了旧值）。
- **结果**：`merge` 拿到一个"撕裂"的快照，部分数据被合并，部分丢失，造成本地与服务器的永久性偏移。

---

## 二、针对"不一致"的终极解决方案（三步走）

### 第一步：日常采用"强制拉取（Pull）"作为基准恢复（治标）
**不要再依赖 `merge` 作为日常修复不一致的手段**，`merge` 只是增量合并，无法清除僵尸数据。

- **操作**：每天早上上班或数据对不上时，先点击 **`⬇ 仅拉取（pull）`**。
- **原理**：`pull` 模式会触发 `forceReplace`，强制用服务器最新快照**完全覆盖**本地。这能瞬间清理所有僵尸数据，让两边数量完全对齐（本地产品数=服务器产品数，兑换码数=服务器兑换码数）。
- **注意**：这会导致本地未推送的新增数据丢失，所以**请确保先点 `push` 推送完本地新增，再点 `pull`**。

### 第二步：修复"删除不同步"的逻辑缺陷（治本，需修改代码）

在 `mergeServerDataIntoLocal` 函数中，增加 **"服务器缺失即本地删除"** 的逻辑。

**修改点**（约在 `mergeServerDataIntoLocal` 函数末尾）：

```javascript
// 在 mergeServerDataIntoLocal 函数中，合并完 sProducts 和 sCodes 后，增加以下清理逻辑：

// 1. 清理本地多余的产品（服务器没有的）
var localProductIds = Object.keys(pLocal);
var serverProductIds = sProducts.map(p => String(p.id).padStart(2,'0'));
localProductIds.forEach(function(id) {
  if (!serverProductIds.includes(id)) {
    // 保守策略：仅当本地产品创建时间 < 服务器快照生成时间，说明是旧数据，删除它
    if ((pLocal[id].updated_at || 0) < (snap.generatedAt || Date.now())) {
      delete pLocal[id];
      console.log('🧹 清理本地孤立产品:', id);
    }
  }
});

// 2. 清理本地多余的兑换码（服务器没有的）
var localCodeMap = getLocalCodesMap();
Object.keys(localCodeMap).forEach(function(code) {
  var existsInServer = sCodes.some(c => String(c.code).toUpperCase() === code);
  if (!existsInServer) {
    if ((localCodeMap[code].updated_at || localCodeMap[code].created_at || 0) < (snap.generatedAt || Date.now())) {
      delete localCodeMap[code];
      console.log('🧹 清理本地孤立兑换码:', code);
    }
  }
});
saveLocalCodesMap(localCodeMap);
```

> 这一改，`merge` 就变成了真正的"双向全量同步"，而不是"只增不减"。

### 第三步：利用现有的"数据对比（Diff）"功能进行精准排雷（运维手段）

页面里已经有 **`📊 数据对比`** 标签页，这是解决不一致的核心武器，请按以下流程使用：

1. **识别孤岛**：点击"开始对比"。
   - 若卡片显示 **"仅本地有"** 且数量 > 0：说明这些是服务器已删除但本地残留的僵尸数据。
   - 若卡片显示 **"仅远程有"** 且数量 > 0：说明这些是服务器有但本地未拉取的新数据。

2. **精准修复**：
   - 针对"仅本地有"的僵尸数据：点击该卡片下方的 **`🔧 修复此表`**，系统会强制将本地数据推送到服务器（覆盖）。*如果这些数据确实不该存在，建议在本地界面手动删除它们，再推送。*
   - 针对"仅远程有"的缺失数据：直接点击顶部的 **`⬇ 仅拉取`**，即可补全。

## 三、彻底杜绝不一致的"黄金操作流程"（请严格执行）

为了避免混乱，请统一遵循以下操作序列，不再随意点击按钮：

| 步骤 | 场景 | 操作 | 原理 |
| :--- | :--- | :--- | :--- |
| **1** | **上班/初次打开** | 点击 **`📊 数据对比`** → 观察"仅远程有" | 判断服务器是否有新数据未拉取 |
| **2** | **发现服务器有新数据** | 点击 **`⬇ 仅拉取`** | 用服务器覆盖本地，获得纯净基准线 |
| **3** | **本地批量操作（增删改）** | 正常操作，全部在本地完成 | 0 数据库连接 |
| **4** | **下班/操作完毕** | 点击 **`⬆ 仅推送`** | 将本地新增推送到服务器（不拉取，避免覆盖） |
| **5** | **推送成功后** | 点击 **`⬇ 仅拉取`** | 重新拉取一次，验证推送是否成功，并清理本地缓存 |

> **核心口诀**：**"上班先拉取（Pull），下班先推送（Push），推送完再拉取（Pull）验证"**。把 `merge` 当作"紧急修复"工具，而不是"日常同步"工具，因为 `merge` 的复杂合并逻辑容易在极端情况下产生分歧。

## 四、辅助排查：检查"计数器"偏移

如果产品数量对不上，但数据库里确实有，检查 `auth:product_counter`。
- 在 `数据对比` 标签页，观察"计数器"卡片。
- 如果 `本地` 大于 `远程`，说明本地生成了新产品但未推送或推送失败。
- **立即操作**：在本地产品列表中，找到 ID 大于远程计数器的产品，确认无误后执行 `push`。若无法推送，手动将本地计数器改小（`localStorage` 中修改 `admin_counters_v2.product_counter`），再用 `pull` 拉取服务器真实 ID。
