# 用户全链路追踪 与 画像汇总页 —— 设计方案

> 日期：2026-09-24
> 目标在一个页面还原「下载/访问课程表 → 扫码访问购买页 → 支付 → 发兑换码 → 激活 → 后续使用」的完整链路
> 位置：后台侧边栏「快捷激活」下的新子 tab
> 前置改动：本次已落地的 `visitor_logs.query / params` 列 + `/go/` 链路参数留存（见 `docs/访客IP归属地异常与URL参数丢失-分析.md`）

## 0. 先回答命名问题

| 候选 | 评价 |
|---|---|
| **用户画像** | ✅ 运营心智友好、可扩展；❌ 语义偏向"静态标签/人群归纳"（RFM、标签云），而本页核心是**单个用户的事件序列** |
| **全链路用户追踪汇总** | ✅ 描述精准；❌ 太长（侧栏 + 子 tab 按钮都放不下），且"汇总"与"单用户时间线"是两种视图，混在一个名字里会打架 |

**推荐：栏目（子 tab）名用「👤 用户画像」，页面主区块标题用「全链路追踪」，二者同时出现。**

理由是这两个词其实描述的是**同一件事的两层**：

```
用户画像（Persona）  = 「他是谁」   静态层：设备指纹 / 地区 / 渠道 / 付费能力 / 生命周期
全链路追踪（Journey）= 「他做了什么」动态层：时间戳事件流 CDN─▶ 支付 ─▶ 激活 ─▶ 使用
```

只叫"画像"会让人以为点进去是一张标签卡；只叫"追踪"则丢掉了"为什么追踪"——最终要沉淀成画像。
所以 UI 上：**tab 名 = 用户画像**（短、好找），**页面第一个组件标题 = 全链路追踪时间线**（解释它是什么）。后续若要扩展第三个子视图，再叫「画像汇总 / 漏斗分析」，名字体系也自洽。

## 1. 目标场景（用一个真实样本串起来）

用户（手表）访问：

```
https://app-auth.gudq.com/go/ev-timetable
  ?deviceId=d4cd0dabcf4caa22ad92fab40844c786
  &m=Emulator-Vela &p=Emulator-Vela &o=0 &v=1200
  &t=band &s=pill-shaped &w=212 &h=520
  &a=2 &l=zh &r=1.6.69 &c=t-9p-d
```

我们能读到的事实：

| 事实 | 来源 |
|---|---|
| 已安装 EV 课程表（版本号 `r=1.6.69`） | URL 参数（App 内生成链接） |
| 设备型号 `Emulator-Vela`、band 类型、212×520 药丸屏、API 2、中文 | URL 参数 `m/p/v/t/s/w/h/a/l` |
| 渠道 `t-9p-d` | URL 参数 `c`（已是 `health.js channels` 的归因口径） |
| IP + UA + 归属地 | Vercel 请求头 + `ip_lookups` |
| 设备唯一 ID `d4cd0dab…c786`（32 位） | URL 参数 `deviceId` |
| 立刻 302 到爱发电 | `api/go.js` |

然后：付款 → 订单 → 生成兑换码 → 用户拿码激活 → 激活时我们拿到完整 `device_info` + IP → 后续访问使用手册。

**我们要的页面**就是把这条链自动拼出来，并给出「每一步花了多久」「在哪个环节掉了」。

## 2. 现有数据资产盘点（能拼到什么程度）

### 2.1 四大域的存储现状

| 域 | 存储 | 主键 | 关键字段 | 可用性 |
|---|---|---|---|---|
| **访问/点击** | Postgres `visitor_logs` | 自增 id | `ts / ip / path / query / params(jsonb) / ua / ref / country / region / city / visitor_hash / source` | ⭐⭐⭐ 刚加了 `query/params`，**deviceId 抓手就在这里** |
| 短链点击 | Redis `stats:go:recent` + `stats:go:<日>:<slug>` | list | `slug / ip / rg / ci / u / r / v(visitor_hash) / utm_*` | ⭐⭐ 只能留 100 条 + 7 天 KV |
| **订单** | Redis `afdian:order:<out_trade_no>` | 订单号 | `out_trade_no / user_id / user_name / plan_title / product_id / total_amount / redeem_code / created_at / dm_sent` | ⭐⭐⭐ **有 `redeem_code` 外键**；❌ 无 IP、无真实下单时间 |
| **兑换码** | Redis `auth:redeem:<CODE4>` | 4 位码 | `code / product_id / duration_months / used / used_device_id(sha256) / generated_activation_code / created_at / used_at / source / user_name / out_trade_no` | ⭐⭐⭐ **爱发电渠道有 `out_trade_no` 双向外键**；后台直开/批量生成的码没有 |
| **激活** | Redis `auth:activation:<CODE18>` | 18 位激活码 | `activation_code / device_id_hash / device_id(4) / device_id_full(原始) / product_id / months / redeem_code / generated_at / expires_at / device_info / visitor_info` | ⭐⭐⭐ **IP + 完整设备指纹都在** |
| 激活失败 | Redis `auth:activation_failure:<ts>:<rnd>` | key 名 | `reason / redeem_code / device_id[_full] / visitor_info / device_info` | ⭐⭐⭐ 掉坑原因全在这 |
| **推送快照** | Postgres `message_delivery.payload` (jsonb) | id | `new_order / new_activation / activation_failure / page_visit / purchase_click` 五种 payload 的全量快照 | ⭐⭐⭐⭐ **唯一同时含 order/redeem/activation/ip/hash 的表**，做跨域检索最快的入口 |
| 归属地 | Postgres `ip_lookups` | ip | `country/region/city/region_zh/city_zh/district/isp/org/asn` | ⭐⭐⭐ 已 JOIN |

> ⚠️ `message_delivery.related_code / related_device` 因取字段写成驼峰（`payload.redeemCode`）而**恒为 NULL**（`lib/notify.js:991-992`），别指望这两列，直接查 `payload->>'redeem_code'`。

### 2.2 现成外键（好消息：链路三跳是齐的）

```
afdian:order:<OUT_TRADE_NO> ──redeem_code──▶ auth:redeem:<CODE4>
                                                │ out_trade_no（反向，仅 source=afdian）
                                                └─generated_activation_code──▶ auth:activation:<CODE18>
                                                                                   ├─ device_id_full ──┐
                                                                                   └─ visitor_info.ip ─┤
                                                                                                       │
visitor_logs.params->>'deviceId'  ─────────────────────────────────────────────────────────────────────┤
visitor_logs.ip ───────────────────────────────────────────────────────────────────────────────────────┘
```

**结论：不需要靠"时间接近"猜关系。** 订单↔兑换码↔激活 三跳外键齐全，缺的只有「访问侧 → 订单侧」这一跳（因为没有 IP、没有 tracking token）。

### 2.3 断点清单（本方案要解决的）

| # | 断点 | 影响 | 解法（见 §6） |
|---|---|---|---|
| B1 | **订单没有 IP / 没有 referer** | 「谁付的钱」和「谁点了购买」拼不上 | `new_order` payload 补 IP + referer；订单记录补 `tracking_ip` |
| B2 | **订单 `created_at` 是系统处理时间，不是真实下单时间** | 「浏览→下单」时长算出来是错的 | 爱发电返回的 `create_time` 落库为 `paid_at` |
| B3 | **访问侧 → 订单侧无 token** | 换 IP 支付后彻底断链 | 落地页生成 `tid`，写 `visit_tokens` 表，付款后按「同 tid 或 IP+UA+6h 窗口」回填 |
| B4 | `visitor_hash`（32bit JS hash）≠ `device_id_hash`（sha256） | 两者不可互转 | 只用 `params->>'deviceId'` 做跨层桥接 |
| B5 | `device_id` 只保留最后 4 位 | **碰撞风险极高**（见 §4.3） | 必须用 `device_id_full` + 设备指纹联合判定 |
| B6 | `auth:device:<hash>` 是覆盖写（且全仓零读） | 一个设备多次激活只剩最后一条 | 不用它，全扫 `auth:activation_codes` 后按 `device_id_full` 过滤 |
| B7 | 后台直开/批量码无 `out_trade_no` | 链路在"订单"处断开 | UI 显式标记「无订单来源（后台直开）」 |
| B8 | `course-guide / user-guide / ev-schedule / ev-timetable` **只推 `section=visit`，不写 `visitor_logs`** | 后续使用行为无法追踪 | 补 `visitor-track` 埋点 + URL 带 `?d=<deviceId>` |

## 3. 关联模型（Identity Graph）

不引入图数据库，用「**候选发现 → 证据打分 → 生成主线**」三步，运行时算。

### 3.1 四类身份锚点

| 锚点 | 强度 | 来源 | 说明 |
|---|---|---|---|
| `device_id_full`（原始设备串，如 32 位 hex） | **强** | `auth:activation:*`、`visitor_logs.params->>'deviceId'` | 跨层唯一硬凭据 |
| `redeem_code` / `out_trade_no` | **强** | 订单↔兑换码↔激活外键 | 链路内三跳串联 |
| `设备指纹` = sha1(`m|p|v|t|w|h|r`) | 中强 | `device_info`、访问 URL 参数 | 同型号不同机可用 objective 区分（尤其 Emulator 需降权） |
| `ip` | **弱** | 全链路都有 | NAT / 换网 / 移动出口都会污染，只做候选发现与佐证 |

### 3.2 打分规则

```
score(device 匹配 full)        +100   → 置信度 强
score(device 后 4 位 匹配)      +45   → 需再用「设备指纹 + 时间窗 ≤ 7 天 + product_id 一致」任一佐证才能升为强
score(设备指纹完全一致且非模拟器) +35
score(设备指纹为 Emulator-*)    +8    → 模拟器 ID 可能复用，刻意降权
score(IP 相同)                  +15
score(IP 同 /24 或同 ASN)        +6
score(时间间隔 ≤ 6h)            +10 ；≤ 72h +5 ；> 30d -20
score(UA 完全一致)              +10
score(redeem_code / order 外键) 直接强关联（不再打分）
```

判定档位：**≥80 强关联（实线）｜50~79 疑似（虚线 + 「?」标记）｜<50 不合并**。
UI 必须把这些内部 evidence **显式展示**（"因为 A、B、C 三条证据判定为同一人"），否则运营无法信任结果。

### 3.3 实体聚合成用户

```
canonical_user  ── 由「强边」构成的连通分量
  ├─ devices[]      （device_id_full + 指纹）
  ├─ ips[]
  ├─ orders[]       （out_trade_no）
  ├─ codes[]        （redeem_code）
  ├─ activations[]  （activation_code）
  └─ events[]       （统一时间线）
```

## 4. 冲突与误判场景（重点）

### 4.1 冲突矩阵

| # | 场景 | 现状会不会错 | 处理策略 |
|---|---|---|---|
| C1 | **换 IP 激活**：扫码用 WiFi、手表激活走另一网络（甚至 4G） | ✅ 会误判成两个人 | 以 `device_id_full` 为强边连接，IP 只做旁证；UI 在 IP 变化节点打「🔄 网络切换」标记 |
| C2 | **同一出口 IP 多人**：公司/校园/家庭 NAT、同一基站 | ✅ 会把多个人合成一个 | **只允许 deviceID/order/code/support 强边合并，绝不靠 IP 合并**；同 IP 多 device 时并在 UI 显示「该 IP 下有 N 个设备」 |
| C3 | **deviceId 只有后 4 位 → 碰撞** | ✅ 严重（见 4.3） | 必须用 `device_id_full`；历史记录若 `device_id_full === device_id`（老数据只有 4 位），降级为"疑似" |
| C4 | **模拟器 / 开发者设备**：`m=p=Emulator-Vela`，一堆人共用同一个模拟环境 ID | ✅ 会把不同真人合成一个 | 指纹含 `Emulator` 时 +8 分，且当同 device 出现 **≥3 个不同 user_name 或 ≥3 个不同 IP/24** 时标记「⚠ 疑似共享/模拟器」并**拆分展示** |
| C5 | **一人多单 / 续费**：同一用户买 2 次、或者买多产品 | ❌ 不会错（本来就该合成一个） | 合并为同一 canonical_user，只在时间线上呈现为多条订单分支 |
| C6 | **二手 / 共用设备**：同一 `device_id_full` 但两个不同 `user_name` 各自买了码 | ⚠️ 边界情况 | 保留合并，但打「👥 疑似换人/共用」标记并列两个 user_name |
| C7 | **码被转赠/泄漏**：订单是 A 买的，激活用的是设备 B | ⚠️ 需要发现 | 对比「购买时的 deviceId/UA」与「激活的 device_id_full」不一致 → 标记「⚠ 购买设备 ≠ 激活设备」 |
| C8 | **长时间延迟激活**：买了几个月后才激活 | ❌ 不影响正确性（有外键） | 时长>7d 时，UI 显示自然跨度但**不计入漏斗转化时延**（避免污染指标） |
| C9 | **纯 IP 访问无任何 deviceId**（用户在电脑浏览器打开） | ❌ 无法强关联 | 标为弱候选，默认不合并，提供「手动合并到某用户」按钮（写 `identity_overrides` 表） |
| C10 | **时间是系统处理时间**（B2） | ✅ 会让"下单→发货"看起来是 0 秒 | 补 `paid_at` 真实支付时间 |

### 4.2 时间一致性校验（防错兜底）

任意一条合并必须满足：`ts(访问) ≤ ts(下单) ≤ ts(发码) ≤ ts(激活)`。
违反则**不合并**，并在「可疑合并」列表里给出原因（常见于：先有人激活、后有另一个人的访问落到同 IP）。

### 4.3 为什么「4 位 deviceId」必须降权（算给你看）

`normalizeDeviceId()`（`lib/validate.js:14-29`）丢掉非字母数字后只取**最后 4 位**，即空间只有 `62^4 = 14,776,336`。
按生日悖论：`p ≈ n² / (2N)`

| 用户量 n | 至少一次碰撞概率 |
|---|---|
| 1,000 | ≈ 3.4% |
| 3,000 | ≈ 30% |
| 5,000 | ≈ 85% |

而 `device_id_hash = sha256(这 4 位)`（`api/activate.js:379`），所以**碰撞在哈希前后都无法区分**。
唯一救命的是记录里还存了 `device_id_full`（原始输入）。→ **结论：匹配一律以 `device_id_full` 为准，4 位只用于快速筛候选。**

## 6. 后端接口设计

### 6.1 新增 `GET /api/admin/health?section=stats&sub=user-journey`

参数：`q`（任意锚点值）、`days`（默认 30）、`include`（`weak` 是否返回弱候选）

实现（`health.js` 里 `section=stats` 已有一整套 `sub=` 分支，照抄 `channels` / `visitor-unique-ips` 的写法）：

1. **锚点识别**：`q` 用正则判定类型（32/16 位 hex → deviceId；IPv4/IPv6 → ip；4 位 `[A-Z0-9]` → redeem；`FD…` → 订单号；其余 → user_name）
2. **取种子**
   - deviceId → `SELECT * FROM visitor_logs WHERE params->>'deviceId' LIKE '%<尾部4位>'` + 全扫 `auth:activation_codes` 匹配 `device_id_full`
   - redeem → `auth:redeem:<CODE>` → `out_trade_no` / `generated_activation_code`
   - order → `afdian:order:<no>` → `redeem_code`
   - ip → `visitor_logs.ip` 窗口查询
3. **扩展**：沿 §2.2 的三跳外键取全集
4. **拼 event 列表** → 排序 → 打分 → 合并成 canonical_user
5. **返回**：`{ user, timeline[], metrics{}, evidence[], candidates[], warnings[] }`

### 6.3 `tracking_events` 表结构建议

```sql
create table if not exists tracking_events (
  id            bigserial primary key,
  ts            timestamptz not null,
  kind          varchar(32)  not null,          -- visit / go_click / purchase_click / order / redeem / activation / failure / doc_view
  canonical_id  varchar(64),                    -- 解析后写入，可为空（待解析）
  device_full   varchar(128),                   -- device_id_full 原文
  device_norm   varchar(4),                     -- 规范化后 4 位（仅用于快速筛）
  visitor_hash  varchar(32),
  ip            varchar(45),
  redeem_code   varchar(8),
  out_trade_no  varchar(64),
  activation_code varchar(32),
  channel       varchar(32),                    -- device_info.source / URL c 参数
  payload       jsonb,
  created_at    timestamptz not null default now()
);
create index if not exists idx_te_ts on tracking_events(ts desc);
create index if not exists idx_te_device on tracking_events(device_full);
create index if not exists idx_te_ip on tracking_events(ip);
create index if not exists idx_te_redeem on tracking_events(redeem_code);
create index if not exists idx_te_canonical on tracking_events(canonical_id);
```

有了它，「漏斗」（访问→支付→激活各步人数与流失）、「画像汇总」（设备/地区/渠道分布）都只是一句 group by。

| 项 | 状态 |
|---|---|

| 面板 | ✅ 用户画像页「⚙️ 人工校正」折叠卡：规则表单（类型/A/合并或拆分/B/备注）+ 规则列表 + 删除；弱候选每行有「合并」一键按钮 |

实现里的两个决定：
1. **不照抄规则里的 `kind`**：A、B 常常是不同类型（典型：设备 ID ↔ IP = 手表激活 + 电脑浏览），所以按**值的形态**自动归类（IPv4/IPv6 → IP；4-8 位大写 → 兑换码；≥8 位 → 订单号；否则 → 设备）。
2. **拆分优先级最高**：同一对值同时存在 merge 与 split 时，merge 直接失效（不播种），split 照常剔除。

剩余（五期）：`tid` 溯源 token、App 内 beacon（启动 / 版本上报，用于留存）。

## 9. 风险与约束

1. **扫描规模**：`auth:activation_codes` / `auth:redeem_codes` 只能用 `sscan` 全扫，量大时慢。→ 一期按 `days` 限制窗口 + 结果缓存 60s；三期由 `tracking_events` 索引替代全扫。
2. **Redis 是 Postgres 代理**（`kv_*` 表），全扫成本高于真 Redis，别在同步请求里做大循环；批量用 pipeline（现有 `health.js` channels 就是这么做的）。
3. **4 位 deviceId 碰撞**（§4.3）：任何"只看 4 位就合并"的实现都会出错，务必用 `device_id_full`。
4. **爱发电 API 单次最多同步 100 单**（`query-orders.js:387` `maxPages=2`），历史订单可能不全 → 订单侧允许为空，UI 显示"未同步到订单"而不是判失踪。
5. **模拟器/脚本刷污染**：`Emulator-Vela` 类设备不入漏斗指标，单独分组统计。
6. **隐私**：页面展示 IP 与地区即可，`device_id_full` 默认掩码显示（`d4cd…c786`），提供"显示完整"按钮。
7. **时间口径统一**：全部按北京时间（复用 `lib/rate-limit.js beijingDateKey()` 的口径），展示带时区标签。
