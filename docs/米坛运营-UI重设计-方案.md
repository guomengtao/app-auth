# 米坛运营三 Tab · UI 重设计方案（v2）

> 任务：`admin_Dx23.html?tab=bandbbs`「米坛运营」栏目三个 Tab **全新视觉风格 + 语义重命名**重设计。
> 用户诉求（2026-10-06 拍板）：**全新视觉风格** + **更好用/更好操作** + **信息更清晰**。
> **v2 修订**（2026-10-06 23:45 用户追加）：
> ① 详情页 → 改名 **获奖名单**；默认展示**全部评论**；头部**筛选全部展开**、一键快捷筛选。
> ② 奖品管理 → 改名 **奖品池**；管理**全部奖品名单**；默认大量奖品处于**未发放**。
> ③ 发奖时系统从池中**随机**抽一个未发放的绑定给获奖人。
> ④ 获奖名单显示**所得奖品池 ID**。
>
> 本方案按总纲 **§3.13** 交付待批；**批准前不动产品代码**。

## 一、目标与边界

### 做什么
1. 为「米坛运营」定义**全新组件语言**（分区卡 / 胶囊签条 / 指标卡 / 状态胶囊 / **筛选芯片组** / 粘性表格）。
2. **语义重命名**：详情 → **获奖名单**（管所有人 + 发放登记）；奖品管理 → **奖品池**（管所有奖品名单）。
3. **筛选交互重构**：把下拉式 `<select>` 全部换成**平铺展开的芯片组（chip）**，点一下即筛，不用展开下拉、不用二次确认。
4. **默认视图重构**：获奖名单默认展示**全部评论**（不再要求先选资源帖）；奖品池默认**未发放优先**。
5. **建立奖品 ID 双向关联**：获奖名单行显示所得奖品池 ID；奖品池行反查获奖人。
6. **发奖改随机**：从池中随机抽未发放奖品（原为顺序取用）。
7. **图标全部换 Lucide**（纠正 emoji 违规，见 §3.14）。

### 不做什么（划边界）
- ❌ 不动全站主色 `--accent`（靛蓝）；不动侧栏/顶栏/其他栏目。
- ❌ 不改抓取（poll）的解析逻辑、不改私信发送通道。
- ❌ 不引入第三方 CSS/JS 框架；Lucide 必须自托管。
- ❌ 不改「五星才发奖」的既有业务规则。

### 关键约束
- `admin-bandbbs.js` 472 行、**29 个 DOM id**；允许改，但 id 必须原样保留。
- `admin_Dx23.html` 是**硬链接**（inode 230660094，link count=2）→ 必须原地改，改完 `ls -li` 复核。
- 全站中文，不得引入新英文。

### 现状痛点
- 筛选是**下拉 `<select>`**：要先展开、再滚动找选项，点两次才筛完，电脑端体验笨重。
- 获奖名单**必须先选资源帖**才有内容，无法一眼看全站获奖情况。
- 奖品池只有 3 个数字（总量/已用/剩余），**看不到具体是哪些奖品、哪份没发**。
- 获奖名单**看不到得了哪个奖品**（虽然有数据）。
- 发奖顺序取用，**同一批总是发池里最早导入的那几个**，靠前的奖品被反复消耗、靠后的长期不用。


| 规则 | 说明 |
|---|---|
| **全部展开** | 所有可选值平铺成一排，不做下拉、不做「更多」折叠 |
| **一键筛选** | 单击即切换，无需确认；同一行内**单选**（点新项自动取消旧项） |

## 四、后端改动（v2 新增，本方案的关键技术点）

> 用户新需求 ③④ 命中后端，必须改 `lib/bandbbs.js`。以下为已核实的改动点。

### 4.1 随机发奖（对应需求 ③）

**现状**（`lib/bandbbs.js` L735–742）：
```js
for (var r = 0; r < eligible.length; r++) {
    if (r >= availableLinks.length) { … break; }
    var el = eligible[r];
    var linkItem = availableLinks[r];   // ← 顺序取用
```

**改为随机**：洗牌 `availableLinks` 后再按序取，保证**同一批内不重复抽**（不是每次 `Math.random()` 取一个 —— 那样会重复命中同一条）。

**风险与对策**：
| 风险 | 对策 |
|---|---|
| 同一批内抽到重复条目 | 用 Fisher-Yates **洗牌一次**再顺序消费（等价于无放回抽样） |
| 并发两次发放（cron 与手动同时跑）抽到同一条 | 写入前**再校验** `entry.assigned`（乐观锁）；已占用则跳过取下一条；日志记录冲突次数 |
| 洗牌依赖 Redis hash 顺序（本身不稳定） | 洗牌前先按 key 排序，保证「输入确定 → 抽签可复现（同 seed 下）」便于排查 |

### 4.2 奖品池「列出全部奖品」接口（对应需求 ②）

**现状缺口**：`reward-pool-stats` 只给 3 个数字；`reward-log` 只返回**已发放**条目 → **无法渲染「未发放的那个列表」**。

**需新增** `op=reward-pool-list`：
- 入参：`status`（all / unassigned / assigned / claimed / unclaimed）、`batch`、`limit`、`offset`
- 出参：`{ items: [{ couponCode, goUrl, assigned, assignedTo, assignedFor, assignedAt, resourceId, batch }], total, counts: {all, unassigned, assigned, claimed, unclaimed} }`
- `counts` 一次性给全，**筛选芯片的计数直接用它**，避免前端为每个芯片单独发请求。
- 注意：**返回体不能含完整兑换链接**（链接即奖品，泄露=白送）→ 列表只给掩码 `afdian.com/item/9f3a…`，详情按需单条取。

### 4.3 获奖名单带奖品 ID（对应需求 ④）

**现状**：`getResourceDetail` 返回评论列表；奖品 ID 存在**池条目**里（`assignedFor = 评论 key`）与**发放记录**里（`coupon_code`）。

**改动**：在 `getResourceDetail`（及新增的「全部评论」查询）中，把 `reward:<resourceId>:<reviewKey>` 的 `coupon_code` 一并回填到每条评论上 → 前端直接渲染。
