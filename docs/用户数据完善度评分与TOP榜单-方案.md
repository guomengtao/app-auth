# 用户数据完善度评分 与 TOP 榜单 —— 设计方案

> 日期：2026-09-24
> 位置：后台「快捷激活 → 📊 画像汇总」
> 依赖：`tracking_events`（已在 v1.7.54 上线，历史数据已回填 692 条）

---

## 0. 先回答：以后新数据会自动写入吗？

**会自动写入。** 六个业务节点都已接上 `lib/tracking.js`，且全部走 `background.run()`（不阻塞用户请求，失败只打日志）：

| 节点 | 触发时机 | 写入位置 | 状态 |
|---|---|---|---|
| `visit` 页面访问 | 页面埋点 `POST /api/activate?section=visitor-track` | `api/activate.js` | ✅ 自动（含 index / activate / my-ip / admin + 5 个文档页） |
| `go_click` 短链落地 | 访问 `/go/:slug` | `api/go.js` | ✅ 自动 |
| `purchase_click` 购买点击 | 同上（同一次点击的另一条记录） | `api/go.js` | ✅ 自动 |
| `order` 支付订单 | 爱发电 webhook / cron 同步 | `lib/afdian-processor.js` | ✅ 自动 |
| `redeem` 发放兑换码 | 同上（跟订单同一时刻） | `lib/afdian-processor.js` | ✅ 自动 |
| `activation` / `failure` 激活结果 | 用户激活 | `api/activate.js` | ✅ 自动 |

**三点需要知道的边界**（不是 bug，是设计）：

1. **表不存在时会自愈**：`ensureTable()` 幂等，第一次写入自动建表建索引。
2. **回填不用再点**：回填只是补历史，新数据实时进。重复点也不会产生重复行（`dedupe_key` 唯一）。
3. **订单的「设备归属」是延迟补齐的**：订单来自爱发电服务端回调，**天生没有 deviceId/IP**；要在该订单的兑换码被激活后，才能用 `redeem_code` 把设备反查回订单（`enrichIdentity()`，在打开漏斗/画像时自动执行，5 分钟节流）。所以**刚支付、还没激活的订单暂时是"无设备"状态**，属正常。

## 1. 这个分数是干什么用的（先明确目的）

用户说的"从业务流程和数据完善度工作开展上就比较合格"，点出了真正用途：

> **这不是"用户价值分"，而是"这个用户的数据是否被完整、可信地记录下来"的体检分。**

它有三个用途：

| 用途 | 说明 |
|---|---|
| **① 采集健康度** | 分数普遍低 → 说明某个环节的埋点/字段还没打通（例如访问侧没带 deviceId），是**开发任务清单** |
| **② 标杆样本** | 满分用户 = 全链路可追溯的理想形态，拿它对照就能看出缺哪一环 |
| **③ 排查入口** | 点开高分用户的时间线，就是一条"标准链路"；点开低分用户，就能看到断点在哪 |

⚠️ 因此 UI 上必须写清"这是**数据完整度**，不是消费能力/忠诚度"，否则运营会误读。

## 2. 现状体检（真实数据，2026-09-24）

回填后 112 台设备、692 条事件的分布：

### 2.1 链路完整度分布

| 链路覆盖 | 设备数 | 说明 |
|---|---|---|
| 0/5（只有激活失败记录） | **34** | 激活失败但从未成功——运营重点对象 |
| 2/5 | 31 | |
| 3/5 | **45** | 最常见：订单 + 发码 + 激活 |
| 4/5 | 2 | |
| **5/5** | **0** | ← 没有人满分，因为下一条 |

### 2.2 字段覆盖率（决定性事实）

| 事件类型 | 条数 | 有 device | 有 IP | 有兑换码 | 有订单号 | 有渠道 | 有机型 |
|---|---|---|---|---|---|---|---|
| redeem | 196 | 52% | **0%** | 100% | 40% | **0%** | **0%** |
| visit | 149 | **1%** | 100% | 0% | 0% | 1% | 0% |
| failure | 132 | 100% | 100% | 98% | 0% | 9% | 17% |
| activation | 122 | 84% | 60% | 85% | 0% | 11% | **25%** |
| order | 79 | 62% | **0%** | 100% | 100% | **0%** | 0% |
| go_click | 17 | 12% | 100% | 0% | 0% | 6% | 0% |

**读出来的三个系统性缺口**：

1. **访问侧没有身份**：`visit` 只有 1% 带 deviceId —— 因为 `visitor_logs.params` 是今天才加的列，历史数据为空。→ 直接用事实回答"为什么访问→支付算不出来"。
2. **订单/兑换码没有 IP**：0%，服务端回调拿不到买家 IP（设计限制，不是缺陷）。
3. **渠道与机型覆盖极低**（0~25%）：`c` / `m` 参数只有 App 生成的链接才带，手动激活（输入 deviceId）没有。

**结论：评分模型不能只判断"有没有事件"。** 如果用"5 步各 20 分"，现在 90% 的人都只能拿 60 分以下，榜单失去区分度，而且**扣分点全在用户无法控制的地方**。所以必须拆成"身份可识别度 + 链路完整度 + 属性丰富度 + 归属地完整度"四个维度，并把"平台能力缺口"与"用户行为差异"区分开。

## 3. 评分模型（满分 100）

### 3.1 四个维度与权重

| 维度 | 权重 | 回答什么问题 |
|---|---|---|
| **A. 身份可识别度** | 25 | 这个人能被稳定、唯一地认出来吗？ |
| **B. 链路完整度** | 40 | 从访问到激活，关键节点是否都能找到记录？ |
| **C. 属性丰富度** | 20 | 设备/渠道/订单信息是否够拿来分析？ |
| **D. 归属地完整度** | 15 | 省 / 市 / 区县是否都有？ |

### 3.2 A. 身份可识别度（25 分）

| 项 | 分值 | 判据 |
|---|---|---|
| 有设备标识 | 10 | `device_full` 非空 |
| 设备标识完整（非 4 位截断） | +6 | `length(device_full) > 4`（4 位碰撞概率详见 `用户全链路追踪与画像汇总-方案.md` §4.3） |
| 有 IP | +5 | 任一事件 `ip` 非空 |
| 设备标识一致（无多设备冲突） | +4 | 该用户下 `count(distinct device_full) == 1` |

**不参与加分的风险项**（只做标记，不扣分）：模拟器指纹、同一 IP 多设备、购买/激活 IP 不同。

> 为什么不扣分：这些是**平台侧识别能力**问题，不是数据缺陷。扣分会打击真实性反而误导。

### 3.3 B. 链路完整度（40 分，5 步 × 8 分）

| 步骤 | 8 分条件 |
|---|---|
| ① 访问（visit / go_click） | 有任一条访问类事件 |
| ② 购买意图（go_click / purchase_click） | 有短链点击或购买点击 |
| ③ 支付订单（order） | 有订单事件 |
| ④ 发放兑换码（redeem） | 有兑换码事件 |
| ⑤ 激活（activation） | 有激活成功事件 |

**顺序校验（最高扣 8 分）**：必须满足 `访问 ≤ 点击 ≤ 支付 ≤ 发码 ≤ 激活`。违反一项扣 4 分，最多扣 8 分——用于发现"时间线不合理"（多账号共用 IP 的典型症状）。

**说明**：① ② 现在几乎拿不到分（历史数据缺 params）。这是**有意为之**——榜单要如实反映"访问侧采集还没打通"，而不是粉饰。等新数据积累，这两项会自然涨上来。

### 3.4 C. 属性丰富度（20 分）

| 项 | 分值 | 判据 |
|---|---|---|
| 机型 / 产品名 | 6 | `payload->>'model'` 长度 ≥ 3（`ap` 这类垃圾值不算） |
| App / ROM 版本 | 4 | `payload->>'rom'` 非空（如 `1.6.69`） |
| 渠道 | 5 | `channel` 非空（如 `t-9p-d`） |
| 订单侧信息（昵称 / 金额 / 套餐） | 5 | 订单事件 payload 里有 `user_name` 或 `amount` |

### 3.5 D. 归属地完整度（15 分）

| 项 | 分值 | 判据 |
|---|---|---|
| 省（`region_zh` / `region`） | 5 | `ip_lookups` / Vercel 头部命中 |
| 市 | 5 | 同上 |
| 区县 | 5 | 腾讯位置服务命中 |

### 3.6 档次标签

| 分数 | 标签 | 含义 |
|---|---|---|
| 85–100 | 🟢 全链路可追溯 | 标杆样本，任何分析都能做 |
| 65–84 | 🔵 基本完整 | 主流程齐全，个别属性缺 |
| 40–64 | 🟡 部分可追溯 | 能认出人、能对齐交易，但缺访问侧/属性 |
| 0–39 | 🔴 数据稀疏 | 只有失败记录或单一事件，需人工介入 |

### 3.7 算一个真实例子

样本：一台有「订单 + 兑换码 + 激活」且带机型的设备（当前 45 台的主流形态）

```
A 身份：有设备 10 + 设备完整 6 + 有 IP 5 + 单一设备 4                = 25 / 25
B 链路：访问 0 + 点击 0 + 订单 8 + 发码 8 + 激活 8                  = 24 / 40
         （① ② 拿不到分：历史访问没有 params）
C 属性：机型 6 + 版本 4 + 渠道 0（手动激活没带 c）+ 订单 5           = 15 / 20
D 归属地：省 5 + 市 4（无区县）                                     = 9 / 15
────────────────────────────────────────────────────────────────
合计 = 73 分 → 🔵 基本完整
```

缺口清单会直接告诉运营/开发：**「缺访问侧 deviceId」「缺渠道参数」「缺区县」** —— 这就是"数据完善度工作"的抓手。

## 4. TOP5 榜单规则

### 4.1 排序与准入

- **准入条件**（防止"只有一条记录但字段全"的噪声设备霸榜）：必须有 `activation` 或 `order` 事件，即**产生了真实业务价值**。
- 按总分降序，**并列时依次比较**：链路完整度 → 身份可识别度 → 事件数 → 最近活跃时间。
- 榜单项展示：分数、档次标签、设备掩码、机型、渠道、地区、5 步打钩图、缺口清单。

### 4.2 榜单的两种形态

| 形态 | 内容 | 价值 |
|---|---|---|
| **🏆 数据完善度 TOP5** | 得分最高的 5 台 | 标杆样本，用来对照"理想链路长什么样" |
| **📉 缺口聚合榜**（建议一并做） | 各项检查点的**未命中设备数**排序 | 直接产出开发优先级：例如「访问侧缺 deviceId：110/112 台」→ 一目了然这是最大的坑 |

**缺口聚合榜比 TOP5 更有行动价值**，建议两个一起上。示例（用当前真实数据）：

```
访问侧缺 deviceId        110 / 112 台   ← 最大缺口（历史遗留）
缺渠道参数                100 / 112 台
缺区县                     88 / 112 台
缺机型                     84 / 112 台
缺短链点击                 98 / 112 台
时间顺序异常                 0 / 112 台
```

### 4.3 口径与防坑

1. **只统计有 device 的设备**，纯 IP 访客不进入榜单（无法判定身份）。
2. **模拟器/共享设备照常参评但打标记**，不排除——否则会掩盖"这类设备数据最全"的事实（模拟器往往参数最全）。
3. **分数随时间波动是正常的**：新数据补进来时低分设备会涨分。UI 要标注"按当前已有记录计算"。
4. **不要把分数导出成"用户价值"指标**（见 §1 的警示）。

## 5. 数据来源与计算

### 5.1 全部来自 `tracking_events`（无需新表）

```sql
-- ① 按设备聚合出打分所需的事实
select device_full,
       bool_or(kind='visit' or kind='go_click')            as has_visit,
       bool_or(kind='go_click' or kind='purchase_click')   as has_click,
       bool_or(kind='order')                               as has_order,
       bool_or(kind='redeem')                              as has_redeem,
       bool_or(kind='activation')                         as has_act,
       bool_or(kind='failure')                             as has_fail,
       max(channel)                                        as channel,
       max(ip)                                             as ip,
       min(ts) as first_ts, max(ts) as last_ts,
       count(*)::int as events,
       max(payload->>'model') as model,
       max(payload->>'rom')   as rom
from tracking_events
where ts >= now() - interval '30 days' and device_full <> ''
group by device_full;

-- ② 归属地用 ip_lookups 富化（复用 lib/geo-zh.resolveDisplayGeo）
select ip, region_zh, city_zh, district, country, region, city from ip_lookups where ip = any($1);

-- ③ 顺序校验：取每类事件的最早时间戳
select device_full, kind, min(ts) as t from tracking_events
where device_full <> '' and kind in ('visit','go_click','purchase_click','order','redeem','activation')
group by device_full, kind;
```

### 5.2 建议模块 `lib/user-score.js`

```
scoreDevices(days, opts) → {
  leaderboard: [ { device(masked), score, grade, dims:{identity,journey,attribute,geo},
                   steps:[bool×5], missing:[...], model, channel, region, city, events, lastTs } ],
  gaps:       [ { key, label, missCount, total, pct } ],   // 缺口聚合榜
  summary:    { devices, avgScore, byGrade:{A,B,C,D} }
}
```

- 一次 SQL 拉事实 + 一次 `ip_lookups` 富化，**在内存里算分**（设备量千级，毫秒级）。
- 读时计算，**不物化**（口径随规则调整立即生效）；若将来设备上万，再考虑每日快照表。

### 5.3 接口

| 接口 | 说明 |
|---|---|
| `GET /api/admin/health?section=stats&sub=user-score&days=30&limit=5` | TOP5 + 分布概览 |
| `GET /api/admin/health?section=stats&sub=data-gaps&days=30` | 缺口聚合榜 |

⚠️ 注意：`section=stats` 有 GET 守卫，**这两个是只读接口，放在守卫之后即可**（写操作才需要提前，参考 `tracking-backfill` 的 405 教训）。

## 6. 分期实施

| 阶段 | 内容 | 说明 |
|---|---|---|
| **一期** | `lib/user-score.js` + `sub=user-score` + `sub=data-gaps` + 画像汇总页两个卡片 | 纯读，不动写入侧，风险最低 |
| 二期 | 分数快照（每日存一份，用于看"采集健康度"随时间的变化曲线） | 新表 `user_score_daily(day, device_full, score, dims jsonb)` |
| 三期 | 与人工校正联动：`identity_overrides` 命中后重算分数 | 让修正立即反映到榜单 |

**建议先做一期**：它立刻能回答两个问题——"我们的数据采集到底打通了几成"（缺口榜）和"理想形态长什么样"（TOP5）。

## 7. 风险与边界

1. **分数会被误读为用户价值**：UI 必须在标题处写明"数据完整度 ≠ 消费能力"，否则运营会拿它做用户分层。
2. **权重是主观的**：当前权重（25/40/20/15）基于"身份可靠性 > 链路完整 > 属性"的判断，落地后建议观察一周分布再微调；建议把权重集中在一个常量对象里，便于调整（类似 §3.1 表格直接映射代码常量）。
3. **历史数据与新数据不可比**：2026-09-24 前后的设备，因为 `params` 列刚加、文档页埋点刚补，分数天然有断层。**上线后 1~2 周内的分数才有横向可比性**，UI 应标注起始日期。
4. **不要用分数做准入门槛**（例如限制低分用户激活），它是观察工具，不是风控规则。
5. **性能**：一期按设备聚合全窗口数据，设备到万级时需要加 `days` 限制或物化；当前千级无压力。
