# 删除后台「切换为本地缓存」功能的可行性分析

## 一、背景概述

后台管理页面 (`admin_Dx23.html`) 存在一个 **ADMIN_MODE** 机制，允许用户在两种数据读取模式间切换：

| 模式值 | 含义 | 数据来源 | 写操作 |
|---|---|---|---|
| `api-always` | 线上模式 | 每次实时请求 Postgres API | ✅ 允许 |
| `local-first` | 本地缓存模式 | 从浏览器 localStorage 读，后台静默 fetch 更新缓存 | ❌ 禁止（只读） |

切换入口位于 **设置 → 数据子面板 → 🔀 数据优先模式** (`admin_Dx23.html:3690-3708`)。

## 三、架构设计意图回顾

`local-first` 模式本质上是一个 **离线只读副本**：

```
                ┌─────────────────────────────────────────┐
                │           admin_Dx23.html              │
                │                                         │
  api-always ──▶│  直接 fetch API ──▶ Postgres (真实数据)  │
                │                                         │
  local-first ──▶│  先读 localStorage                    │
                │  同时后台 fetchAndCache 静默更新缓存     │
                │  写操作 → requireOnlineMode 拒绝 ❌      │
                └─────────────────────────────────────────┘
```

**设计初衷**：
1. **开发/离线使用**：网络不通时仍能打开后台查看数据
2. **多用户隔离**：不同浏览器有独立的本地缓存副本
3. **灾备兜底**：API 全挂了还能看到上一次缓存的数据

## 四、当前实际使用情况分析

### 4.1 后端已完全在线化

根据 `api/admin/products.js`、`api/admin/redeem-codes.js`、`api/admin/records.js` 等文件，后端所有 CRUD 操作均已稳定走 Postgres（或通过 `db-switches.js` 做主备切换）。Vercel 部署 + Neon/Upstash 数据库的稳定性已足够。

### 4.2 本地模式的几个硬伤

| 问题 | 影响 |
|---|---|
| **只读但不真正锁死**：`requireOnlineMode` 是前端门禁，任何开发者打开 DevTools 删掉 `admin_mode` 就能绕过 | 形同虚设的写保护 |
| **数据漂移**：localStorage 缓存过期后，不同机器看到的数据不一致 | 运维困扰 |
| **代码复杂度倍增**：每个读取函数都有 `if (ADMIN_MODE === ...)` 分支，维护成本 ×2 | 技术债 |
| **死代码**：`renderSyncStatusChip` 引用的 `syncModeLabel2`、`modeToggleBtn` 在 HTML 中不存在 | 噪音 |
| **localStorage 容量限制**：单个浏览器 ~5MB，兑换码/记录多时会触发 `⚠️ 本地存储空间不足` | 边界 bug |
| **导出/导入本地数据**：这套功能在真实线上场景没用——谁会把浏览器里的缓存当主备份？ | 冗余 |

### 4.3 引用次数分布

**写操作门禁（7 处，均可删除）：**

| 行号 | 操作 |
|---|---|

## 五、删除方案（逐步执行）

### 阶段 1：硬编码为 api-always（零风险，推荐先做）

将 `ADMIN_MODE` 直接硬编码为 `'api-always'`，所有写保护门禁自动失效，不改变任何行为：

```js
// 原来
var v = String(localStorage.getItem('admin_mode') || ADMIN_MODE);

// 改为：
ADMIN_MODE = 'api-always';
```

**收益**：立刻消除数据漂移风险，且不需要大规模删代码，可安全运行一段时间观察。

### 阶段 2：删除 UI 入口（HTML 部分）

删除 `admin_Dx23.html` 中：

1. **设置面板的"数据优先模式"整个卡片**（行 3690-3708）
2. **设置面板中的"删除保护"相关项**（这些是为了配合本地缓存的删除标记而设计的，行 3712-3743）
3. **本地数据管理按钮**（行 3766-3769 附近的导出/导入/清空按钮）
4. **顶部 syncStatusBar / syncBanner**（行 3164-3174，如果只服务于模式切换）

### 阶段 3：删除 JS 逻辑（推荐分多 commit）

| 类别 | 函数/变量 | 行数估算 |
|---|---|---|
| 模式状态 | `readAdminMode`, `setAdminMode`, `switchAdminMode`, `ADMIN_MODE` 变量 | ~30 行 |
| 模式渲染 | `renderSyncStatusChip` | ~25 行（且是死代码） |
| 写门禁 | `requireOnlineMode` + 7 处调用 | ~20 行 |
| localStorage 底层 | `STORAGE_KEY_*` (6个常量), `getLocalData`, `saveLocalData`, `_storageErrorShown`, backup sessionStorage 逻辑 | ~70 行 |
| 本地数据模型 | `codesMapToArray`, `codesArrayToMap`, `recordsLocalNormalize`, `getLocalCodesMap`, `saveLocalCodesMap`, `getLocalProducts`, `saveLocalProducts`, `getLocalCounters`, `saveLocalCounters`, `getLocalDeletes`, `saveLocalDeletes`, `fillProductFiltersFromLocal` | ~120 行 |
| 初始化 | `initLocalData` | ~55 行 |
| 渲染分支 | `renderProductsFromLocal`, `renderCodesFromLocal` + `loadStats/loadProducts/loadCodes/loadRecords` 中的 `if(local-first)` 分支 | ~200 行 |
| 后台静默缓存 | `fetchAndCacheProducts`, `fetchAndCacheCodes`, `fetchAndCacheRecords` | ~120 行 |
| 离线匹配 | `generateRedeemCodeLocal`, `matchCodeLocal` | ~30 行 |
| 本地导出导入 | `exportLocalData`, `importLocalData`, `clearAllLocalData`, `saveQuotaToLocal` | ~90 行 |
| **合计** | | **~760 行** |

### 阶段 4：清理残留的 `if (ADMIN_MODE === 'local-first')` 分支

将以下位置的分支彻底删除，只保留 `api-always` 的逻辑：

| 行号 | 函数 | 处理方式 |
|---|---|---|
| 5076 | `loadStats` | 删除 local-first 分支，直接走 API |
| 5353 | `loadProducts` | 删除 local-first 分支，直接走 API |
| 5552 | `loadCodes` | 删除 local-first 分支，直接走 API |
| 5865, 5903 | `loadRecords` / 激活记录渲染 | 同上 |
| 5962, 5990 | 记录为空时的提示语分支 | 简化为单一文案 |
| 6092, 6127 | 直接激活模块的 local-first 分支 | 删除 |
| 8937 | 统计报表中的 `if (ADMIN_MODE === 'api-always')` | 改为无条件执行 |

### 阶段 5：删除已无引用的 CSS

`sync-status`、`sync-banner` 等样式（行 2458-2504）如果只为本地缓存模式服务，一并移除。

## 七、风险评估

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| 某个页面忘记处理，local-first 分支被删后报 undefined | 🟡 低 | 阶段 1 先硬编码观察 1 周，确无异常再删代码 |
| 部分用户依赖离线查看功能 | 🟡 低 | 目前无已知离线用户；如需保留可改用 Service Worker 做真正的离线缓存（另一种方案） |
| `initLocalData` 中从 `/data/*.json` 加载的老数据路径可能有隐藏依赖 | 🟢 极低 | 搜索确认：后端 API 已统一，`/data/*.json` 是历史遗留静态文件 |
| exportLocalData / importLocalData 某些用户在用 | 🟢 极低 | 这两个函数是对浏览器缓存做 JSON 导入导出，不是主数据备份 |

## 八、结论与建议

### 可行性：✅ 完全可行

- 后端零耦合，删除纯前端逻辑不影响任何 API
- 已有稳定的 Postgres + Vercel 部署链路
- 本地缓存模式引入的数据漂移和维护复杂度远大于它的价值

### 推荐执行顺序

1. **第一优先级**：阶段 1（硬编码 `ADMIN_MODE = 'api-always'`），观察 3-7 天
2. **第二优先级**：阶段 2（删 UI 入口）+ 阶段 3-5（删 JS 逻辑），分批 commit
3. 每步 push 代码到远程仓库，保持可回滚

### 不建议的做法

- ❌ 一次性全删：9676 行的大文件，容易引入回归
- ❌ 保留 `ADMIN_MODE` 变量但只在一处赋值：留着就是留技术债，删干净
- ❌ 同时改后端 API：这次是纯前端清理，后端不用动
