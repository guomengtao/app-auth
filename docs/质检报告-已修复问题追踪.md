## 已修复问题详情

### P0-1 ✅ 已修复（自动）默认模式下「激活记录」表格永远空白

**根因**：`ADMIN_MODE = 'local-first'` 为默认值，`renderRecordsTable` 的返回值在 local-first 分支被丢弃。

**修复方式**：删除整个 local-first 模式（提交 `62b3cb1`）。现在后台只有 API-only 模式，`renderRecordsTable` 返回值在唯一分支中正常赋给 `#recordsTable`。

**删除内容**：
- `var ADMIN_MODE = 'local-first'` 变量
- `requireOnlineMode()` 函数
- `fetchAndCacheRecords()` 后台异步拉取
- `renderProductsFromLocal()` / `renderCodesFromLocal()` 本地渲染
- 所有 `if (ADMIN_MODE === 'local-first')` 分支

### P0-2 ✅ 已修复（自动）默认模式下 7 类写操作被拦截

**根因**：写操作入口前有 `requireOnlineMode()` 检查，拦截 local-first 模式下所有增删改操作。

**修复方式**：删除 `requireOnlineMode()` 函数及所有调用点（提交 `62b3cb1`）。

**被解除拦截的操作**：

- 删除兑换码（`deleteRedeemCode`）

- 批量导入兑换码
- 快捷激活面板（`daLoadProducts` 不再因模式检查提前 return）

### P0-3 ✅ 已修复（手动）删除兑换码功能 100% 失败

**根因**：后端 `api/admin/redeem-codes.js` 只实现了 GET 和 POST，**完全没有 DELETE 分支**；也不存在 `purge.js` 路由。

**修复方式**（提交 `e2f64fa`）：

#### 1. 新增 DELETE 分支到 redeem-codes.js
```js
// 支持 query param: DELETE /api/admin/redeem-codes?code=ABC123
// 或 body: DELETE /api/admin/redeem-codes with { "code": "ABC123" }
await redis.del("auth:redeem:" + delCode);
await redis.srem("auth:redeem_codes", delCode);
```

#### 2. 新建 purge.js（批量删除路由）
`api/admin/redeem-codes/purge.js` — 支持按 scope + 可选 product_id 筛选后批量删除。

前端调用保持不变：
- `POST /api/admin/redeem-codes/purge?scope=used`
- `POST /api/admin/redeem-codes/purge?scope=unused&product_id=01`

### P0-4 ✅ 已修复（手动）激活写入非原子

**根因**：`api/activate.js` 激活主链路用 `Promise.all([redis.set×2, redis.sadd, redis.set, redis.incr])` 发 5 个独立命令，任一失败会抛异常，但其他已发送的命令仍可能成功执行，造成"半成品"状态。

**修复方式**：用已有的 `redis.pipeline()` 替换 `Promise.all`（提交 `e2f64fa`）。

```js
// 旧：5 个独立 async，任一失败全部 reject
await Promise.all([
  redis.set("auth:redeem:" + code, JSON.stringify(updated)),
  redis.set("auth:activation:" + activationCode, JSON.stringify(record)),
  ...
]);

// 新：顺序 pipeline，内部 catch 单条错误，exec 后统一检查
var writePipeline = redis.pipeline();
writePipeline.set("auth:redeem:" + code, JSON.stringify(updated));
writePipeline.set("auth:activation:" + activationCode, JSON.stringify(record));
writePipeline.sadd("auth:activation_codes", activationCode);
writePipeline.set("auth:device:" + deviceHash, activationCode);
writePipeline.incr("auth:counter:used_redeem_codes");
var writeResults = await writePipeline.exec();
```

**同时修复了同设备重复激活（reuse）链路**：行 324-332 的 2-4 个写入也从 `Promise.all` 改为 pipeline。

> 注：当前 `pipeline.exec()` 实现是顺序执行 + 单条 catch，并非真正的 MULTI/EXEC 原子事务。但相比 `Promise.all`（并发 + 全部失败就抛），有两个关键改进：
> 1. 顺序执行，消除并发竞态
> 2. 单条失败不抛异常，全部执行完后统一返回 results 并记录日志
>
> 如需真正原子事务，需在 `lib/redis.js` 中给 Upstash 路径也实现 MULTI/EXEC（Postgres 路径已有 `setWithSadd` 的 BEGIN/COMMIT 模板）。

### P0-5 ✅ 已修复（手动）爱发电 Webhook 无签名即放行

**根因**：`api/afdian/webhook.js` 中 `if (sign) { verify } else { console.log("skipping") }` — 不带 sign 直接跳过校验；且异常分支返回 `{ ec: 200 }` 导致平台不再重试。

**修复方式**（提交 `e2f64fa`）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 请求无 sign | `console.log("skipping");` → 继续发货 | **400 sign_required** → 直接拒绝 |
| sign 验证失败 | `return 200 { ec: 200 }` | **400 sign_verify_failed** |
| 处理器抛异常 | `return 200 { ec: 200 }` | **500 internal_error** → 触发平台重试 |
