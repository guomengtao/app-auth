## 2. 诊断：302 跳转被阻塞（实测确诊）

### 2.1 实测数据

对生产环境 `/go/ev-timetable`（购买跳转链接）连续请求三次：

```
第1次: 总耗时 5.119s | 首字节 5.119s | 302
第2次: 总耗时 1.792s | 首字节 1.792s | 302
第3次: 总耗时 20.0s+ | 首字节 0s    | 000（超时无响应）
```

**首字节时间 = 总耗时**，说明整个延迟都发生在服务端返回之前，不是网络问题。

### 2.2 代码根因

`api/go.js` 第 149 行 `pushPurchaseClick()` 内部有 5 个**串行**外部调用：

1. `geoDistrict.getStoredGeo(ip)` — 查 IP 归属地缓存
2. `geoDistrict.getDistrict(ip)` — 调用腾讯 IP 定位 API
3. `md.createMessageDelivery()` — 写消息投递表
4. `fetch(Upstash /xadd)` — 写 Redis Stream
5. `fetch(Upstash /publish)` — 发布 Pub/Sub

而跳转处的代码是：

```js
var pushTask = pushPurchaseClick(...);
await Promise.race([pushTask, new Promise(r => setTimeout(r, 5000))]);
res.setHeader("Location", entry.target_url);
return res.status(302).end();
```

**`await` 在 302 之前。** 用户必须等上述 5 个调用跑完（或 5 秒超时）才能被重定向。

第 1 次实测的 5.119s 正是撞上了这个 5 秒上限。

### 2.3 引入时间与数据吻合

| 提交 | 日期 | 动作 |
|---|---|---|
| `4af5186` | **9-23** | 把 fire-and-forget 改成 `await Promise.race`，理由是"推送链被冻结截断、丢失通知" |

订单转化率：

| 周 | 点击 | 订单 | 转化率 |
|---|---|---|---|
| W39 | 69 | 27 | **39.1%** |
| W40 | 67 | 15 | **22.4%** |
| W41 | 81 | 14 | 17.3% |
| W44 | 69 | 11 | **15.9%** |

W39 是 9-21~9-27，改动发生在 9-23——**该周前半段仍是旧逻辑，所以它是混合值**。W40 起完整生效，直接跌到 22%，之后稳定在 16–17%。

**时间点、量级、方向全部吻合。这不是相关性推测，是首字节实测 + 代码路径双向确认。**

### 2.4 用户侧感受

移动端点击"购买"→ 页面转圈 2–5 秒无反应 → 大概率判定"点了没用"→ 退出。

这解释了那个最反直觉的现象：**点击量完全正常（69→69），订单少了一半**。人来了，也点了，但没等到页面。

### 2.5 修复方案（低风险，不需要动业务逻辑）

项目里**已经有** `background.run()`（Vercel `waitUntil` 封装），`visitor_log` 和 `ip_warmup` 都在用它。唯独 `pushPurchaseClick` 用了 `await`。

改法：把跳转前的 `await Promise.race` 换成

```js
background.run(pushTask, "purchase-click-push");
```

- 用户立刻拿到 302（首字节应降到 100–300ms 量级）
- 推送链由 Vercel `waitUntil` 保证跑完，**不会丢通知**（这本来就是 9-23 那次改动想解决的问题）
- 改动量：约 10 行，单文件，无 schema 变更

**这一条修完，转化率应回到 35% 以上。是本次所有动作里性价比最高的一项。**

## 3. 你的三条建议，按代码实际能力修正

我上一轮的建议有两处建立在"猜测已有能力"上，核对后需要修正。

### 3.1 建议②「补埋点跳转回流」→ **已有，不需要新埋点，需要修覆盖率**

现状核对：

| 环节 | 记录数 | 带设备号 | 覆盖率 |
|---|---|---|---|
| `purchase_click` | 403 | 154 | **38%** |
| `order` | 160 | 79 | **49%** |
| `activation` | 242 | 223 | 92% |
| 点击设备 ∩ 订单设备 | — | **仅 21 台** | 点击设备的 29% |

机制已经存在：`lib/afdian-processor.js` 的 `extractDeviceIdFromRemark()` 从付款备注里抠设备号，还有 `remark-device / same-ip-24h / fallback` 三级归因（字段 `channel_basis`）。

**但前端没有任何地方提示用户填备注**（已 grep 全站确认）。所以这是**被动捡漏**：用户自愿填就捡到，不填就丢。49% 的订单带设备号 ≈ 大约一半用户自己填了。

**所以真正缺的不是"回流埋点"，是设备号的传递链**：

```
用户点击 /go/xxx?deviceId=abc
   → purchase_click 记录了 deviceId ✅
   → 302 跳转到 entry.target_url
   → ❌ deviceId 没有拼进跳转 URL（代码里 paramDeviceId 只喂了埋点）
   → 爱发电侧完全不知道是谁
   → 用户下单，只能靠他自己手填备注才能关联回来
```

`api/go.js` 最后一行是 `res.setHeader("Location", entry.target_url)`，**原样抛出，不带任何参数**。

三个提高覆盖率的选项（不互斥）：

| 选项 | 做法 | 提升 | 代价 |
|---|---|---|---|
| A | 跳转 URL 拼 `?remark=deviceId` 之类参数（需确认爱发电是否透传到订单） | 待验证 | 需实测爱发电是否吃这个参数 |
| B | 在购买引导页**明确提示**"付款备注请填 xxx" | 高 | 增加下单摩擦，可能反而降转化 |
| C | 维持现状，靠 44 条 `same-ip-24h` 兜底 | 0 | 归因长期只有一半 |

**我的判断：B 不要做。** 在一个已经因为等待 5 秒而掉一半转化的环节上再增加"请填备注"，风险大于收益。先做 A 的可行性验证。

### 3.2 建议③「激活成功回传单号」→ **已有 34%，是覆盖率问题不是缺失**

`api/activate.js` 已记录 `outTradeNo`，`activation` 事件 242 条中 83 条带单号（34%），其中 72 条能与订单对上。

剩下 159 条不带单号的原因很明确：**用户是手环填码激活的，此时他手上只有码，没有单号**——除非页面把单号一起带过去。

所以这不是"漏做"，是"结构上拿不到"。要补齐需要：激活落地页 URL 带上 `?order=xxx`，且用户从订单通知点进来（而不是自己翻聊天记录找码）。

**优先级低于 302 修复。**

### 3.3 关于"后台已有完善的追踪分析"

确认存在，我之前看数据库是偏颇的：

- `lib/user-journey.js`（950 行）：可按订单号反查 `getOrder / getRedeem / getActivation / findActivationsByDevice / findFailuresByDevice / visitorLogsByIp`，还有 `ipGeoMap` 和证据链拼装（第 874 行会输出"订单备注里带出了 deviceId"这类判定理由）
- `lib/tracking.js`：`funnel(days)` 漏斗、`portrait(days)` 画像、`enrichIdentity` 手机↔手环身份合并
- 后台侧可看单笔订单的完整旅程，比我在 Supabase 里跑聚合精确得多

**结论：后台能力不缺，缺的是"跨周期趋势"这一层视角**——后台擅长看"这一单发生了什么"，不擅长看"转化率这五周为什么在跌"。这次的 302 发现就是靠趋势对比才浮出来的。

## 4. 爱发电落地页：三种形态的取舍

你的实测：链接打开先落到爱发电登录页，微信扫码后才进商品页；但进店铺页/产品列表页则可以免登录先浏览。

| 形态 | 现状 | 优点 | 缺点 |
|---|---|---|---|
| **商品页直链**（当前 `ifdian.net/item/xxx`） | 现在用的 | 一步到位，无选择负担 | 先撞登录墙，看不到产品介绍，信任建立为零 |
| **店铺页** | 可选 | 免登录先看，有"这是一家真店"的信任感 | 多一次点击才到商品 |
| **产品列表页** | 可选 | 同上，且能展示产品矩阵 | 产品一多就产生选择负担；用户可能"选来选去弄乱了"就跑了 |

**判断：这件事的优先级排在 302 之后，且不应作为"修复订单"的手段。**

理由：
1. 落地页当前状态是**长期既有**的，不能解释 9 月底的突变（你自己也指出了这点，我同意）
2. 改落地页是**改变转化路径结构**，影响面比修 302 大得多，但预期收益小得多
3. 产品矩阵还在扩张期，列表页的"选择负担"风险会随产品数量上升而放大

**建议做法**：302 修完之后，用**现有埋点做一次对照**——把 target_url 复制一份配成店铺页，两个 slug 各投一半流量（`go:mapping` 本来就支持多 slug），跑两周看转化率。有数据再定，不要凭感觉改。

## 7. 购买来源构成与归因缺口

> ⚠️ **本节已于 2026-11-03 重写。** 初版的「手表二维码扫码占 53%」是**错误口径**，已作废。
> 错误原因：用 `c`（渠道位标识）的 `t-` 前缀推断设备来源。`c` 是投放位置的人工编号，
> 任何链接带上它都会显示这个值，它与「用户是否从手环点进来」无关。
> 正确判据是**点击是否携带设备维度参数**（`t` 设备类型 / `p` 型号 / `s` 屏幕形态 / `w h` 分辨率 / `deviceId`），
> 这些只可能由手环端的 `device.getInfo()` 上报。

### 7.1 真实来源构成（405 次购买点击，按设备维度重分）

| 分类 | 判定规则 | 次数 | 占比 |
|---|---|---|---|
| **确证来自手环** | 带 `t`/`p`/`s`/`w`/`h` 任一设备维度 | **101** | **24.9%** |
| 只有 deviceId，无型号/屏幕 | 仅带 `deviceId` | 49 | 12.1% |
| **仅渠道位 c，无任何设备维度** | 有 `c`，其余全空 | **207** | **51.1%** |
| 完全无参数 | query 为空 | 48 | 11.9% |

**结论修正**：能确证「从手环点进来」的是 **101 次（24.9%）**，不是 53%。
初版把 207 次「只有渠道位」的点击也算进了手环来源，虚高了约一倍。

关键在于这 207 次：它们**不是「不是从手环来」，而是「从哪来无法证明」**——
可能是手环端取参失败、也可能是用户把链接复制到了微信/网页再点。
现有埋点无法区分这两者，这是本节最需要修的地方（见 7.3）。

### 7.3 参数丢失是静默的（真正的 P0 数据缺陷）

按渠道位 `c` 横向对比「带型号比例」，差异大得不合理：

| `c` 渠道位 | 点击 | 带型号 | 比例 |
|---|---|---|---|
| `g` | 30 | 29 | **97%** |
| `t-10-r` | 17 | 16 | **94%** |
| `t-9p-d` | 69 | 39 | 57% |
| `t-w-r` | 21 | 7 | 33% |
| `t-b9-d` | 17 | 1 | **6%** |
| `t-10-d` / `t-s4-d` / `t-w-d` / `t-10p-d` / `t-9-d` | 80 | 0 | **0%** |
| `apk-fast` / `ev-guide` / `q` / 无 | 143 | 0 | 0%（正常） |

同一个 `t-` 前缀，有的 94%、有的 0%。**如果是渠道本身决定的，不会出现这种分布**——
真正的变量是「这一次调用取参成不成功」。

根因在 `class-schedule/src/pages/activation/shared/activation-context.js`：

```js
_getInfo: fail / 异常 → _infoParams = ''      // 静默置空，无任何标记
_fallback: deviceId 取失败 → _deviceId = ''    // 静默置空
_build:  base + '?deviceId=' + '' + '&' + ''   // 结果只剩 &c=xxx
```

取参失败后 URL 变成 `?deviceId=&c=t-10-d`，`deviceId` 为空被丢弃，
`_infoParams` 为空也被丢弃，**最终数据里只剩一个 `c`**。
从数据库看，它和「用户从网页点进来」完全一样。

**这是本节最重要的一条**：不是「手环用户少」，而是
**手环用户的参数丢了，且丢得无声无息**。修法见 7.5 第 ② 条。

### 7.4 未付费用户规模（「只用不买」到底有多少）

这是此前算不出来的数，本次用设备维度交叉验证：

| 口径 | 数量 | 说明 |
|---|---|---|
| 用过同步器的手机 | **72 台** | `watch_device_id` 去重 |
| 其中出现在激活记录里（已付费） | 38 台 | 53% |
| **从未激活** | **34 台** | **47%** |
| 见过同步器但从未点过购买按钮 | 37 台 | 51% |

按首次出现周看「从不购买」占比：W41 61%、W42 50%、W43 52%、W44 50%。

**结论：约一半装机用户始终未付费，但该比例五周保持稳定，没有恶化趋势。**

这否定了「近期绕过收费的漏洞导致越来越多人不升级」的假设——如果漏洞是新增的流失源，这个比例应该随时间上升。它没有。

| ③ | 服务端额外记降级字段 | `api/go.js` | — | ❌ **不做**。`params` 已完整保留 `i=f`，加冗余字段只增加部署风险 |

#### 7.5.1 向下兼容硬约束（改任何埋点前必读）

已发出去的安装包**无法升级**，老用户的 URL 参数写死在旧包里。因此所有埋点改动必须遵守：

1. **只追加，不改动**——绝不修改既有参数名、顺序、含义，也不动 `AFDIAN_BASE` 等直链常量。
2. **新参数必须可缺失**——老包不会发新参数，服务端与统计脚本必须在缺失时退化为改造前的行为。
3. **deviceId 缺失时保持空值，绝不写假 ID**——`deviceId=none` 这类写法会被服务端当作真实
   `device_full` 入库，造成不可逆污染。URL 里的空值本身已表达该状态，**不额外加标记**。
   （本节初稿曾建议写 `none`，二稿曾建议加 `dn=1`，两者均已废弃。）
4. **失败标记不能被当成失败结论**——`i=f` 只代表「这次没取到」，不代表「这个用户不是手环用户」。
5. **成功场景不追加任何字节**——二维码密度已到极限（实测长码 190 字符），
   任何只为「好看」的新增参数都会挤占识别余量，须有明确统计收益才加。

#### 7.5.2 两态判据（服务端与统计的唯一口径）

| URL 特征 | 含义 | 统计处理 |
|---|---|---|
| **无 `i` 参数** | 新包**取参成功**，或**老包**（老包不发该参数） | 有 `p`（型号）即按型号归类；无任何设备参数则归「未知老包」 |
| `i=f` | 新包**明确取参失败** | 计入「手环端取参失败率」分子 |

**为什么成功不标记**：成功场景的码是最长的（190 字符），失败场景只剩 `deviceId=i=f=c`
（96 字符），二维码压力极小。只在失败时标记，等于**用最短的码承担全部标记成本**。

**代价与补偿**：新包的「成功样本量」无法直接计数，因此

- 失败率 = `i=f` 条数 ÷ 「带 `deviceId` 且无 `i=f`」条数（近似，分母含老包成功样本，会**低估**）
- 要精确切分，在发布新包时改 `c` 渠道后缀（如 `t-10-v2`），用渠道位区分包版本——
  这条零字符成本，是与老包分期的正确做法

#### 7.5.3 混合期统计纪律

新包上线后，一段时间内会**新老包数据混在一起**。必须遵守：

- 老包既会成功也会失败，且**两者都不带 `i`**——所以「无 `i`」不能当作「成功」，
  只能当作「老包或有 `p` 的成功样本」；
- `i=f` 是**确定的下界**：它一定是失败，不会误判；
- 要得到真实失败率基线，须等新包覆盖率足够，或直接用 `c` 渠道后缀切出纯净样本；
- 判断「手环来源占比」时，老包数据只能确认下界（带型号的），不能确认上界。

#### 7.5.4 实测证据（改动前备份 vs 当前实现，同场景逐字对比）

五个场景 × 三个 URL 生成函数（购买 / 兑换 / APK），逐一对比「剥掉 `i=f` 后的 URL
是否与引入标记之前逐字一致」：

| 场景 | 引入前 | 当前 | 长度 | 兼容 |
|---|---|---|---|---|
| 取参成功 + 有 deviceId | `...&l=zh&c=t-10-r` | **完全相同** | 190 → 190 | ✅ 零增长 |
| getInfo fail | `...deviceId=uuid&c=t-10-r` | 同左 + `&i=f` | 92 → 96 | ✅ |
| device 模块缺失 | 同上 | 同左 + `&i=f` | 92 → 96 | ✅ |
| deviceId 空 + 取参成功 | `...&l=zh&c=t-10-r` | **完全相同**（无 `dn`） | 158 → 158 | ✅ 零增长 |
| 两者皆失败 | `...deviceId=&c=t-10-r` | 同左 + `&i=f` | 60 → 64 | ✅ |

**判定结果：成功场景零增长，旧参数零丢失、零变更，全部场景通过。**

**② 的价值不在于修好什么，而在于让问题可见。** 现在那 207 次点击里到底有多少
是「手环端取参失败」、多少是「用户从别处点进来」，完全是黑箱。
打上标记、等新包铺开一周后就能分开，那时再谈优化目标才对。

#### 7.5.5 参数语义订正：`m` 与 `p` 不是重复字段

这条是核实时发现的，必须记下来，否则以后还会误判。

`docs/激活页面参数升级方案.md` 的设计意图是：`m` = model（人可读型号名，例 `Watch S4`）、
`p` = product（产品代号，例 `vela_ws4`），两者本是不同维度，**设计没有错**。

但 Vela 真机 `device.getInfo()` 的实际返回值与之不符（全表统计）：

| 参数 | 实际取值 | 取值种类 | 结论 |
|---|---|---|---|
| **`m`** | 恒为 `"ap"`（模拟器为 `Emulator-Vela`） | **2 种** | 常量，无区分度 |
| **`p`** | `Xiaomi Smart Band 10` / `11` / `10 Pro` / `9 Pro` / `9`、`REDMI Watch 6`、`Watch S4` / `S5 eSIM` / `S3` | **6 种** | **唯一机型来源，不可删** |

即：当时按快应用规范推断的字段语义（`m` 更有信息量）与 Vela 实际实现**正好相反**。
这不是当初定错，是规范文档与实现不一致，只有跑起来才会暴露。

**因此：**

- **绝对不能删 `p`**——删了就没有任何机型信息，7.2 的机型分布表、消费力分析全部失效；
- 删 `m` 只省 5 个字符（`&m=ap`），**不改变 QR 版本**，属无收益优化，不做；
- 长码实测 **190 字符**（deviceId 32 + 型号 32 + 其余参数），对应 **QR Version 10（53×53）**。
  要降到 Version 9 需压到 ≤182 字符，只能缩写型号名或屏幕形态，
  两者都改语义、需维护映射表、违反向下兼容硬约束——**结论：不动，现状即最优**。

### 7.6 完全无法统计的部分（技术限制，非埋点缺失）

手环（Band 系列）快应用**没有独立网络能力**，因此：

- 用户从第三方平台直接下载 APK、不经任何网页入口 → 我们不知道他装了多少次
- 手环上的使用行为（打开次数、停留）→ 无法上报

这不是埋点没做，是**通道不存在**。想解决只有两条路：要么让 APK 首次启动强制走一次上报（已部分实现，见 `app_open` 事件），要么等 Watch 系列的联网能力（见第 8 节）。

### 8.2 可行性：三个必须先验证的未知

Vela 快应用框架本身提供 `@system.fetch`，Watch S4/S5 具备 WiFi/eSIM，理论上支持独立联网。但以下三点**不能靠推断**：

### 8.3 探针方案（成本最低的第一步）

**不要先写完整埋点。** 先做一个只做一件事的探针：启动时发一次 ping，成功与否都静默。

```js
// src/utils/ping.js
import fetch from '@system.fetch'

export function pingProbe() {
  try {
    fetch.fetch({
      url: 'https://app-auth.gudq.com/api/ev?ping=1&v=probe',
      method: 'GET',
      responseType: 'text',
      success: (res) => console.log('[probe] ok', res.code),
      fail: (err, code) => console.log('[probe] fail', code, err),
    })
  } catch (e) {
    console.log('[probe] not supported')
  }
}
```

在 `pages/index` 的 `onInit` 里调一次。三条判定：

- 编译报 feature 不支持 → V1 不通过，方案终止
- 编译通过但真机 fail → V2 不通过，方案终止
- 请求成功 → 通道可用，进入 8.4

**先决条件**：`/api/ev` 需要一个不吃参数、不写库、直接返回 200 的 ping 分支，避免探针本身污染数据。

### 8.4 通道打通后的完整方案（三条硬约束）

| 约束 | 具体做法 | 理由 |
|---|---|---|
| **不阻塞 UI** | 上报一律在 `onInit` / `onHide` 的异步回调里，不 `await` | 手表的响应速度是产品体验的一部分 |
| **失败静默** | `fail` 回调只写本地日志，不弹提示、不重试当前请求 | 联网不稳定时不能影响使用 |
| **本地攒批** | 写入 `@system.storage`，攒够 N 条或跨天再批量上报 | 减少请求次数，省电 |

建议采集的最小字段集：

```
device_model / rom_version / app_version   设备与环境
open_count / last_open_ts                  使用频率
page_dwell_ms                              停留时长（按页面）
connect_result                             与手机连接是否成功
```

**与手环线共用的好处**：字段口径对齐现有 `app_open` 事件，可以直接并入 `tracking_events`，无需新表。

## 9. 区域迁移与第三方跳转层（2026-11-03 晚定稿）

### 9.1 先把三个组件的真实位置钉死

这一步之前一直没做，导致「迁不迁香港」只能凭感觉。实测：

| 组件 | 证据 | 真实位置 |
|---|---|---|
| Supabase 数据库 | `.env` 中连接串 `aws-0-**us-east-1**.pooler.supabase.com` | **美东 us-east-1** |
| Vercel 函数 | 响应头 `x-vercel-id: sin1::**iad1**` | **美东 iad1** |
| Upstash Redis | `dig` CNAME 链 → `global-latency` → `global-apn1`，A 记录 `13.196.80.13` = `ap-northeast-1` | **东京**（Global 就近） |

所以当前一次购买点击的真实路径是：

```
中国用户 → [200~250ms 跨洋] → 美东 iad1（函数）→ [<10ms] → Upstash 美东副本 → 302
                                        ↓ waitUntil 异步
                                   [<5ms] → Supabase 美东
```

**跳转慢的 200ms 是物理距离，不是代码问题。** 之前实测热态 0.58–0.75s 里，约 0.25s 是这段跨洋 RTT，其余是 TLS 握手与函数自身开销。

### 9.2 结论：迁 hkg1，且代价接近于零

之前不敢迁的顾虑是「如果 Supabase 在美东，迁香港会赔上 DB 延迟」。
这个顾虑现在被否掉，理由是**读写路径分离**：

| 路径 | 是否在用户面前 | 迁香港后 |
|---|---|---|
| `redis.hget`（读配置） | ✅ 在 302 之前 | 已用内存缓存消掉（见 9.3），冷启才走一次，且 Upstash 从香港就近东京，比从美东访问更近 |
| `visitorLog` / `tracking` / `pushPurchaseClick`（写库） | ❌ 全在 `background.run`（waitUntil） | 函数→DB 从 <5ms 变成 ~250ms，**用户完全感知不到**，只影响实例存活时长（远小于 30s 上限） |

即：**迁香港只改善用户可见的那一段，代价全部落在用户看不见的异步段。** 这是纯赚。

配置：`vercel.json` 顶层 `"regions": ["hkg1"]`。Hobby 套餐只允许 **1 个**区域（Pro 5 个 / Enterprise 全部），所以这是单选，不是多区域。

预期收益：中国用户 TTFB 减少约 **200ms**，冷启动（原来 1.4–5.8s）因地理距离缩短也会明显下降。

### 9.3 配套改动：跳转路径上的同步 IO 必须清零

光迁区域不够。302 之前只要还有一次跨洋 `await`，迁到哪都被拖住。所以 `api/go.js` 的配置读取改为三层降级：

```
1. 内存新鲜（60s）    → 零网络，直接 302
2. Redis 正常         → 回填内存
3. Redis 超时(>1.5s)/报错 → 用内存陈旧值（6h 内）
4. 仍无值             → 静态兜底表 GO_FALLBACK_MAP
5. 全都没有           → 404（此时确实无从得知该跳哪）
```

两个关键点：

- **`hget` 加 1.5s 上限**。原来是裸 `await`，Redis 异常时最坏 20s 超时才报错，期间用户白屏。
- **读失败 ≠ 不存在**。原代码 `if (!raw) return notFound(...)`，把「Redis 挂了」和「这个 slug 不存在」混为一谈，一次 Redis 抖动就能让所有短链变成 404。现在用独立标记区分。

实测（Playwright 无关，纯 handler mock）：

| 场景 | 结果 | 耗时 |
|---|---|---|
| Redis 正常 | 302 → 真实地址 | 1ms（缓存命中 0ms） |
| Redis 卡 9s | 302 → 静态兜底 | 1502ms |
| Redis 拒连 | 302 → 静态兜底 | 0ms |
| Redis 拒连 + 无兜底 | 404 | 0ms |

**副作用（必须知道）**：改 `go:mapping` 后最多 **60 秒**才全局生效。若要立刻生效，只能重启实例或等 TTL。这是拿「配置秒级可见」换「用户侧 200ms」，值。

### 9.4 「落库失败也要能跳转」——现在真的成立了

原话是对的，但原来的代码并没有做到：

- **写路径**：`visitorLog` / `tracking` / XADD 全部走 `background.run`（`waitUntil`），失败只打日志，302 照发 —— 这部分本来就是对的。
- **读路径**：这是漏洞。`await redis.hget` 失败直接 `catch → 500`，用户看到的是 Internal error，等于**数据库挂了就连跳转都没了**。现在已按 9.3 修掉。

结论：**只要静态兜底表里有的 slug，Supabase + Upstash 全挂也能把人送到爱发电。**

### 9.5 第三方跳转层：逐个体检后，建议不做

你的直觉是对的（"引进第三方也是很多坑"）。逐个否掉：

| 方案 | 能否做 302 | 致命问题 | 结论 |
|---|---|---|---|
| GitHub Pages | ❌ 只能 `meta refresh` / JS 跳 | 多一次 HTML 加载（**反而慢 100–300ms**）；丢 `Referer`（`ref` 字段直接废掉）；无法服务端计数；国内访问本身不稳 | 否决 |
| Gitee Pages | ❌ 同上 | 同上，且 Gitee Pages 已对个人关闭/需实名审核 | 否决 |
| Cloudflare Workers | ✅ 边缘 302，延迟极低 | 需把域名 NS 迁到 CF，影响现有 Vercel 部署；**CF 免费版国内线路晚高峰丢包严重**，把稳定问题换成了更不可控的稳定问题 | 暂缓 |
| 腾讯云 EdgeOne 免费版 | ✅ 边缘函数 302，国内 10–30ms | 需域名**备案**；多一跳；点击事件要双写回 Vercel，一致性成本高 | 备选后手 |
| 短链平台（缩我/新浪等） | ✅ | 完全黑盒：拿不到 IP/UA/来源/deviceId，等于**放弃全部归因**（而这正是第 7 章花大力气补的东西） | 否决 |

**核心理由：我们现在缺的不是 30ms，是「数据一条都不能少」。** 引第三方跳转层 = 在归因链最上游插一个不可控的黑盒，前面 7 章做的来源补全、deviceId 透传、参数丢失修复全都要重新对齐。

**后手**：如果迁 hkg1 后国内实测仍不达标（比如到 Vercel 香港被绕路），再考虑 EdgeOne 做**纯 302 转发层**——只负责跳转，事件通过带签名的异步请求回传 Vercel，绝不在第三方的库里落地数据。这是唯一可接受的形态。

### 9.6 遗留风险

1. `GO_FALLBACK_MAP` 需要在 Vercel 环境变量里配一份核心 slug 快照（JSON）。**没配就等于少一层保险**，建议至少配 `ev-timetable` 等已在二维码/安装包里流通的 slug。
2. 缓存 TTL 60s 意味着运营改价后最长 1 分钟才全网生效，改价请提前 1 分钟操作。
3. 迁 hkg1 需要重新部署才生效，且**部署后要用 `x-vercel-id` 验证**实际执行区域，不要只看配置项。

### 9.7 ⚠️ 订正：9.2 的结论是错的，当天已回滚（同日 13:14）

9.2 判定「迁香港纯赚」，前提是「`redis.hget` 走 Upstash（东京），香港比美东更近」。
**这个前提不成立。**

线上日志与数据实证：
- `db-switches` 显示 `{"upstash":"on","supabase":"on","neon":"on"}`，但这只表示「可用」

- 生产 `effectiveProvider = supabase` → 未命中 Upstash 分支 → 走 **Postgres proxy**
- `go:mapping` 的 23 条配置实际存在 Supabase 的 `kv_hashes` 表里（我最初查 Upstash 得到空数组，是因为查错了库）

后果：函数迁到 hkg1 后，每次 `hget` 变成「香港 → 美东」跨洋 SQL，超过我当时设的 1.5s 上限 → 判读失败 → 无兜底 → **全部短链 404**。

时间线：12:22 数据库仍有正常跳转记录 → 12:55 部署 hkg1 → 全站 `/go/*` 404 → 13:14 回滚 iad1 → 恢复 302。

**修正后的结论**：
| 项 | 判断 |
|---|---|
| 现在能不能迁香港 | **不能**。redis 数据在 Supabase 美东，函数必须待在 iad1 |
| 迁香港的前置条件 | ① `kv_hashes` 数据迁到 Upstash；② `USE_UPSTASH=true` 且日志出现 `[redis] MODE: Upstash Redis`；③ 迁移后先验证 302 再撤旧部署 |
| 今天真正落地的改善 | 配置内存缓存（60s）——热实例 60 秒内不再查一次 Supabase，这是当前唯一确定有效的提速 |
| 加超时的教训 | 给关键路径加超时**必须同时配兜底值**，否则等于把「慢」升级成「挂」 |

**方法论教训**：判断「某个服务在哪个区」不能靠环境变量、开关状态或依赖库的存在，只能靠**线上运行日志里的实际分支**。这次三个证据都指向 Upstash（开关 on、依赖已装、DNS 在东京），实际跑的是 pg 代理。
