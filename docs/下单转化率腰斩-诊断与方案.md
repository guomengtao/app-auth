## 2. 诊断：302 跳转被阻塞（实测确诊）

### 2.1 实测数据

对生产环境 `/go/ev-timetable`（购买跳转链接）连续请求三次：

```
第1次: 总耗时 5.119s | 首字节 5.119s | 302
第2次: 总耗时 1.792s | 首字节 1.792s | 302
第3次: 总耗时 20.0s+ | 首字节 0s    | 000（超时无响应）
```

**首字节时间 = 总耗时**，说明整个延迟都发生在服务端返回之前，不是网络问题。

### 2.2 代码根因

`api/go.js` 第 149 行 `pushPurchaseClick()` 内部有 5 个**串行**外部调用：

1. `geoDistrict.getStoredGeo(ip)` — 查 IP 归属地缓存
2. `geoDistrict.getDistrict(ip)` — 调用腾讯 IP 定位 API
3. `md.createMessageDelivery()` — 写消息投递表
4. `fetch(Upstash /xadd)` — 写 Redis Stream
5. `fetch(Upstash /publish)` — 发布 Pub/Sub

而跳转处的代码是：

```js
var pushTask = pushPurchaseClick(...);
await Promise.race([pushTask, new Promise(r => setTimeout(r, 5000))]);
res.setHeader("Location", entry.target_url);
return res.status(302).end();
```

**`await` 在 302 之前。** 用户必须等上述 5 个调用跑完（或 5 秒超时）才能被重定向。

第 1 次实测的 5.119s 正是撞上了这个 5 秒上限。

### 2.3 引入时间与数据吻合

| 提交 | 日期 | 动作 |
|---|---|---|
| `4af5186` | **9-23** | 把 fire-and-forget 改成 `await Promise.race`，理由是"推送链被冻结截断、丢失通知" |

订单转化率：

| 周 | 点击 | 订单 | 转化率 |
|---|---|---|---|
| W39 | 69 | 27 | **39.1%** |
| W40 | 67 | 15 | **22.4%** |
| W41 | 81 | 14 | 17.3% |
| W44 | 69 | 11 | **15.9%** |

W39 是 9-21~9-27，改动发生在 9-23——**该周前半段仍是旧逻辑，所以它是混合值**。W40 起完整生效，直接跌到 22%，之后稳定在 16–17%。

**时间点、量级、方向全部吻合。这不是相关性推测，是首字节实测 + 代码路径双向确认。**

### 2.4 用户侧感受

移动端点击"购买"→ 页面转圈 2–5 秒无反应 → 大概率判定"点了没用"→ 退出。

这解释了那个最反直觉的现象：**点击量完全正常（69→69），订单少了一半**。人来了，也点了，但没等到页面。

### 2.5 修复方案（低风险，不需要动业务逻辑）

项目里**已经有** `background.run()`（Vercel `waitUntil` 封装），`visitor_log` 和 `ip_warmup` 都在用它。唯独 `pushPurchaseClick` 用了 `await`。

改法：把跳转前的 `await Promise.race` 换成

```js
background.run(pushTask, "purchase-click-push");
```

- 用户立刻拿到 302（首字节应降到 100–300ms 量级）
- 推送链由 Vercel `waitUntil` 保证跑完，**不会丢通知**（这本来就是 9-23 那次改动想解决的问题）
- 改动量：约 10 行，单文件，无 schema 变更

**这一条修完，转化率应回到 35% 以上。是本次所有动作里性价比最高的一项。**

## 3. 你的三条建议，按代码实际能力修正

我上一轮的建议有两处建立在"猜测已有能力"上，核对后需要修正。

### 3.1 建议②「补埋点跳转回流」→ **已有，不需要新埋点，需要修覆盖率**

现状核对：

| 环节 | 记录数 | 带设备号 | 覆盖率 |
|---|---|---|---|
| `purchase_click` | 403 | 154 | **38%** |
| `order` | 160 | 79 | **49%** |
| `activation` | 242 | 223 | 92% |
| 点击设备 ∩ 订单设备 | — | **仅 21 台** | 点击设备的 29% |

机制已经存在：`lib/afdian-processor.js` 的 `extractDeviceIdFromRemark()` 从付款备注里抠设备号，还有 `remark-device / same-ip-24h / fallback` 三级归因（字段 `channel_basis`）。

**但前端没有任何地方提示用户填备注**（已 grep 全站确认）。所以这是**被动捡漏**：用户自愿填就捡到，不填就丢。49% 的订单带设备号 ≈ 大约一半用户自己填了。

**所以真正缺的不是"回流埋点"，是设备号的传递链**：

```
用户点击 /go/xxx?deviceId=abc
   → purchase_click 记录了 deviceId ✅
   → 302 跳转到 entry.target_url
   → ❌ deviceId 没有拼进跳转 URL（代码里 paramDeviceId 只喂了埋点）
   → 爱发电侧完全不知道是谁
   → 用户下单，只能靠他自己手填备注才能关联回来
```

`api/go.js` 最后一行是 `res.setHeader("Location", entry.target_url)`，**原样抛出，不带任何参数**。

三个提高覆盖率的选项（不互斥）：

| 选项 | 做法 | 提升 | 代价 |
|---|---|---|---|
| A | 跳转 URL 拼 `?remark=deviceId` 之类参数（需确认爱发电是否透传到订单） | 待验证 | 需实测爱发电是否吃这个参数 |
| B | 在购买引导页**明确提示**"付款备注请填 xxx" | 高 | 增加下单摩擦，可能反而降转化 |
| C | 维持现状，靠 44 条 `same-ip-24h` 兜底 | 0 | 归因长期只有一半 |

**我的判断：B 不要做。** 在一个已经因为等待 5 秒而掉一半转化的环节上再增加"请填备注"，风险大于收益。先做 A 的可行性验证。

### 3.2 建议③「激活成功回传单号」→ **已有 34%，是覆盖率问题不是缺失**

`api/activate.js` 已记录 `outTradeNo`，`activation` 事件 242 条中 83 条带单号（34%），其中 72 条能与订单对上。

剩下 159 条不带单号的原因很明确：**用户是手环填码激活的，此时他手上只有码，没有单号**——除非页面把单号一起带过去。

所以这不是"漏做"，是"结构上拿不到"。要补齐需要：激活落地页 URL 带上 `?order=xxx`，且用户从订单通知点进来（而不是自己翻聊天记录找码）。

**优先级低于 302 修复。**

### 3.3 关于"后台已有完善的追踪分析"

确认存在，我之前看数据库是偏颇的：

- `lib/user-journey.js`（950 行）：可按订单号反查 `getOrder / getRedeem / getActivation / findActivationsByDevice / findFailuresByDevice / visitorLogsByIp`，还有 `ipGeoMap` 和证据链拼装（第 874 行会输出"订单备注里带出了 deviceId"这类判定理由）
- `lib/tracking.js`：`funnel(days)` 漏斗、`portrait(days)` 画像、`enrichIdentity` 手机↔手环身份合并
- 后台侧可看单笔订单的完整旅程，比我在 Supabase 里跑聚合精确得多

**结论：后台能力不缺，缺的是"跨周期趋势"这一层视角**——后台擅长看"这一单发生了什么"，不擅长看"转化率这五周为什么在跌"。这次的 302 发现就是靠趋势对比才浮出来的。

## 4. 爱发电落地页：三种形态的取舍

你的实测：链接打开先落到爱发电登录页，微信扫码后才进商品页；但进店铺页/产品列表页则可以免登录先浏览。

| 形态 | 现状 | 优点 | 缺点 |
|---|---|---|---|
| **商品页直链**（当前 `ifdian.net/item/xxx`） | 现在用的 | 一步到位，无选择负担 | 先撞登录墙，看不到产品介绍，信任建立为零 |
| **店铺页** | 可选 | 免登录先看，有"这是一家真店"的信任感 | 多一次点击才到商品 |
| **产品列表页** | 可选 | 同上，且能展示产品矩阵 | 产品一多就产生选择负担；用户可能"选来选去弄乱了"就跑了 |

**判断：这件事的优先级排在 302 之后，且不应作为"修复订单"的手段。**

理由：
1. 落地页当前状态是**长期既有**的，不能解释 9 月底的突变（你自己也指出了这点，我同意）
2. 改落地页是**改变转化路径结构**，影响面比修 302 大得多，但预期收益小得多
3. 产品矩阵还在扩张期，列表页的"选择负担"风险会随产品数量上升而放大

**建议做法**：302 修完之后，用**现有埋点做一次对照**——把 target_url 复制一份配成店铺页，两个 slug 各投一半流量（`go:mapping` 本来就支持多 slug），跑两周看转化率。有数据再定，不要凭感觉改。
