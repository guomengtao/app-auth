# app-auth 测试方案 —— 怎么测、有几种方式、优劣对比

> 2026-10-07 · 单号 `evtask-X-evapp-auth-261007-zqn7x6`
> 结论先行：**没有银弹**。本项目 = 「无框架静态大页 + serverless 函数 + 两个外部服务（BandBBS / Supabase·Redis）+ 多会话共享工作区」，
> 所以测试必须是**分层组合**：本地纯逻辑打底，外部集成用只读探针，上线靠只读冒烟 + 受控写自检收口。

---

## 一、目标与范围

**要测的对象**

| 层 | 内容 | 特点 |
|---|---|---|
| 页面层 | `admin_Dx23.html`（1.28 万行自包含 HTML：CSS + 结构 + 378KB 内联 JS） | 无构建、无框架，语法坏了 = 白屏，编译期抓不到 |
| 前端逻辑 | `admin-bandbbs.js` 等外挂 JS（渲染函数、事件委托） | 直接操作 DOM，`api()` 走相对路径 |
| 函数层 | `api/**`（serverless：catalog、activate、review…）与 `lib/**`（bandbbs、auth、redis…） | 无状态函数 + 模块级可变状态（如 cookieJar），Vercel 上每次调用可能冷启动 |
| 数据层 | Upstash Redis、Supabase（pg） | 测试不能污染生产数据 |
| 外部服务 | BandBBS（登录/私信/评论）、爱发电兑换链接 | 会真发私信、真消耗奖品 |
| 交付管道 | git push → Vercel 自动部署；`.vercel/output` 预构建产物与源文件**硬链接** | 部署即上生产，无 staging |

**不测的**：第三方站点自身的功能正确性；Vercel 平台行为；手机端（EvOps 另有方案）。

## 三、测试方式清单（10 种）

### ① 语法 / 静态自检
**做法**：`node --check` 逐个 JS；对 `admin_Dx23.html` 的每个内联 `<script>` 做 `new Function()` 编译（现有 `admin-panel.inline-js.test.js`），顺带断言 CSS 变量存在、标签配平。
**能抓**：白屏级语法错误、用错 CSS 变量、标签错位（1.28 万行单文件最容易死在这）。
**成本/速度**：极低，秒级。**前提**：无。**副作用**：无。
**缺点**：只保证「能跑」，不保证「跑对」；正则断言会随页面演化过时（今天就有 2 条断言因并行会话新增子 tab 而失效）。
**现状**：✅ 已有，仍在维护。

### ② 纯逻辑单元测试（桩化 Redis / env，零网络）
**做法**：`require` lib 函数 + 内存假 Redis（`hgetall/hget/hset` 计数）+ 假 env；典型如 `rewardOne` 的 8 条断言（已发拦截 / 池空 / 选链接 / force 复用 / dryRun 零写入 / 缺参）。
**能抓**：分支逻辑错误、并发护栏语义、参数校验、**不写库就验证写库决策**。
**成本/速度**：低，毫秒级。**前提**：函数要「依赖注入」友好（redis 作参数传入 ✅ 本仓已是）。**副作用**：无。
**缺点**：覆盖不了真实 IO 行为（私信格式、Set-Cookie 细节）；桩和真实行为会漂移，需要用 ④ 的真实样本回填。
**现状**：⚠️ 零散存在（test/ 下几例），核心链路（rewardOne/rewardPoolList 掩码）尚无入库测试。

### ③ 渲染层单元测试（DOM 桩跑前端函数）
**做法**：`vm` + 假 `document`，直接调 `bbRenderReviewTable` / `renderBandBBSFlows` 等，对生成的 HTML 字符串断言（列数、按钮、data-* 属性、转义）。
**能抓**：表格少列/错列、按钮事件属性丢失、XSS（转义遗漏）、重构后渲染回归。
**成本/速度**：低，毫秒级。**前提**：渲染函数是「数据进、HTML 出」的纯函数（✅ 本仓大多是）。**副作用**：无。
**缺点**：桩 DOM 与真浏览器有差异；断言易碎（UI 一改就要改断言）；覆盖不了 CSS 视觉效果。
**现状**：⚠️ 本会话在 /tmp 写过两套（12+19 条断言），**未入库**。

### ④ 本地直连集成探针（真实凭据 + 真实外部服务）
**做法**：本地脚本加载 `.env`，走真实链路（如米坛 `login()` → `diagnosticLogin()` 4 步、`resource-detail` 只读），打印信号（`data-logged-in`、`_xfToken`、Set-Cookie）。
**能抓**：外部服务行为变化、登录/会话失效、**误判类 bug**（今天「`/login` 子串误判未登录」就是这么抓到的）、真实页面样本（回填 ② 的断言）。
**成本/速度**：中（数秒 + 需要凭据在 `.env`）。**前提**：凭据；外部服务可达。
**副作用**：⚠️ 只读操作安全；**严禁**在探针里直接做写操作（私信/消耗奖品）。
**缺点**：依赖外部服务在线与账号状态；凭据不能进仓（本地 `.env` 与生产不一致时，测不到生产语义——今天 JWT/CRON_SECRET 就对不上）。
**现状**：✅ 已有雏形（诊断按钮 + 今日 /tmp 探针），未固化为 test 文件。

### ⑤ 本地 HTTP 预览 + 反向代理（页面冒烟）
**做法**：本地静态服务 + `/api/*` 反代到生产（绕 file:// 的 CORS），无头 Chrome 截图 / DOM 断言；改哪个文件就挂哪个文件。
**能抓**：布局破版、CORS/路径类错误、Tab 切换白屏、「改了 A 文件页面没变化」。
**成本/速度**：中高（要写代理脚本；本机 headless Chrome 不稳）。**前提**：Node/Chrome。**副作用**：无（读生产只读接口）。
**缺点**：截图工具链脆弱（今天 Chrome 无头反复失败）；代理脚本是一次性成本；验证 UI 仍需人看。
**现状**：⚠️ 脚本在 /tmp（`bbprev/proxy.js`），可沉淀为 `scripts/preview.js`。

### ⑥ 本地函数运行（`vercel dev` / Build Output）
**做法**：`npx vercel dev`（或 `vercel build` 后跑 `.vercel/output/functions`）在本地起 serverless 函数，配合 ⑤ 的代理打真实函数代码。
**能抓**：函数层路由/环境变量/依赖打包问题——**部署前**就能发现「线上 unknown op」这类问题（今天的 `reward-one` 部署延迟就属于这类）。
**成本/速度**：中（首次要拉构建环境；`.env.local` 需与生产对齐）。**前提**：vercel CLI 登录。**副作用**：⚠️ 连的是本地 env 指向的真实 Redis/Supabase → 只读 op 安全，写 op 仍会动生产数据。
**缺点**：冷启动慢；与线上运行时（Vercel 平台注入的变量）仍有差异。
**现状**：❌ 未启用（CLI 已具备，零配置差异未知）。

### ⑦ Vercel Preview 部署（分支 → preview URL）
**做法**：开分支推送 → Vercel 生成 preview URL → 在 preview 上跑 ⑧ 的只读冒烟与人工点验。
**能抓**：部署配置问题、函数打包问题、页面集成问题——**最接近生产**且不影响正式域名。
**成本/速度**：中（一次 push 等构建 ~1-2 分钟）。**前提**：Vercel 项目开启 preview（默认开）。**副作用**：⚠️ 函数仍连生产 Redis/Supabase → 只读验证安全，写操作照样污染。
**缺点**：数据不隔离使「preview」价值打折；多分支并发部署互相覆盖 alias 时会混乱；多会话同时用会碰车。
**现状**：❌ 未使用（大家直接 push main）。

### ⑧ 生产只读冒烟（部署后核对）
**做法**：部署完成后 `curl` 一组只读 op（`stats` / `reward-pool-list` / `resource-detail`）+ 抓线上 HTML 断言新标记（如 `data-btab="flow"`）。
**能抓**：**部署没生效 / 回滚 / 构建产物过期**（今天 `reward-one` 线上 `unknown op` 就是这样发现的）。
**成本/速度**：极低（几条 curl，可写成脚本）。**前提**：无。**副作用**：无。
**缺点**：只覆盖只读面；需要「新改动有可断言的标记」的纪律（版本号 / 特征串）。
**现状**：⚠️ 人肉在做，未脚本化。**建议**：写成 `scripts/smoke.sh`，每次部署后跑一遍。

### ⑨ 生产受控写自检（上线后的写路径验证）
**做法**：约定好的「无害写」清单——`dryRun:1` 校验、测试私信发 `peipeijin`、自检任务 `task-register` 后置 `cancelled`、奖品导入用标记批次再清理。
**能抓**：只有真写才能暴露的问题（权限、字段、邮箱白名单、真实 XSS 过滤、私信格式）。
**成本/速度**：中。**前提**：写接口必须支持 dryRun / 测试账号；操作者有后台权限。**副作用**：⚠️ 受控但非零（会话记录、看板上会出现自检行——项目已有此惯例）。
**缺点**：无法完全自动化（需要后台登录态）；要防「自检数据忘了清」。
**现状**：✅ 惯例成熟（dryRun、peipeijin、自检任务），未固化为脚本。

### ⑩ 数据对账与巡检
**做法**：周期核对「两本账」——奖品池条目 vs `rewarded:<rid>` 记录 vs 奖品池 Tab 计数；看板聚合 vs 库中真实状态；孤儿数据扫描（`scripts/check-dbs.js`、`clean-orphans.js` 已有）。
**能抓**：静默丢数据、双写不一致、测试残留、并发撞车后的脏数据。
**成本/速度**：低（脚本化后可 cron）。**前提**：无。**副作用**：只读（清理类脚本需人工确认后跑）。
**缺点**：发现即「已发生」，是兜底而非预防。
**现状**：⚠️ 工具在，未形成周期。

## 六、本项目特有的坑 → 必须写进测试

1. **`admin_Dx23.html` 是硬链接**（与 `.vercel/output/static/` 同 inode）：`perl -i`、部分编辑器、`git checkout` 都可能断链 → 断言「源与副本同 inode 且 links=2」（今天断了两次，都已修复）。
2. **「含 `/login` 子串 = 未登录」是错的**：登录后的页面含 `/login/keep-alive`、`login_signup.min.js`。登录态判定只用 `data-logged-in`（已有 `looksLoggedOut()`，② 应拿真实页面样本做固定用例）。
3. **写操作必须有 dryRun**：`reward-one` 已支持；新写接口照此办理（⑨ 的前提）。
4. **列表接口掩码链接**：兑换码本体不得出现在 `reward-pool-list`（② 加一条断言）。
5. **多会话共享同一工作区**：❌ 永远不要裸敲 `git stash pop`（今天弹出别会话的保护 stash，4 文件 UU）；提交一律**逐文件 `git add`**；测试脚本里别用 stash 切换状态。
6. **`.env` 的 JWT_SECRET / CRON_SECRET 与生产不一致**：本地签不出生产凭据 → 凡需要鉴权的线上验证只能走后台人工（⑨），文档里如实标注「未测」。
7. **serverless 无持久内存**：模块级 `cookieJar` 不可依赖跨请求存活（`sendDm` 每次重新登录是对的）。
