## 〇、先更正一条错误结论

主报告曾写「Supabase `visitor_logs` 连不上，地域与设备维度缺失」，并归因为「本地代理对非 HTTP 端口（6543）做 TLS 拦截」。

**这条定性不完整，必须修正**：

| | 说明 |
|---|---|
| ❌ 错的 | 「本地读不到 Supabase 数据」 |
| ✅ 对的 | **PG 直连（6543）被代理拦截；但走 443 的 HTTPS REST API 完全可读** |

`GET {Ev_SUPABASE_URL}/rest/v1/visitor_logs?select=*` 带 `apikey` + `Authorization: Bearer <service_role>` 头，
**HTTP 206 正常返回**。代理只对非 HTTP 端口做 MITM，443 是放行的——之前没试这条路是排查上的疏漏。

**可复用口径**：Supabase 读数据**优先走 REST API（443）**，不要卡在 PG 直连上。

## 一、最重要的发现：近六成流量是开发机自己产生的

全表 4,790 条记录里，**单个 IP `36.113.xx.xx` 独占 2,743 条（57.3%）**，横跨全部 16 天，且是全表第一条记录（id=1）。

**它的 UA 直接暴露了身份**：

```
Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) ... CodeBuddyCN/1.106.1 Chrome/...
Mozilla/5.0 (Linux; Android 8.0.0; BLN-AL20; HMSCore 6.16.xx.xx; ...) AppleWebKit/537.36
```

出现 **`CodeBuddyCN`** 与 Mac Chrome —— 这是**开发机 / AI 编程工具自身发起的请求**，不是真实用户。
它在 16 天里贡献了 12 个不同 `visitor_hash`，其中单个 hash 就占 2,428 条。

**另一个畸形信号**：机型 `BLN-AL20`（荣耀畅玩 7X，2017 年机型）+ Android 8.0.0 出现 **1,942 次**，
但**只来自 2 个 IP、2 个 visitor_hash** —— 典型的单一设备高频访问，不是用户分布。

**剔除开发机后：真实记录 2,047 条 / 唯一访客 327 个 / 唯一 IP 232 个。**

## 五、可复用方法（已写入 skill）

1. **读 Supabase 走 443 REST**：`curl "$URL/rest/v1/<table>?select=*&order=id.asc" -H "apikey: $KEY" -H "Authorization: Bearer $KEY" -H "Range: 0-999"` 分页。
2. **分析访问数据前必做「开发机污染检测」**：按 IP 聚合，看单 IP 占比；UA 里搜 `CodeBuddyCN` / `Macintosh` / 自家工具标识。
   本次单 IP 占 57.3%，不做这一步会把开发机流量当成用户增长。
3. **单机型 + 单 OS + 极少 IP/hash → 判定为单设备刷量**（本例 BLN-AL20：1,942 次 / 2 IP / 2 hash）。
4. **数据中心 IP 识别**：UA 为 `X11; Linux x86_64`、无机型、地域落在机房常见地（如都柏林）→ 非真实用户。
