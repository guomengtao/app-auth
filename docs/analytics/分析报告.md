## 2. 数据来源与口径说明（必读）

### 2.1 数据来源

| 维度 | 来源 | 说明 |
|---|---|---|
| 订单 | Neon Postgres `kv_strings` 表 `afdian:order:<单号>` | 爱发电同步落库的订单快照，114 条 |
| 访问 | Neon `kv_zsets`（`stats:pages:<日期>`）、`kv_sets`（`stats:uv:<日期>`）、`kv_strings`（`stats:pv/dl/go`） | Upstash KV 的业务镜像 |
| 激活 | Neon `kv_sets`（`auth:activation_codes` 等） | 激活码/兑换码/失败记录集合 |

> ⚠️ **未能获取的数据**：Supabase 上的 `visitor_logs` 明细表（含 IP / UA / 地区 / 来源）因连接证书链校验失败无法读取，故本报告**不含地域、设备、Referer 维度**。如需这些维度，须先修复该连接。

### 2.2 四个必须知道的口径陷阱

1. **PV 并非全部来自网站**。埋点中 `/apk/*` 路径是 **App 内页面**（手机端 App 内部各页），占比高达 **76.4%**；只有非 `/apk/` 路径才是网站页面。二者混在同一 PV 里，**混算会产生严重误读**（详见 §5.2）。
2. **PV 原始记录只有 11 天**（09-23 起），但 `stats:pages` zset 有完整 27 天页面计数。**已验证两者在 11 个重叠日完全吻合（差值 ≤1）**，故用 `pages` 求和**反推补全**了缺失 16 天，报告采用补全后口径（合计 4,798）。
3. **「下载 → 订单」不能算转化率**。下载埋点 09-30 才上线（仅 6 天有数），订单覆盖 31 天，分母不完整，计算会得出 134% 的荒谬值。**本报告不给出该转化率**。
4. **GMV 金额维度无分析价值**。`AFDIAN_PLAN_MAP` 只映射了 1 个套餐（plan_id `54100fe4…`），该档位定价恒为 **¥1.00**（113/114 笔金额完全相同，标准差 = 0）。因此订单的**金额分布、客单价趋势均无信息量**，收入分析应另找渠道（站内打赏页等）。

## 4. 订单分析

### 4.1 走势（图 01 上半）

- **累计曲线近似线性**，日均 3.7 笔，**无衰减也无加速**——说明增长靠稳定的新用户涌入，而非某个爆发点。
- 单日峰值 **11 笔（09-11）**，次高 8 笔（09-17）。
- 无「周末效应衰减」迹象，全月产出平稳。

### 4.2 时段与星期（图 03）

| 维度 | 发现 |
|---|---|
| **时段** | 呈**晚间单峰**：19:30–23:30 为高峰（22 点单小时 14 笔，占全月 12.3%）；午后 13–18 点为次平台 |
| **星期** | **周末显著高于工作日**：周六 27 笔、周日 26 笔 vs 周二仅 7 笔（**周六是周二的 3.9 倍**） |
| **周趋势** | 13 → 25 → 32 → 27 → 15（最后一周仅 2 天，不可比） |

**解读**：用户是学生群体，**周末与晚间是决策窗口**——这与「课程表」的使用场景高度一致（周末整理下周课表）。

### 4.3 用户结构（图 03 右下）

- **109 位买家，105 位仅购买 1 次**，复购率 3.7%（4 人购 2 次，无人 ≥3 次）。
- 复购者多为同一日内重复下单（如 09-07 同一用户 2 笔），**更可能是补单/测试而非真实复购**。
- 单人单次 ¥1 的低价策略下，**复购天然缺乏动力**，这不构成产品问题，但意味着 **LTV 完全依赖新客获取**。

## 5. 访问数据分析

### 5.1 总量与走势（图 01 下半、图 05）

| 指标 | 数值 | 说明 |
|---|---|---|
| 全期 PV | **4,798** | pages 反推口径 |
| 全期独立访客 | **253** | UV 哈希全期去重 |
| 日均 PV / UV | 178 / 11.7 | — |
| 单日最高 PV | 860（09-28） | 见 §5.4 异常分析 |

**增长判定（关键）**：以 09-23 为界切分（App 埋点上线日）：

| 阶段 | 网站 PV/天 | App PV/天 | UV/天 | 网站 PV/UV |
|---|---|---|---|---|
| 09-09~09-22 | 21.9 | 0 | 5.9 | 3.69 |
| 09-23~10-05 | 63.5 | 282.0 | 18.0 | 3.53 |
| **变化** | **+191%** | 埋点新上线 | **+205%** | **基本持平** |

**结论**：网站 PV/UV 稳定在 **3.5~3.7**（人均浏览 3~4 页，健康且无刷量特征）；UV 近 3 倍增长是**真实用户增长**；而总 PV 的「暴涨」全部来自 App 内埋点计入。

### 5.2 结构拆分（图 02、图 05）

- **App 内页面 PV 3,666（76.4%）** vs **网站页面 PV 1,132（23.6%）**。
- App 内 TOP：`home` 1052 → `schedules` 715 → `band` 501 → `settings` 465 → `theme` 252
  → **首页 + 课表 + 手环**三页占 App 内流量 62%，与产品核心链路（课表→手环）完全一致。
- 网站 TOP：`/` 180 → `/go/ev-timetable` 178 → `/activate.html` 137 → `/user-guide.html` 116 → `/apk-download.html` 59
  → `/go/ev-timetable` 是**最重要的引流落地页**（178 PV，仅次于首页）。

### 5.3 下载与跳转（图 02 左下）

- **APK 下载 85 次**（09-30 起有数据，6 天），日均 14 次；峰值 32 次（10-04）。
- **`/go` 跳转 194 次**（18 天有数），峰值 37（09-18）。
- 下载与跳转**并不同步**（跳转早于下载埋点上线），反映的是**两条不同的转化链路**：`/go` 是外部链接点击（如从手环端/二维码跳出），下载是 APK 落地。

### 5.4 异常日分析（图 02 右上）

`PV/UV` 比值上界出现在 09-28（50.6）与 09-29（40.8），显著高于中位 5.3。逐页拆解后：

- **09-28 的 PV 增量集中在 App 内页**：`/apk/home` 280、`/apk/settings` 133、`/apk/theme` 126、`/apk/schedules` 100——而当天 **UV 仅 17**。
- 即：**少数用户当天高频操作 App**（人均 50 页），更像**集中调试/测试**，而非外部攻击（攻击不会去打 App 内页）。
- **同日另有一件独立的事**：09-28 激活失败 72 次、09-29 56 次（见 §6），发生在 **API 层**，在页面 PV 上只体现为 `/activate.html` 的 18 次 PV —— **两件事性质不同，不可混为一谈**。

## 6. 转化链路与健康度（含风险提示）

```
访问 253 位独立访客
   └─ APK 下载 85 次（埋点仅 6 天，口径不可比）
        └─ 激活码池 195 / 兑换码 240
             └─ 已处理订单 113 笔  ← 与爱发电侧 114 笔基本一致（差 1 笔待同步）
                    └─ ⚠️ 激活失败 285 次
```

### ⚠️ 风险点：激活失败次数超过激活码总数

| 项 | 数量 | 备注 |
|---|---|---|
| 激活码（`auth:activation_codes`） | 195 | 已发放 |
| 兑换码（`auth:redeem_codes`） | 240 | 4 位短码（如 `1BZR`/`UP8Z`） |
| **激活失败（`auth:activation_failures`）** | **285** | **285 条记录各不相同**（非同一标识反复失败） |
| 失败集中度 | 09-28：72 次 · 09-29：56 次 | 两天占 45% |
| 失败标识形态 | `auth:activation_failure:<时间戳>:<4位小写字母>` | 尝试的码为 4 位小写字母 |

**判读**：失败记录**全唯一**说明是 **285 次不同的失败尝试**；集中在两天爆发 + 尝试码为 4 位短码，**符合暴力枚举（撞库）特征**。4 位字母码空间仅 26⁴ ≈ 45.7 万，**对抗枚举的强度不足**。

**建议动作**：① 核查 09-28/09-29 的 `/api/activate` 请求来源 IP 与频率；② 兑换码短码位数提升或加失败锁定/限流；③ 确认失败是否已被 rate-limit 拦截（仓库已有 `lib/rate-limit.js`）。

## 7. 结论与行动建议

### 7.1 对「增长」的判断

- **真实增长成立**，但幅度是 **UV 约 3 倍**，不是 PV 表面显示的 14 倍。
- **App 内使用深度优于网站**：App 内 PV 占 76%，说明用户装完 App 后确实在用（`home`→`schedules`→`band` 链路清晰）。
- **订单不依赖网站流量**，属于**产品内转化**；网站的角色是**下载分发 + 激活落地**。

## 附：数据源局限补充说明（2026-10-06 复核更正）

本报告正文提到「Supabase `visitor_logs`（IP/UA/地区明细）连不上，地域与设备维度缺失」。经 2026-10-06 专项复核，**该结论需按下述修正，请勿据此判断线上有故障**：

| 项 | 修正后结论 |
|---|---|
| 故障归属 | **本地分析环境**的网络限制，**不是** Supabase 配置问题、**不是** app-auth 代码缺陷 |
| 证据 | 本地 pg 直连 pooler:6543 报 `SELF_SIGNED_CERT_IN_CHAIN`；`rejectUnauthorized:false` 与内置根证书 CA 均无法绕过——说明证书在握手层被替换 |
| 根因 | 本机出站强制经代理 `HTTPS_PROXY=127.0.xx.xx:57808`，该代理对非 HTTP 端口做 TLS 拦截并重签证书；清空代理后 TCP 直连直接挂起，反向印证「出站必须过代理」 |
| 线上真相 | Vercel 环境无该代理，`visitor_logs` 写入一直正常（数据量持续增长即为证据） |
| 处置结论 | **不改代码**。为绕过本地限制去关闭 SSL 校验，等于拿线上安全性换本地便利，不划算 |
| 缺失维度怎么补 | 在**非沙箱终端**直连，或由用户在已登录后台导出（`GET /api/admin/catalog?kind=health` 走 `visitorLog.dayOverview / listRecent`，匿名访问正常返回 401，鉴权行为符合预期） |

**因此**：本报告的地域、设备、来源明细维度"未覆盖"，属**分析侧取数受限**，不代表这部分数据不存在或异常。

**补记（同日第二次尝试）**：按「走 HTTP CONNECT 隧道绕开拦截」的思路又试了一次 —— 本地起 TCP 转发、对代理发送 `CONNECT pooler:6543`、
隧道监听正常，但 pg 连上去**仍报** `SELF_SIGNED_CERT_IN_CHAIN`；`openssl s_client -proxy` 抓不到证书链，代理根证书也未暴露给会话环境。
**结论：该代理对 CONNECT 隧道同样实施拦截重签**，本地沙箱内不存在可行绕过，只能在非沙箱终端取数。

## 附二：地域/设备维度已补齐 + 结论重要修正（2026-10-06 14:40）

**先更正**：本报告此前称「Supabase `visitor_logs` 连不上，地域与设备维度缺失」——
**该结论错误**。PG 直连（6543）确被本机代理拦，但**走 443 的 PostgREST REST API 完全可读**，
已成功拉取 **4,790 行**（09-18 ~ 10-06）。完整补充分析见同目录
**《用户访问-地域与设备维度补充分析.md》**。

**最重要的新发现（影响本报告所有"增长"结论）**：

| 项 | 数值 |
|---|---|
| `visitor_logs` 总记录 | 4,790 |
| **单一 IP `36.113.xx.xx` 占比** | **2,743 条 = 57.3%**（UA 含 `CodeBuddyCN/1.106.1` + Mac Chrome → **开发机/AI 工具自流量**） |

| 真实唯一 IP | 232 |

**因此**：本报告「总 PV +1349%」不只是 App 埋点上线造成的假象，**其中 57.3% 更是开发机自己产生的**。
