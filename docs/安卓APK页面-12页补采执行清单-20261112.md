## 一、为什么需要这份清单

`android-apk.html` 是「逐页截图档案」，共 16 页。2026-11-12 已把有真机实拍的 4 页
（首页 / 课表 / 手环 / 设置）换成 v0.6.8 并上线，其余 **12 页仍是 2026-10-05 的
v0.5.166 旧图**，页面里标 `legacy:1` 与灰色「旧版存档」徽标。

补采被外部条件卡住，不是代码问题：

| 阻塞 | 实测 |
|---|---|
| `adb devices` | 空，无 `device` 状态行 |
| AVD / emulator | 本机无 `emulator` 可执行程序、无 AVD 列表、无 qemu 进程 |
| 全库新图 | 11-05 之后的图片全是 `ev-class-face/dist/` 表盘产物，与 APK 页面无关 |

按仓库「真机截图比对铁律」，**不拿设计图、合成图、旧图冒充实拍**。因此本轮把
「设备恢复后」的动作固化为脚本 + 清单，设备一上线即可执行，不必重新分析。

## 二、脚本能做什么、不能做什么

| 能做 ✅ | 不做 ❌ |
|---|---|
| 抓设备当前屏 → 按 `*-v<版本>.png` 落盘 | 不自动导航 APP 页面（翻页由人在设备上完成） |
| `legacy:1 → fresh:1`、改文件名/版本/时间 | 不伪造截图；设备离线时抓取直接拒绝 |
| 联动 `shotSets` 双计数、`capturedAt`、`pageUpdatedAt` | 不改线上已发布的 4 页 |
| 重写 `stateNote` / `footer` 里的 4/12 静态数字 | 不擅自 `git add -A`、不碰其它会话 WIP |
| 同步进 `.vercel/output` 预构建产物 | 不自动 commit / push（人工复核后走流程） |
| 自带结构校验 + Node 解析 `DATA` | 不删除旧图（保留存档，便于回溯） |
| `--interactive` 逐页提示翻页，一条命令补完 12 页 | 不用 `setClipToOutline` 之类 UI 手段凑图 |

3. **演练副本（可选但推荐）**：先 `--dry-run` 或 `--root /tmp/xxx` 跑一遍，确认替换逻辑。

## 六、每补一页，脚本自动改 6 处

1. 该页 `shots` 块：`file` / `version` / `at` 更新，`legacy:1 → fresh:1`（徽标由灰变绿）
2. `shotSets.fresh.count +1`、`shotSets.legacy.count -1`
3. `shotSets.fresh.version / at / size / source` 更新为最新采集批次与实拍尺寸
4. `capturedAt` 改双批次口径；旧版归零后自动去掉「旧图」半句
5. `pageUpdatedAt` 改为当天
6. `stateNote` 提示条与 `footer` 里的「N 页新版 / M 页旧版」静态数字重写

页面每张图自身仍保留 `version` / `at` 精确信息；`shotSets.fresh.version` 表示
**最新采集批次**（首批 4 页是 v0.6.8，后续补采是另一批次），`source` 里已注明。
新文件名天然破缓存，`renderShots` 的 `?v=20261112` 不必改。

## 八、常见故障

| 现象 | 处理 |
|---|---|
| `设备不在线，拒绝补采` | 脚本按铁律主动拒绝。连上真机/模拟器后重跑，**不要**改用 `--simulate` 绕过 |
| `adb exec-out screencap` 失败 | 脚本用 `shell screencap → pull` 链路（比 `exec-out` 稳）；仍失败则查 `adb shell echo ok` |
| 尺寸打印为 `?` | 装 Pillow 或确认 `sips` 可用；`size` 留空时人工复核 `shotSets.fresh.size` |
| `已是新版实拍，拒绝重复补采` | 该页已补过；确需重截先人工把该 shots 块改回 `legacy:1` 再跑 |
| `shots 块定位不唯一` | 页面结构被别的会话改过，先 `--status` 看解析结果，别硬改脚本 |
| 版本写错 | 用正确版本重跑前，先 `git diff` 人工修正 `version` / `at` / 文件名三处 |
| 补采后线上还是旧图 | 查 Vercel 部署是否 Ready；图片 URL 带新文件名应天然破缓存 |
