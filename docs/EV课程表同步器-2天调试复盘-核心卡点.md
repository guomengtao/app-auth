# EV 课程表同步器：2 天调试复盘（核心卡点）

> 现象起点：插件**能启动**手环上的 EV 课程表，但点「读」没有任何反应、读不到数据。
> 结论：**平台没问题、宿主没问题、手环 EV 没问题 —— 4 个 bug 全在插件自己**，而且它们互相掩护。
> 详细分析：`docs/EV课程表同步器-读不到数据原因分析.md`

---

## 一、一句话结论

**卡点不在"发不出去"，而在"发出去之后没人知道结果"**：

- QAIC 下发**没有 ACK**，`send_qaic_message` 返回 `Ok` 只代表"宿主受理了"；
- 同时插件把回包**在解析前就吞掉/认错**（死锁吞掉、信封认错）；
- 于是现象与真因**完全反向** —— 看起来"通道不通"，实际是"通道一直通，插件自己没接住"。

---

## 二、真正卡住我们的 4 个 bug（按危害排序）

| # | 卡点 | 真因 | 为什么难发现 | 修复 |
|---|---|---|---|---|
| 1 | **回包被吞**：点读之后"没反应、日志不动" | `push_log()` 内部要 `STATE.lock()`，而调用处**已经持有**这把**不可重入**的锁 → wasm 单线程里永久死锁 → `on_ui_event` 永不返回，此后所有事件（含 Timer）都不再派发。共 **8 处**（`handle_device_message` 6 处 + 导入到手环 + sgschedule） | 死锁发生在**打日志那一行之前**，所以日志里连一条 `[RX]` 都没有 —— 与"根本没收到回包"**表象完全一样** | **v1.0.56**：新增 `push_log_locked()`，持锁处专用 |
| 2 | **回包认不出来**：明明收到 10KB 回包，却显示"无法识别" | 宿主 `on_event(InterconnectMessage)` 给的是**事件信封** `{"addr","payloadHex","payloadText"}`，插件却把整个信封当业务报文喂给各解析器 → ping/export/update_settings **全部**解析失败 | 三层解析器都"解析成功但字段全空"（字段都是 `Option`），不报错 | **v1.0.57**：`decode_event_payload()`，优先 `payloadText`、否则 hex 解码 |
| 3 | **错误被伪装**：所有东西都显示"收到 basic 回包" | `BasicResponse` 字段全 `Option` + serde 忽略未知字段 → **任意 JSON 对象都"解析成功"**，把 bug 2 的错误统一伪装成"收到 basic 回包" | 它让 bug 2 隐身了整整一天多：日志看起来"有反馈、很正常" | **v1.0.57**：强制要求存在 `ok` 字段，否则返回 Err |
| 4 | **业务报文被多剥一层** | `unwrap_envelope()` 无条件剥最外层 `data`，但 **export 的业务回包自带 `data`**（就是课表数据），一剥之下 `ok`/`action`/`scopes` 全丢；另外课表用强类型 `DaySchedule/ClassEntry`，任一字段类型不符会让**整包**反序列化失败 | ping 回包**不含 `data`**，所以 ping 通了而 export 不通 —— 差异极小、极易误判 | **v1.0.58**：外层含 `ok`/`action` 就原样返回；课表改 `flatten_schedule()` 宽容拍平（坏字段只跳单条） |

## 三、次要坑（不致命，但每次都多绕一圈）

| 坑 | 说明 | 修复 |
|---|---|---|
| `launch-qa => Ok(())` 被当成"已启动" | 只代表宿主受理；已运行实例走 `onShow`，不重跑 `onCreate`（接收器注册在 onCreate） | 靠实测确认"手环确实立刻打开"排除 |
| `set_timeout(300, "interconnect-ready")` 是**假等待** | `set_timeout` 异步立即返回、payload 无人消费 → 实际"注册后立即发送"；日志里那句"注册后等待 300ms 完成"是假的 | v1.0.56 删除 |
| 启动后 ping **只发一次、不重试** | 落在 EV 冷启动窗口内必丢，且无 ACK | v1.0.59 加 5 秒超时结论；重试式 ping 仍是待办 |
| 手动「启动 EV」按钮不带自动 ping | 只有"选设备"流程会排 auto-ping，两条路径行为不一致 | v1.0.56 补齐 |
| 界面版本号与 manifest 不一致（1.0.54 vs 1.0.55） | 远程排错时无法确认用户装的是哪个版本 | v1.0.56 同步；核对版本看页脚 `v… · 当前:<页名>` |
| 日志框太小 | 一屏看不到完整交互过程 | v1.0.59 `160 → 480`（3 倍） |

## 五、为什么绕了整整两天（三个"掩护"机制）

1. **死锁掩护了回包**：回包到达的第一件事（打 `[RX]` 日志）就卡死 → 回包"看起来不存在"。
2. **空洞成功掩护了错误**：解析器"返回 Ok"却什么都没认出 → 错误"看起来成功"。
3. **无 ACK 掩护了发送**：`send = Ok` 只代表受理 → "发出去了"与"收到了"在日志上无法区分。

三者叠加，任何单点推断都会被误导到错误方向（我们先后怀疑过平台、EV 版本、后台常驻、注册竞态）。

## 六、可复用的教训

1. **`Mutex` 不可重入**：持锁期间只能调 `*_locked` 版本；写日志/辅助函数前先看当前作用域有没有活着的守卫。
2. **解析器"返回 Ok" ≠ "认出报文"**：`parse_*` 必须要求特征字段（如 `ok` / `action`）存在，否则会把错误吞成"成功"。
3. **分层剥壳前先判断这层是不是业务报文**：业务报文自己也可能带 `data` 字段，无条件剥会把业务字段剥掉。
4. **反序列化不要做全有全无**：网络侧字段类型/缺失都可能变，用裸 JSON + 宽容取值，坏一条跳一条。
5. **没有 ACK 的通道必须自己造反馈**：发送后登记"待回包 + 超时结论"，否则用户只能看到"已发送"发呆。
6. **先证明哪一段不通，再改代码**：本次转折点是"用 `import`（最古老、必被支持的能力）验下行通道" + "让手环回包可见"，而不是继续改协议报文。
