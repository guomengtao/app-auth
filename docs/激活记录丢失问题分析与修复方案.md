# 激活记录丢失问题分析与修复方案

- 报告日期：2026-09-24
- 涉及页面：后台「激活记录」(`admin_Dx23.html` → `tab=records`)、后台「消息投递」
- 涉及接口：`/api/admin/health?section=records`（原 `/api/admin/records`，已合并）
- 结论：**不是记录被删除，而是「复用激活」在旧版实现里原地覆盖了首次那条记录，导致新激活不产生新行**。已在 `192a537` 修复，历史遗留 2 条无法从记录侧还原。

## 一、现象

1. 后台「消息投递」页有 `new_activation` 通知且状态 `✅ 已送达`；
2. 后台「激活记录」页对应时间点没有新行，列表里看不到这次激活；
3. 用户复述：*"我最近收到 2 条激活通知，但是记录里没看到"*。

用户提供的现场快照：

| 页面 | 内容 |
| --- | --- |
| 激活记录（表格） | 成功 `003371 139788 282822 ->` / 兑换码 `CWDG` / 设备 `818a` / 2026/9/24 11:26:40 / 永久<br>成功 `003322 057260 879562 ->` / 兑换码 `C6QS` / 设备 `1234` / 2026/9/24 08:54:32 / 2026/10/24 |

即：`CWDG` 的通知**有**记录；`YI1O` 12:11:16 的通知**没有**记录。

## 三、根因分析

### 根因 1（主因）：复用激活「原地覆盖」首次记录，不产生新行

旧版 `api/activate.js` 复用分支（同兑换码 + 同设备再次激活）：

```js
mergedRecord = Object.assign({}, _existing, {
  activation_code: activationCodeReuse,
  generated_at: _existing.generated_at || reuseNow,   // ← 保留首次时间
  expires_at: reuseExpires,
  ...
});
reusePipeline.set("auth:activation:" + activationCodeReuse, JSON.stringify(mergedRecord));
```

三个致命点：

1. **写入的是同一个 key**（`auth:activation:<激活码>`），不是新 key；
2. `generated_at` 用 `_existing.generated_at || reuseNow` 保留首次时间 → 列表按 `generated_at` 倒序，这一行永远不会"冒到最上面"；
3. 激活码是 `sha(product, device, months, redeemCode)` 的确定性函数 → 同一兑换码 + 同一设备算出的激活码**恒定**，所以永远命中同一行。

结果：**用户明明激活成功（通知已发），记录页却看不到"这次"激活**，只在详情里看到一条时间很旧的行。

> 为什么"通知有、记录无"能同时成立？
> 因为通知是在写库之后独立发出的（`notify.pushNotification("new_activation", ...)`），覆盖写成功也会发通知，两者并不互为校验。

### 根因 2：`tracking_events` 去重键撞车，事件流同样丢掉这次激活

旧版复用的 `dedupeKey` 是 `"ac:" + activationCodeReuse`，与首次激活**完全相同**：

```js
dedupeKey: "ac:" + activationCodeReuse    // 旧版：与首次激活重复
```

而 `lib/tracking.js` 的写入是：

```sql
insert into tracking_events (...) values (...)
on conflict (dedupe_key) do nothing
```

→ 复用事件被当成重复事件**静默丢弃**。

实测 `tracking_events` 中 `dedupe_key like 'ac:004860393496999814%'` 只有 3 条（9/16 首次、13:23:40 `:2`、13:30:30 `:3`），**12:11:16 那条不存在**。这就是「通知有、事件流也没有」的原因，漏斗 / 用户画像同样漏掉这次激活。

### 根因 3（潜伏，尚未触发）：`section=records` 只取一批 `SSCAN`，忽略游标

```js
var ss = await redis.sscan(setKey, 0, { count: recCount });   // ← 只调一次，游标丢弃
var keys = Array.isArray(ss) ? (ss[1] || []) : (ss && ss.keys) || [];
```

`lib/redis.js` 的 `sscan` 是 `SELECT member FROM kv_sets WHERE key=$1 ORDER BY member LIMIT $2 OFFSET $3`，返回 `[nextCursor, keys]`。

- 当前集合 129 条 < 500，**暂未触发**（余量 371 条）；
- 一旦超过 500，接口只会返回"按 member 字典序前 500 条"，其余**静默丢失**，且**不报错**；
- 项目里其它地方（`lib/tracking.js scanSet`、`lib/user-journey.js batchGetByMembers`）都是 `smembers` 全量 + 分批 `mget`，只有 records 接口用了单次 `sscan`，属实现不一致。

### 根因 4（潜伏）：`pipeline().exec()` 吞错，可能产生"孤儿 member"

`lib/redis.js`：

```js
exec: async function () {
  ...
  } catch (e) {
    results.push(null);     // ← 错误被吞成 null
  }
}
```

`api/activate.js` 里只做了 `console.error`：

```js
var writeFailed = writeResults.some(function (r) { return r === null; });
if (writeFailed) { console.error("activate.js pipeline had failures:", writeResults); }
```

若 `set("auth:activation:...")` 失败而 `sadd("auth:activation_codes", ...)` 成功，就会出现 **member 存在、value 缺失** → 接口 `mget` 拿不到值 → 记录彻底不可见且无告警。本次核对为 0 条，属"未爆的地雷"。

## 四、已修复内容（提交 `192a537`，2026-09-24 13:21）

| 改动 | 说明 |
| --- | --- |
| 复用改为**追加** | 首次记录 `auth:activation:<激活码>` 原样保留；本次追加 `auth:activation:<激活码>:<seq>`，并 `sadd` 对应的 `:seq` member |
| `activation_seq` 序号 | 优先取 `auth:redeem:<code>.activation_seq` 累计值，退回首次记录，兜底 1；写回兑换码记录 |
| `generated_at: reuseNow` | 复用行使用真实发生时间，列表能"冒泡"到最上面 |
| `activation_member` / `is_repeat` / `first_activated_at` | 新字段，记录首次激活时间与本次是第几次 |
| `dedupeKey: "ac:" + reuseMember` | 事件流去重键带上 `:seq`，不再被首次激活吞掉（同时把旧的重复行按 conflict 忽略） |
| 后台展示 | 激活记录状态列新增「第 N 次激活」徽标；详情面板展示激活次数 / 记录 Key |
| `verify-activation` 兼容 | 顺着 `auth:redeem:<code>.activation_seq` 取最新 `:seq` 行，用最新 `expires_at` 判有效期 |
| 接口地址合并 | `/api/admin/records` → `/api/admin/health?section=records`（Vercel 函数文件数 ≤ 10 硬约束） |

**已在线上验证生效**：`/api/admin/records` 返回 `HTTP 404`，`/api/admin/health?section=records` 正常（需登录）；13:23:40 / 13:30:30 两次复用的通知、记录、事件三者齐全。

## 五、遗留问题

### 5.1 2 条历史复用记录无法从记录侧还原

`2026/9/18 01:15:11`（设备 `df55`）与 `2026/9/24 12:11:16`（`YI1O` / `00NA`）这两次复用，旧版已把新数据**覆盖进首次那条记录**（`expires_at` / `device_info` / `visitor_info` 已被改写，但 `generated_at` 保留首次时间）。

- 首次记录本身**没丢**（激活码、设备、时长都在）；
- 丢的是"这次激活发生过"的痕迹；
- 原始时间与 IP 只能从 `message_delivery` 的 `payload`（`ip` / `city` / `months` / `device_id` / `source`）反查。

补录思路（可选，需人工确认后再执行）：以 `message_delivery` 中 `source='user-reuse'` 的通知为基准，用 `payload.device_id` + `related_code` 反算激活码，构造 `:seq` 行写入 `kv_strings` 与 `kv_sets`：

```sql
-- 1) 找出所有复用通知（作为补录基准）
select created_at, related_code, payload->>'device_id' as dev,
       payload->>'months' as months, payload->>'ip' as ip
from message_delivery
where message_type = 'new_activation'
  and payload->>'source' = 'user-reuse'
order by created_at;

-- 2) 找出已有独立复用行（避免重复补录）
select member from kv_sets
where key = 'auth:activation_codes' and member ~ ':[0-9]+$';

-- 3) 找首次记录（补录时继承 device_info / 首次时间）
select key, value from kv_strings
where key = 'auth:activation:<激活码>';
```

> 由于历史数据已被覆盖，12:11:16 那次激活的 `visitor_info`（IP / UA）只存在于 `message_delivery.payload`，补录时按"通知为准"填。

### 5.2 激活记录总数偏少的即时排查口径

按以下顺序判断"是丢了还是没到"：

1. `select count(*) from kv_sets where key='auth:activation_codes';` 与
   `select count(*) from kv_strings where key like 'auth:activation:%';` 是否相等 → 不等说明有孤儿 member；
2. set 里带 `:` 后缀的 member 数量，应等于"修复后发生的复用次数"；
3. `message_delivery` 中 `new_activation` 的通知条数应 ≥ set 中的记录行数（通知是"发生过"的唯一可靠凭据）；
4. 若通知数 > 记录行数，差值 = 被覆盖/未写入的激活次数。

### 本轮实现细节

**`api/admin/health.js` · `section=records`**

- 取数：`smembers(setKey)` 全量 → 每 200 条一次 `mget`（一次 `SELECT ... IN`），不再单次 `sscan`；
- 安全上限：`max`（默认 20000，可调 1000–50000）防止集合无限增长把函数拖垮，超限截尾并置 `truncated`；
- 返回体新增 `total` / `fetched` / `returned` / `truncated`；`count`（默认 500，上限 2000）只裁剪返回条数，且如实上报裁剪；
- 检测"孤儿 member"（`sadd` 成功但 `set` 失败）并 `console.error` 留痕。

**`api/activate.js` · 写库失败上报**

- 新增 `reportPipelineFailures(results, ops, ctx)`：把 `exec()` 的 `null` 结果定位到**具体命令**（如 `set auth:activation:xxx`），`console.error` 之外再推一条 `activation_failure` 通知；
- 首次激活的 `writePipeline` 与复用激活的 `reusePipeline` 都接入。

**`admin_Dx23.html` · 记录页**

- 新增 `_recordsMeta`，在筛选提示条里显示：`⚠️ 库中共 N 条，本次仅返回最近 M 条，更早的记录未展示`。

> 验证：本地用新逻辑直连线上库取数 —— `auth:activation_codes` 129 条 / `auth:activation_failures` 132 条，**全部取到、孤儿 0 条**（旧实现同样 129/132，说明当前数据量下两者等价；差异只会在集合超过单批上限时暴露）。
