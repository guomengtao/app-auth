# 用户激活验证码功能 · 测试报告

> 视角：**终端用户 / 测试人员**（不关心代码实现，只关心"我能不能顺利激活、失败时提不提示、会不会卡死"）
> 被测对象：`activate.html` + `POST /api/activate`
> 被测地址：`https://app-auth.gudq.com/activate.html`
> 测试日期：2026-09-18
> 结论速览：**功能"正常"，但"稳定性"有明确短板（限流 + 无超时 + 异步通知拖慢响应）**

---

## 一、结论速览（先看这里）

| 维度 | 结论 | 说明 |
|------|------|------|
| **主流程能否激活** | ✅ 正常 | 正确兑换码 → 3 秒内返回 18 位激活码 |
| **失败是否有提示** | ✅ 正常 | 兑换码不存在 / 被占用 / 格式错，都有明确中文提示 |
| **重复激活（同一设备）** | ✅ 正常（幂等） | 返回同一个激活码，不会报错 |
| **换设备激活** | ✅ 正常（拒绝） | 提示"已被其他设备使用过，如需解绑请联系作者" |
| **限流是否合理** | ⚠️ 有风险 | IP 15 次/分钟，**但页面一打开就自动消耗 1 次**；设备 10 次/天 |
| **稳定性 / 会不会卡死** | ❌ 有风险 | 前端 XHR **没有超时兜底**，服务端慢时按钮会一直转圈 |
| **响应速度** | ⚠️ 偏慢 | 服务端在返回结果前要先等邮件/推送发送完成 |

**一句话给用户的建议**：正常网络下可以放心激活；**如果点了"立即激活"一直转圈超过 15 秒，直接刷新页面重试**（刷新会多消耗一次限流额度，所以不要连续狂点）。

1. 页面标题：**设备激活**
2. "设备ID"输入框是**灰色只读**的，不能手动改

## 五、第三组：设备绑定相关（最容易踩坑的一组）

### TC-11 同一设备重复激活（幂等）

| 项 | 内容 |
|---|---|
| **步骤** | 用同一个设备ID + 同一个兑换码，连续激活 2 次 |
| **预期结果** | 两次都成功，**返回同一个 18 位激活码**（不会报"已被使用"） |
| **注意（用户必读）** | 第二次激活会**在原有效期基础上叠加时长**。例如 12 个月的码再激活一次，到期时间会往后加 12 个月。**不是覆盖，是叠加** |
| **判定** | 通过（行为正确，但用户容易误以为是"重新计时"） |
| **需实测** | ☐ |

### TC-12 换设备使用同一兑换码

| 项 | 内容 |
|---|---|
| **步骤** | 用设备 A 激活后，再用同一个兑换码在设备 B 的页面上激活 |
| **预期结果** | 设备 B 报错「该兑换码已被其他设备使用过」 |
| **判定** | 通过 |
| **需实测** | ☐ |

### TC-13 ⚠️ 直接打开网页（不带设备参数）

| 项 | 内容 |
|---|---|
| **步骤** | 直接在浏览器输入 `https://app-auth.gudq.com/activate.html`（没有 `?deviceId=` 参数），输入正确兑换码激活 |
| **预期结果（实际）** | **会提示激活成功**，并给出激活码。但此时设备ID是**浏览器随手生成的 4 位随机字符**（页面会显示"设备ID来源: 本地生成"） |
| **风险** | 兑换码会被**永久绑定到这个假设备**上，手环端拿到的激活码**无法使用**，且这个码以后再也不能在真设备上激活 |
| **建议** | 页面在"本地生成"状态下应**阻止激活**并提示"请从手环/应用内打开本页面"。当前代码未做此拦截 |
| **判定** | ⚠️ **设计缺陷，建议反馈** |
| **需实测** | ☐ |

## 六、第四组：限流与稳定性（本次重点）

### 限流规则（用户需要知道的三条）

| 限流 | 额度 | 用户感受 |
|---|---|---|
| IP 限流 | **15 次 / 分钟**，但**页面一打开就自动消耗 1 次**（埋点） | 实际约 **14 次/分钟**；提示"请求过于频繁，请稍后再试" |
| 设备限流 | **10 次 / 天**（按"设备ID + 兑换码"计算） | 超了提示"该设备激活次数过多，请明天再试" |
| 共享 IP | 同一 WiFi / 校园网 / 公司网下**所有用户共用这 15 次** | 别人疯狂重试，可能连累你被限流 |

### TC-14 快速连续点击

| 项 | 内容 |
|---|---|
| **步骤** | 连续快速点"立即激活" 15 次以上 |
| **预期结果** | 超过上限后返回「请求过于频繁，请稍后再试」，**下一分钟自动恢复** |
| **判定** | ✅ 机制正确（当前代码用"每分钟独立计数"，60 秒后会自愈） |
| **需实测** | ☐ |

### TC-15 限流后等待自愈

| 项 | 内容 |
|---|---|
| **步骤** | 触发限流 → 什么都不做等 **65 秒** → 再提交一次 |
| **预期结果** | **恢复正常**，可以继续激活 |
| **判定** | ✅（历史版本曾出现"永久 429"，现版本按分钟分区已规避，**必须实测确认**） |
| **需实测** | ☐ **重点回归** |

### TC-16 ⚠️ 按钮永久转圈（无超时）

| 项 | 内容 |
|---|---|
| **步骤** | 打开手机飞行模式或限速到极慢 → 点"立即激活" |
| **预期结果（应有）** | 若干秒后提示"网络错误，请检查网络后重试" |
| **预期结果（实际）** | 请求层只会提示"网络错误"，但**如果服务器只是"慢"而不是"断"，按钮会一直停在"激活中..."**，因为前端请求**没有设置超时** |
| **用户自救** | 等超过 15 秒仍无反应 → **刷新页面重试**（刷新会多消耗 1 次 IP 额度） |
| **判定** | ❌ **稳定性缺陷（已知问题，代码中 XHR 未设 timeout）** |
| **需实测** | ☐ |

## 八、汇总：到底"正常"吗？"稳定"吗？

### ✅ 正常的部分（功能正确性）

1. **主流程通畅**：正确码 → 18 位激活码，链路完整
2. **提示友好**：6 种失败场景文案清晰、区分明确
3. **幂等正确**：同设备重复激活不报错，返回同一个码
4. **防串用有效**：一码一设备，换设备被拒绝
5. **限流能自愈**：按分钟/按天分区，不会永久封禁

### ⚠️ 不稳定的部分（可用性 / 稳定性）

| # | 问题 | 用户会遇到的现象 | 严重度 |
|---|---|---|---|
| 1 | **前端请求无超时** | 点了"立即激活"按钮永久转圈，只能刷新 | **高** |
| 2 | **服务端返回前要先发通知** | 正常激活也可能等十几秒 | **高** |
| 3 | **埋点与激活抢同一份 IP 额度** | 共享网络下额度提前用光，被"连坐"限流 | 中 |
| 4 | **无设备参数也能激活** | 码被绑定到随机假设备，手环用不了 | 中 |
| 5 | **小时长在月末可能顺延** | 会员天数略少 | 低 |
| 6 | **限流无后台解除入口** | 一旦误封只能等，或找作者 | 中 |

### 📌 给用户的最终判断

> **能正常用，但称不上"稳定"。**
> 在网络正常、从手环链接进入、一次输对的前提下，体验是没问题的。
> 一旦出现"输错几次"或"网络较慢"，就容易碰到**限流**和**按钮转圈**这两个坑。

### 📌 给项目的 4 条改进建议（按性价比排序）

1. **给前端加超时**：`xhr.timeout = 15000` + 超时提示 —— 一行代码，直接消灭"永久转圈"
2. **先返回结果、再发通知**：把邮件/推送挪到响应之后，激活耗时立刻从秒级降到百毫秒级
3. **埋点用独立限流 key**：让"打开页面"不再消耗用户的激活额度（约可多 1 次机会）
4. **"本地生成设备ID"时禁止激活**：提示用户"请从手环/应用内打开"，避免码被绑到假设备
